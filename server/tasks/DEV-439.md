## DEV-439 Provision ID login for an existing UAT producer

- Issue: [DEV-439](https://linear.app/sswp6/issue/DEV-439)

### Goal
Allow an operator to attach ID credentials to an existing eligible UAT producer so the same user can use its already-linked farm. Never create a replacement user or mutate farm/product/order state.

### Out of scope
- No production database or settings operation.
- No changes to UAT user test classification, farm/product visibility or approval, inventory, or orders.
- No migration unless implementation proves a schema change is necessary; current username/hash/token fields should suffice.
- No new user creation or farm reassignment.

### Decisions
- 2026-11-23: Add a separate existing-user provisioning action. Allow only an active seed-test PRODUCER with no username/hash and an existing linked farm. Assign a validated operator-chosen login username; keep `User.id`, role, `is_test_account`, and farm link unchanged.
- 2026-11-23: Treat an ID-credentialed seed producer like an ID account for the existing password-change and current-consent gates. Other seed accounts retain the existing consent exemption.
- 2026-11-23: Do not use idempotency storage for one-time credentials. Repeated provisioning returns conflict; use the existing audited temporary-password action only after initial credentials exist.
- 2026-11-23: Actual UAT farm/product state is not verified from this workspace. The operator must verify the current user/farm/product association and status read-only before provisioning; this action cannot change a pending/hidden farm into an operable one.
- 2026-11-23 review: Match the UI eligibility to the linked-farm requirement. Use a non-submitting input container so Enter cannot navigate away from a one-time secret; bind confirmation to the chosen username. Extend coverage for authorization, ineligible accounts, login-unlock and concurrent issuance. No production mutation is part of implementation validation.
