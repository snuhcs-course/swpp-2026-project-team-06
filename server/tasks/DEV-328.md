## DEV-328 Serve published product photos as resized JPEG/WebP with caching instead of full-size PNG

- 이슈: [DEV-328](https://linear.app/sswp6/issue/DEV-328) (선행 조사 DEV-325)
- 브랜치: `jangjinuite/dev-328-published-photo-size`
- 기능·인수 조건: FEAT-03/04 · AC-SRC-6(공개 사진 독립 수명)·AC-SRC-9(공개 사진 접근). 근거 `docs/spec/source-integration.md` 상품사진 줄
- 상태: 진행 중
- 위험 등급: 일반(고위험 경로를 바꾸지 않는다. `server/app/core/images.py`는 `sniff`를 불러 쓰기만 한다)

### 왜
실제 생산자 피드백: 페이지가 느리다. DEV-325 조사에서 서버 쪽 가장 큰 원인이 나왔다.
- 공개 반영(`publish.py` `copy_photo`)이 상품사진마다 원본 해상도 PNG로 다시 저장한다. 대표 사진(커버)이 상품 대표 사진 `/api/source-media/{id}`가 되어 소비자 상품 상세·홈 카드·농가 목록이 모두 이 파일을 받는다.
- `/api/source-media/{id}`는 `image/png`·`Cache-Control: no-store`로 내보내서 같은 사진을 화면마다 처음부터 다시 받는다.
- 780px 사진에서 PNG가 JPEG의 6~6.6배다(예: 120,319 B → 795,778 B). 휴대폰 원본(4032×3024 등)은 수십 MB가 된다.

### 목표
새로 공개되는 상품사진은 표시에 충분한 크기의 JPEG로 저장하고, `/api/source-media/{id}`는 실제 형식의 Content-Type과 짧은 캐시·ETag로 내보낸다. 접근 규칙(현재 공개 상품이 참조하는 사진만)은 그대로 둔다.

### 결정 사항
- 11/15 **크기**: 긴 변 최대 1600px, 작은 사진은 키우지 않는다. 앱 본문 최대 폭이 480 CSS px(`packages/ui/src/tokens.ts` `maxWidth`)라 3x 화면 전체 폭에 1440px가 필요하다. 1600px는 가로 사진(1600×1200)을 3x 전체 폭에 채우고, 세로 사진(1200×1600)도 2.5x 이상이다. 비율은 유지하고 자르지 않는다.
- 11/15 **형식**: JPEG(quality 82, progressive, optimize). React Native `Image`(iOS·Android·웹)와 모든 브라우저가 문제없이 읽는다. WebP는 비슷하게 더 작지만 오래된 iOS(14 미만)·일부 공유 미리보기에서 위험이 있어 쓰지 않는다. 투명도는 기존처럼 RGB로 바꾼다(상품 사진에 투명 배경을 쓰지 않음).
- 11/15 **메타데이터**: 변환 전에 EXIF 방향을 적용하고(`ImageOps.exif_transpose`) EXIF·XMP·ICC 없이 저장한다. ICC를 버리는 것은 기존 PNG 경로와 같다(분석용 PNG 단계에서 이미 버려짐).
- 11/15 **Content-Type**: 마이그레이션 없이 저장 바이트 앞부분으로 판별한다(`app.core.images.sniff`). 기존 PNG 사진은 계속 `image/png`, 새 사진은 `image/jpeg`. 판별이 안 되면 `application/octet-stream` + `nosniff`.
- 11/15 **캐시**: `Cache-Control: private, max-age=300` + `ETag`(scan-before-merge 반영: API 앞에 CDN이 없어 `public`과 효과가 같고, `private`면 공개 취소 뒤 공유 프록시에 남지 않는다). 사진 id 하나는 저장 키 하나를 가리킨다(`Storage.put`이 새 uuid 키를 만든다, 다시 공개하면 새 `PublicPhoto` id가 생긴다, 변환 명령은 키를 새로 쓴다). 그래도 접근 여부는 상품이 계속 공개 중인지에 달려 있어 긴 캐시(immutable)는 쓰지 않는다. 공개 취소 뒤 최대 5분까지만 캐시에서 보일 수 있다(원래 공개였던 사진). ETag는 저장 키의 해시라 저장 키를 노출하지 않고, 변환 명령으로 저장 키가 바뀌면 ETag도 바뀐다. `If-None-Match`가 맞으면 접근 검사를 통과한 뒤에만 304를 주고, 이때 저장소(R2)를 읽지 않는다.
- 11/15 **작업 공간 업로드**(`POST /product-workspaces/{pid}/photos`): 같은 `/api/source-media/{id}`로 소비자에게 나가므로 같은 JPEG 변환을 쓴다. 생산자 미리보기(`GET /product-workspaces/{pid}/photos/{id}`)는 비공개라 `no-store`를 유지하고 Content-Type만 판별한다.
- 11/15 **`prepare_photo`(분석용 비공개 사본)**: 소비자 경로가 아니다(자료 분석 페이지 이미지·공개 반영의 원천). 무손실 PNG를 그대로 둔다. 공개 반영이 이 PNG에서 JPEG를 만든다.
- 11/15 **기존 공개 PNG**: 새 공개부터 작은 형식이 적용된다. 이미 공개된 사진은 사람이 실행하는 명령 `python -m app.source_analysis.recompress_photos`(기본 미리보기, `--commit`일 때만 변경)로 같은 id를 유지한 채 JPEG로 바꿀 수 있다. URL이 같아 상품 데이터는 바꾸지 않는다. 새 키를 쓰고 커밋하며, 옛 키는 바로 지우지 않고 worker cleanup이 지운다(읽는 중인 요청이 깨지지 않게). 예전 PNG는 되돌릴 수 없어(작업실 업로드는 원본 크기 사본이 이것뿐일 수 있음) `--commit`에는 R2 백업 확인 `--backup-done`이 함께 있어야 한다. 실패한 사진이 있으면 종료 코드 1(scan-before-merge 반영).
- 11/15 **`/api/media` 썸네일**: 하지 않는다(후속). 이미 `public, max-age=31536000, immutable`로 캐시되고, 업로드 10MB 제한이 있다. 크기별 변형은 (1) 요청마다 리사이즈하면 Range 응답·CPU 부담이, (2) 저장 변형은 모델·마이그레이션이, (3) 어느 쪽이든 앱이 `?w=`를 붙이도록 화면 코드 변경이 필요해 이 이슈 범위를 넘는다.

### 운영 실행 (사람이 함, 선택)
머지·배포 뒤 기존 공개 PNG를 줄이려면:
0. 시간·장소: 미리보기도 사진마다 R2에서 받아 풀고(최대 40MP, RGB 약 120MB) 줄여 보므로 **모든 단계를 트래픽이 적은 시간에** 한다. 가능하면 API 대신 worker 서비스(`server/railway-worker.json`)에서 실행하고, API에서 할 때는 Railway 메모리 그래프를 보며 한다.
1. 미리보기: `railway ssh --service farmclub-api -- .venv/bin/python -m app.source_analysis.recompress_photos` → 바꿀 사진(id·예전 키) 수와 전후 바이트 합계를 확인한다.
2. 백업: R2 사진 버킷을 복사해 둔다(예전 PNG는 되돌릴 수 없다).
3. 실행: 같은 명령 끝에 `--backup-done --commit`. 종료 코드가 1이면 출력의 '실패' 사진을 확인한다(그 사진은 그대로 둠).
4. 확인: 공개 상품 하나의 대표 사진 `curl -s -o /dev/null -D - https://farmclub-api-production.up.railway.app/api/source-media/<id>`(GET으로 헤더만; 이 서버는 HEAD에 405) → `content-type: image/jpeg`, `cache-control: private, max-age=300`.

### 후속
- `/api/media` 크기별 변형(썸네일): 위 결정 사항 참고. 농가·소식 사진이 무거우면 업로드 때 표시용 크기로 줄이는 쪽을 먼저 검토한다.
- `/api/source-media/{id}` 접근 검사는 요청마다 `catalog.product_detail` 전체를 만든다. 캐시로 반복 요청은 줄지만 첫 요청 비용은 그대로다. 느리면 참조 여부만 보는 가벼운 조회로 바꾸는 것을 후속으로 본다.
- 색 프로필(ICC): 분석용 PNG 단계부터 버린다(기존 동작). Display P3 사진은 조금 덜 선명해 보일 수 있다. 필요하면 sRGB로 변환하는 것을 후속으로 본다.
