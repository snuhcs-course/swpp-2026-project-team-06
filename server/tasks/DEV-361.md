## DEV-361 Server: product draft, one-step apply and admin change history (PR B)

- 이슈: [DEV-361](https://linear.app/sswp6/issue/DEV-361)
- 스펙: FEAT-04·05, R-18·R-21·R-25, `docs/spec/capacity-1.4.md`, `docs/spec/source-integration.md` DEV-361 절(이 PR에서 씀)

- 상태: PR B 구현(서버·`packages/api`·관리자 웹·스펙). 앱 화면 변경 없음.

### 왜
composer('상품 수정')가 상품의 유일한 편집기가 된다(PM 11/17). 구매자에게 보이는 상품의 모든 상품 칸·판매 조건 변경은 비공개로 두었다가 '상품에 반영' 한 번에 판매페이지와 함께 반영해야 하고, 승인 대기 상품의 변경은 다시 승인받지 않는 대신 운영자가 기록을 봐야 한다. PR C 화면이 쓸 서버 API를 먼저 만든다.

### PM 결정 (11/17)
1. 판매 중·승인 대기 상품: 상품명·원산지·보관·품종·당도·사진·옵션·받는 시기·환불 날짜·배송비·가격·기간·박스를 비공개 초안에 두고 '상품에 반영'(판매페이지와 한 번에) 때만 구매자에게 보인다.
2. 판매 전 상품은 지금처럼 바로 저장. 판매 종료 상품은 지금처럼 고칠 수 없다.
3. 반영은 기존 검증을 그대로 쓴다: R-18, R-21(받는 시기 변경 + 예약 → 동의·환불), R-25(가격 변경은 새 주문부터), PERIOD_LOCKED. 반영 응답·미리보기는 바로 보임 / 새 주문부터 / 예약자 동의 필요로 묶는다.
4. 승인 대기 상품의 변경은 다시 승인받지 않는다. 운영자만 보는 변경 기록을 남기고 관리자 웹 공급 물량 카드에 보인다.
5. 공급 물량 신청(운영자 승인)과 판매 설정(한도·한 주문 최대·중지)은 따로, 바로 적용.

### 결정 사항
- 초안 위치는 workspace(composer가 늘 여는 곳, 상품당 하나). 초안 버전은 workspace `version`.
- 충돌은 칸 단위 기준값으로 본다(product.version은 판매 설정·물량 신청으로 자주 오름). 같은 칸을 다시 저장해도 기준값은 그대로다(사이에 바뀐 것을 놓치지 않게). 생산자가 확인한 칸은 저장 본문 `rebase`로 지금 값을 새 기준값으로 삼는다(scan 1회차: 두 번 저장해야 풀리던 것을 바꿈, PR C 화면은 충돌 칸 확인 → rebase 저장). 지금 상품 값이 초안 값과 같으면 충돌이 아니다.
- 대표사진은 하나: page를 반영할 때 판매페이지 대표사진이 참조 사진(상품 페이지가 이미 쓰는 주소)이면 photos 초안 첫 장, photos 초안이 없으면 지금 대표사진과 같아야 한다(아니면 409 `PHOTO_CHANGED`, 전부 되돌림). 다른 곳(SCR-25·예전 앱)에서 바꾼 대표사진을 낡은 composer 대표사진이 덮지 않게 한다(scan 3회차). composer에서 새로 올린 대표사진은 반영 때 주소가 생기므로 photos 초안 순서 앞에 넣는다(scan 2회차). page 없이 반영하면 photos 초안 순서가 그대로 들어간다. PR C는 참조 사진으로 대표사진을 바꿀 때 photos 초안 첫 장도 같이 바꾸고, 409면 composer를 다시 연다.
- 반영 때 지금 값이 이미 초안 값과 같아진 칸은 변경으로 세지 않고, 남는 변경이 없으면 기록을 쓰지 않는다(`changeId` null).
- 판매 전 상품에 남은 초안의 칸이 직접 저장으로 바뀌었으면 `PRODUCT_CHANGED` 메시지가 '남은 수정을 버리고 상품에서 직접 고쳐 주세요'다.
- 초안 옵션 ID는 PATCH처럼 형식 제한 없이 받는다(1~64자). 예전 앱이 만든 ID도 다시 보낼 수 있게.
- 예전 판매페이지 반영 경로의 기록에 대표사진이 바뀌었으면 '사진' 줄도 넣는다.(바뀐 것이 없는 반영은 기록하지 않는다. 반영 전 값은 칼럼만 읽어 잠금 전 상품 행을 세션에 올리지 않는다)
- `load_my_product(lock=True)`는 `populate_existing`으로 잠근 뒤 상품을 다시 읽는다. `product_lock`이 잠금 전에 한 번 읽어 두면 그 사이 다른 요청이 커밋한 값을 놓쳤다(scan 5회차, 기존 코드의 경합).
- `deliveryWindowProposed`·기록의 받는 시기 제안은 동의를 물을 예약이 있을 때만 참이다.
- `product_lock`의 첫 읽기는 소유 확인 칼럼만 본다. 상품·옵션·기간은 잠근 뒤 처음 읽는다(scan 6회차: 하위 행이 잠금 전 값으로 남던 경합).
- apply-all의 page는 실제로 페이지(`module_detail`·`detail_content`)가 바뀐 때만 '판매페이지' 줄과 `page_changed`를 남긴다(`pageApplied`는 요청 기준).
- 중량 옵션은 '바로 보임'으로 묶는다. 기존 주문도 옵션 이름은 지금 값을 읽고(중량은 PERIOD_LOCKED), 추가·삭제는 새 주문에만 해당한다. PM 결정의 '새 주문부터'는 가격·박스·기간.
- 알려진 한계: 예전 판매페이지 반영 경로 기록의 '전' 값은 잠금 전에 읽는다(기록 정확도만 영향, 판단에는 쓰지 않음).
- 예전 판매페이지만 반영 경로(`…/product-workspaces/{pid}/apply`, `/batches/{bid}/drafts/{did}/apply`)도 판매 중·승인 대기 상품이면 '판매페이지' 한 줄을 기록한다(승인 대기 변경이 기록에서 빠지지 않게, scan 2회차).
- R-21 확인은 사람 수와 묶을 수 있다: `confirmedReservedCount`가 지금 수와 다르면 다시 409.
- 초안 칸 길이·개수 제한은 PATCH와 같게(없음) 둔다. 이미 제한을 넘는 상품의 다른 칸 저장이 막히지 않게.
- 초안 버전은 workspace version이라 composer를 다시 열면(open이 workspace version을 올릴 수 있음) PR C는 초안을 다시 읽는다.
- 심사 중에 담은 초안이 반려·철회로 판매 전 상품에 남으면 apply-all로 반영(직접 저장과 같음, REJECTED → DRAFT, 필수 칸 검사 없음)하거나 버릴 수 있다. 새로 저장하지는 못한다(판매 전은 직접 저장).
- 관리 정리(purge): 남는 상품의 변경 기록은 남기고, 지워지는 반영자는 다른 감사 행처럼 비운다(`_null_dangling`).
- `changesSinceRequest`는 신청부터 결정까지(심사 중이면 지금까지)만 센다. 관리자 웹 목록도 같은 기간으로 거른다.
- 저장 때는 모양만 검사(만드는 중인 초안 저장 허용), 규칙 검사는 반영 때. 반영 중 하나라도 실패하면 전부 되돌리고 초안을 남긴다.
- 초안 칸에서 뺀 것: `maxQuantityPerOrder`(판매 설정), `detailContent`(판매페이지는 batch 초안). 새 옵션도 `optionId`를 앱이 정한다(기간 가격이 가리키게).
- `maxDelayUntil`은 '새 주문부터'(주문에 저장되지 않고 결제 전 상품 화면에만 보임). 받는 시기는 예약자가 없으면 '새 주문부터', 있으면 '동의 필요'.
- 동의 인원 = 입금 대기·예약 완료·출하 준비 주문의 사람 수(기존 R-21 제안 대상과 같음).
- 판매 중 상품의 변경도 기록한다(승인 대기만이 아니라). 관리자 화면은 신청 카드에서 신청 뒤 기록 수만 센다.
- 승인 대기 상품의 직접 PATCH·PUT stages 거절은 그대로(예전 앱·e2e 호환). 직접 엔드포인트를 판매 중 상품에서 막을지는 PR C 뒤에 정한다.
- 자료 분석이 꺼진 서버(DEV-84)에서는 workspace API와 함께 이 API도 404. composer를 그 상태에서 열지는 PR C에서 정한다.
- 미리보기 `changes`에는 판매페이지·batch 대표사진 변경이 없다(앱이 batch 초안으로 안다). 반영 응답·기록에는 `page`와 실제 사진 변경이 들어간다.
- composer에서 직접 올린 대표사진(참조 사진이 아님)은 처음 반영할 때만 복사한다. 마지막으로 반영한 판매페이지 초안(`page_draft_id`)이 같은 사진·같은 판을 대표사진으로 썼으면 apply-all은 대표사진을 그대로 둔다(`publish.cover_applied`). 같은 사진이 반영할 때마다 하나씩 늘거나, 다른 곳에서 바꾼 대표사진을 낡은 composer 대표사진이 덮지 않게 한다(scan-before-merge 1회차).
- 알려진 한계: `cover_applied`는 마지막으로 반영한 판매페이지 초안 하나만 본다. (1) 예전 경로로 판매 중 상품의 판매페이지만 반영(대표사진은 그대로)한 뒤 같은 업로드 대표사진으로 apply-all을 하면 대표사진이 들어가지 않는다(판매 중 상품의 대표사진은 composer에서 잠겨 있어 자동 선택일 때만 생김). (2) 업로드 X → 참조 사진 Y → 다시 X로 반영하면 X가 한 번 더 복사된다. 둘 다 PR C 화면에서 대표사진을 상품 사진과 맞추는 흐름으로 다룬다(scan-before-merge 2회차 INFO, 고치려면 복사한 대표사진을 workspace에 따로 기록해야 함).
- 알려진 한계(PR C): 다른 곳에서 대표사진을 참조 사진으로 바꾸면 apply-all(page)은 409 `PHOTO_CHANGED`인데, composer를 다시 열어도 batch 대표사진은 상품의 지금 대표사진으로 다시 맞춰지지 않는다. PR C에서 composer를 열 때 맞추거나, 화면에서 상품의 지금 대표사진을 고르게 한다.
- `load_my_product(lock=True)`는 잠그기 전에 직접 flush한다(`populate_existing`이 flush 안 한 변경을 덮지 않게, 호출부 약속에 기대지 않음).
