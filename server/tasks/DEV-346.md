## DEV-346 Migrate legacy product pages into a composer draft on first composer open

- 이슈: [DEV-346](https://linear.app/sswp6/issue/DEV-346) · 앱 기록: `apps/producer/tasks/DEV-346.md`
- 스펙: `docs/spec/source-integration.md` 'DEV-346' 절 · FEAT-04 · AC-SRC-1/5/9/11

### 왜
- 11/17 PM: 모든 상품의 '판매페이지 수정'을 composer로 열고, composer 밖에서 만든 페이지(시드·직접 입력·composer 이전·기존 편집기)도 지금 내용 그대로 옮긴다. 반영해도 내용을 잃으면 안 된다.
- composer는 batch 초안만 보여 주고, 초안 반영(`publish.apply_draft`)은 상품 상세를 통째로 바꾼다. 초안 사진은 batch 사진 자료 id만 가리키고, 반영은 batch에 올린 사진의 정리본만 복사했다. 그래서 빈 batch로 열면 빈 페이지가 보이고, 반영하면 예전 상세가 사라졌다.

### 범위 (수정 허용 경로)

- `server/app/source_analysis/models.py`, `server/migrations/versions/0033_source_product_photo.py`(고위험 경로: 컬럼 세 개 추가 — `source_assets.product_photo`, `source_product_workspaces.page_source`·`page_draft_id`)
- `server/tests/test_source_page_migration.py`(새 파일)
- `server/app/source_analysis/spec.md`(오래 남을 구현 결정 표, AGENTS.md 작업 순서)

### 결정 사항
- **사진은 복사하지 않고 참조한다(선택지 b).** 복사(선택지 a)는 서버가 바이트를 가진 `/api/source-media/…`만 가능하고, 시드·UAT의 앱 사진 `/photos/*.jpg`와 https 주소는 서버가 받을 길이 없다(서버가 앱·외부 주소를 받아 오면 네트워크 의존·SSRF 문제). 참조는 모든 주소를 잃지 않고, 반영 결과 주소가 그대로라 공개 페이지가 같다.
- 참조 사진 = `source_assets` 행: `original_photo=True`, `status="PREPARED"`, `storage_key=""`, 쪽 없음, 새 컬럼 `product_photo={"uri","alt"}`(JSON, nullable, 마이그레이션 0033). batch의 다른 사진과 같은 행이라 대표사진 선택·사진 배치·첨부함·삭제·초안 검증(`patch_review`·`save_drafts`)이 그대로 동작한다. 다른 곳은 이렇게 갈랐다.
  - `start_run`: 아이템을 만들지 않는다(분석할 바이트 없음). run `inputs`에는 남겨 composer 편집 가능 판단(`canEditBatch`)이 그대로다. 참조 사진만 있으면 '자료를 먼저 넣어 주세요.'
  - `patch_asset`(상품 연결 바꾸기): 거절(다시 준비할 수 없음).
  - worker 삭제 정리: `storage_key`가 비면 저장소 삭제를 건너뜀.
  - `apply_draft`: 참조 사진은 `{uri, alt}` 그대로. `/api/source-media/`는 그 상품의 `PublicPhoto`일 때만(다른 상품 사진이면 409 `PHOTO_CHANGED`). 복사가 없어 다시 반영해도 사진이 쌓이지 않는다.
- 옮기기는 `POST /product-workspaces {productId, composer: true}`에서만 한다. `composer` 없는 호출(기존 편집기·예전 앱)은 지금과 똑같이 동작하고 응답에도 `composer`가 없다. 응답 `composer`:
  - batch에 이 상품 초안이 있으면 true(옮기지 않음, composer로 만든 상품 포함).
  - 페이지·대표사진·사진·설명이 하나도 없으면 true(옮길 것 없음).
  - 초안 없이 검토 값·분석 기록만 있는 batch면 false(composer가 페이지를 못 보여 주므로 건드리지 않음).
  - 그 밖은 옮기고 true. 옮길 수 없으면(칸 3,000자·사진 30장 초과) false.
- 옮기는 내용(원본은 `ProductWorkspace.snapshot` = 반영 안 한 기존 편집기 수정본이 있으면 그것, 없으면 지금 공개 페이지):
  - 모듈 페이지: 모듈의 항목 칸마다 문구(같은 칸 여러 문구는 빈 줄로 이음), 사진·일러스트는 hero 모듈이면 `hero` 칸, 아니면 모듈의 첫 칸. 켜짐(`enabled`)·숨긴 섹션 그대로.
  - 블록 페이지·설명만 있는 페이지: `summary` 한 칸 = 글 블록 '제목\n본문'을 빈 줄로 이음 + 사진 블록 모두. 블록이 없으면 설명.
  - 칸 값은 PRODUCER/CONFIRMED(생산자가 이미 공개한 값). 재분석이 덮지 않는다(AC-SRC-11).
  - 대표사진 = 스냅샷 `representativeUri`(= 상품 `photos[0]`). 기본 정보(품종·사이즈·예상 당도)는 batch를 만들 때 상품에서 이미 복사된다(`service.targets`).
  - 초안은 기존 `save_drafts(editor=True)`로 만들되 `migrated=True`면 금액·효능 검사를 건너뛴다(이미 공개된 문구를 잃지 않게. 다음 composer 저장 때 칸별 오류).
  - 반영 안 한 기존 편집기 수정본을 옮겼으면 `snapshot`을 공개본으로 되돌린다(composer 반영을 막는 `PAGE_DRAFT_EXISTS` 방지, 수정본은 초안에 있음).
- 멱등: 상품 advisory lock + batch 행 잠금 안에서 판단. 같은 상태로 다시 열면 아무것도 쓰지 않는다. 같은 요청의 멱등 키 재시도는 기존 `s.idempotent`.
- 11/17 사전 스캔 반영 — 다시 옮기기 규칙(CRITICAL 1). origin/main에서는 판매 중 상품의 '판매페이지 수정'이 기존 편집기였으므로, composer로 만들고 기존 편집기로 고쳐 반영한 상품은 batch 초안이 낡았다. 그래서 `source_product_workspaces.page_source`(마이그레이션 0033에 함께 추가)에 초안이 마지막으로 맞춘 이야기 지문(모듈 → 블록 → 설명 순 JSON의 sha256)을 옮길 때·composer 반영(`apply_draft`) 때 기록한다. 기존 편집기 반영은 기록하지 않아서 다음 composer 열기에서 차이가 보인다.
  - 반영 안 한 기존 편집기 수정본이 있으면 초안이 있어도 늘 그 수정본으로 다시 옮기고 비운다(`PAGE_DRAFT_EXISTS`로 갇히지 않음).
  - 초안이 있고 지문이 지금과 같으면 그대로. 지문이 있는데 다르면 지금 페이지로 다시 옮긴다(구매자에게 보이는/반영된 페이지가 이김. 그 뒤 composer에 저장만 한 수정은 이전 Draft 행에만 남음, 화면에서는 볼 수 없음).
  - 지문이 없는 예전 초안: 공개 이야기가 비었으면 그대로, 초안 글(previewModules)이 공개 모듈 글과 같으면 지문 기록 후 그대로, 다르면 DRAFT·REJECTED는 초안 유지(구매자에게 안 보임, composer에서 반영 뒤 계속 고친 경우가 흔함), 그 밖의 상태는 공개 페이지로 다시 옮김.
  - 다시 옮길 때 이 상품의 ReviewedField를 모두 지우고 페이지 값으로 다시 쓴다. 같은 주소의 참조 사진은 다시 쓴다(중복 행 없음). 올린 사진·분석 후보·이전 초안은 남는다.
  - 대표사진 순서만 바뀐 것은 지문에 넣지 않는다(이야기가 같으면 생산자의 비공개 수정을 지우지 않으려고). 그래서 SCR-25에서 대표사진만 바꾼 뒤 composer로 반영하면 composer의 대표사진이 앞으로 온다(알려진 한계).
- 11/17 기본 정보 맞추기(CRITICAL 2, 2차 스캔에서 고침): 판매 전(DRAFT·REJECTED)은 batch가 원본이라 열 때 건드리지 않는다(blur 저장·분석 예상 당도 채우기가 batch에 먼저 들어가고, 사이즈는 상품에 넣는 길이 없음 — 1차 수정은 이것들을 지웠다). 판매 중·승인 대기·종료는 대상 JSON의 `productBasicInfo`(지난번 맞출 때 상품 값)와 비교해, 비어 있지 않고 그 뒤 바뀐 상품 값만 기본 정보로 가져온다(SCR-25의 품종·당도 수정). 값이 실제로 바뀐 때만 손대지 않은 specification·qualityEvidence 제안을 지우고 버전을 올린다. `productBasicInfo`는 대상 이름 바꾸기(`patch_batch`)에서 사라질 수 있고, 그러면 다음 열기에서 비어 있지 않은 상품 값을 다시 가져온다.
