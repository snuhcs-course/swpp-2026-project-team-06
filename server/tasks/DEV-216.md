### 목표
`POST /api/orders`가 소비자가 본 기간·단가·옵션 중량과 지금 값을 비교해, 다르면 주문을 만들지 않고 409 `STAGE_CHANGED`(이전·지금 값)로 돌려준다.

### 범위 (수정 허용 경로)
- `server/app/orders/schemas.py`(`OrderInput` 선택 필드 3개), `server/app/orders/service.py`(`create_order` 비교·details, `request_deposit` STAGE_CHANGED details), `server/app/orders/spec.md`(결정 한 줄)
- `server/tests/test_orders.py`
- `server/spec.md`(오류 reason 목록 한 줄)

### 비범위 (건드리지 않음)
- `server/app/catalog/**`(`soldOut` 정의, 질문 3), 모델·마이그레이션(필드 추가 없음), 멱등 저장 방식(`run_idempotent`)

### 결정 사항
- 11/04 제안: `expected_stage_id`·`expected_unit_price`·`expected_unit_weight_grams`는 선택(None이면 지금 동작). 앱 배포 뒤 필수로 바꿀지는 PM 질문 ①.
- 11/04 제안: 검사 순서 판매 중지 → 지금 기간 없음 → 전체 물량 → 기간 물량 → 기대값 비교. 기존 4단계 뒤에 비교만 더한다.
- 11/04 제안: details `{reason, productId, optionId, previous:{stageId,unitPrice,unitWeightGrams}, current:{stageId,unitPrice,unitWeightGrams,startsAt,endsAt}|null, nextStageStartsAt}`. `request_deposit`도 같은 모양(previous = 주문 스냅샷).
- 11/04 멱등: 기대값은 본문 해시에 포함 → 같은 키·다른 기대값은 `IDEMPOTENCY_MISMATCH`, 409도 멱등 결과로 저장(10-08 결정 유지). 앱은 409 뒤 새 키.
- 11/04 PM 승인: 기대값은 이번에 선택(다음 이터레이션 필수), 동의 재체크 없음, catalog `soldOut`은 DEV-215(#410) 담당이라 안 건드림.
- 11/04 구현: details는 `_stage_changed(item, option, stage, previous, message)` 한 곳에서 만든다. 날짜는 ISO 문자열(멱등 결과 JSON 저장). `SOLD_OUT`에 `optionId`를 더했다(앱 ‘{옵션}은 … 다 팔렸어요’). `request_deposit`의 검사 순서는 그대로(details 모양만 맞춤). 멱등 해시는 Pydantic 본문 전체라 새 필드(None 포함)가 자동으로 들어간다 — 배포 직후 24시간 안에 예전 앱이 같은 키로 재전송하면 해시가 달라 `IDEMPOTENCY_MISMATCH`가 날 수 있으나 앱은 409 뒤 새 키로 보내므로 영향은 작다.
- 11/04 발견: 지금 `request_deposit` 비교는 방금 만든 주문과 지금 값을 비교해 두 요청 사이에 바뀔 때만 걸린다(I3-PRE-05).
