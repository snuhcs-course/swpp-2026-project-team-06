## DEV-228 자료에 있는 당도가 '예상 당도' 칸으로 옮겨지지 않음

- 이슈: [DEV-228](https://linear.app/sswp6/issue/DEV-228) · GitHub #424
- 브랜치: `nemodleo/dev-228-source-brix-prefill`
- 기능·인수 조건: FEAT-03 / AC-03-1, AC-03-5(새로 추가) · 규칙 M-11 · AC-SRC-3·11
- 제안서: 2026-11-05 DEV-228 제안서(레포 밖), PM 승인안 C
- 상태: 리뷰 중

### 목표
사전 점검 P7에서 자료에 "당도 11브릭스 정도"가 있는데도 새 상품 화면의 '당도 예상' 칸이 비었다. 원인은 정규식보다, 지금 '새 상품'(자료 분석) 흐름에 자료 속 당도를 기본 정보 칸으로 옮기는 길이 없다는 데 있다. 분석이 끝나면 서버가 규칙으로 칸을 미리 채우고, 당도 인식 정규식도 보강한다.

### 범위 (수정 허용 경로)
- `server/app/ai/grounding.py`(당도 인식 공용 함수 `brix_readings`·`single_brix`, 예전 초안 경로 `_supported_brix`가 같은 함수 사용)
- `server/app/source_analysis/service.py`(`refresh_runs` 완료 시점에 `prefill_expected_brix`)
- `server/tests/test_source_brix_prefill.py`(새 파일), `server/tests/test_ai_service.py`
- `server/app/ai/spec.md`, `server/app/source_analysis/spec.md`, `server/tasks/DEV-228.md`
- `docs/spec/functional/FEAT-03-ai-product-draft.md`, `docs/spec/source-editor.md`, `docs/wiki/Requirements-and-Specifications.md`
- `docs/design/proposals/DEV-228/before.png`, `after.png`

### 비범위 (건드리지 않음)
- DB 열·마이그레이션·`models.py`, 자료 분석 프롬프트·스키마(모델이 당도 칸을 내게 하는 B안)
- 앱·Mock 코드(서버 응답의 기본 정보에 값이 실려 기존 입력칸에 그대로 보인다), 새 화면 요소
- '올해/작년' 같은 문맥으로 값 고르기

### 결정 사항
- 11/05 (PM 승인) 방안 C. 분석이 끝났을 때(run이 SUCCEEDED·PARTIAL로 바뀔 때) 기본 정보의 예상 당도가 비어 있으면, 개인정보를 가린 자료 글(`Page.redacted_spans`, 글·OCR·PDF 조각)에서 당도 값이 하나로 정해질 때만 채운다. 모델을 부르지 않는다.
- 11/05 (PM 승인) 이미 값이 있으면 덮어쓰지 않는다. 값이 여러 개로 갈리면 비운다. 숫자 없는 "당도 높은"은 비운다.
- 11/05 (PM 승인) 범위("11~12브릭스")는 하한(11)을 넣는다. 예상 칸이라 낮게 잡는 쪽이 과장이 적다(M-11). 예전 초안 경로의 근거 확인은 범위 양끝을 모두 근거로 본다.
- 11/05 (PM 승인) 제안 표시 없이 미리 채운다. 생산자는 칸을 고칠 수 있고, 고친 값은 재분석에서 유지된다.
- 11/05 대상 자료: 그 상품에 지정한 자료 + 상품이 하나일 때의 공통 자료(`refinement.includes_target`과 같은 기준). 원본 상품사진(`originalPhoto`)은 OCR하지 않으므로 뺀다.
- 11/05 정규식: 단위가 앞인 "브릭스 11" 인정, 범위 양끝 인식, 날짜는 먼저 지우고, 년·월·일·%·상자 단위 숫자와 "5-10kg"처럼 범위로 읽히지 않은 앞 숫자는 제외. "12 brix 선별 3일"처럼 단위 뒤 숫자를 당도로 읽던 경우도 막는다(숫자 바로 뒤 brix/브릭스는 키워드로 쓰지 않음).
- 11/05 채운 뒤 batch `version`·`reviewVersion`을 올린다(`patch_basic_info`와 같은 방식). 앱은 분석이 끝나면 batch를 다시 읽으므로 앱 코드 변경은 없다.
- 11/05 같은 작업을 다시 분석하면, 생산자가 일부러 지운 빈 칸도 다시 채워질 수 있다(빈 칸과 "지움"을 구분할 열이 없음, DB 변경은 범위 밖). 리뷰 포인트로 남긴다.
