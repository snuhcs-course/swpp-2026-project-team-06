- 상태: 진행 중 — PM 결정(11/28) 반영. 이 PR(#875)은 나가는 순서 2·3(서버 outbox·발송 루프·솔라피 클라이언트·관리 API·스펙). 처리방침 문구(4)는 후속 PR

### 왜
11/27 생산자 QA: 주문이 들어와도 농가는 아무 알림을 받지 못한다. 농가가 앱을 열어 보기 전까지 주문을 모르고, 그사이 입금 기한(안내 + 24시간, R-28)이 흘러간다. 서버에는 알림 기반이 전혀 없다(알림톡·문자·푸시 코드 없음).

PM이 정한 방향: 채널은 카카오 알림톡, 알림톡이 실패하면 발송 업체의 대체 발송으로 문자. 앱 푸시는 새 네이티브 빌드가 필요해 범위 밖, 웹 푸시는 하지 않는다. 업체 후보는 솔라피(아직 가입 전).

### 지금 코드 (조사, 2026-11-27 `origin/main` f9bfd04c 기준)
**주문 흐름과 상태가 바뀌는 곳** (`server/app/orders/service.py`)
- 주문 생성 `create_order`(263행) → `PENDING_PAYMENT`. 물량을 잡지 않고 생산자 목록에도 아직 의미가 없다(주문서 동의 단계).
- 입금 안내 `request_deposit`(688행, 상태 변경 755행) → `AWAITING_DEPOSIT`. 여기서 물량을 잡고 입금자명(`deposit_code`)과 입금 기한(`deposit_due_at`)이 정해진다. 라우터 `POST /api/orders/{id}/deposit`(`router.py` 116행)이 `run_idempotent`로 감싸 한 번만 일어난다.
- 소비자 '입금을 마쳤어요' `report_deposit`(831행) → 상태는 그대로, `deposit_reported_at`만 기록. 라우터 129~134행이 바로 커밋. 이 값이 있으면 기한이 지나도 자동 취소되지 않는다(`_expire_if_overdue` 617행).
- 생산자 미승인 `reject_deposit`(845행): 입금 대기로 두면 `deposit_reported_at`을 지워 소비자가 다시 알릴 수 있다.
- 입금 확인 `confirm_deposit`(876행, 896행) → `PREPARING`(FEAT-09 정상 흐름 4번과 같음. `docs/spec/tech-design/README.md` 상태 표의 `RESERVED`는 옛 표기). `undo.record_action`(`undo.py` 253행)이 감싸고 실행 취소(DEV-455)로 입금 대기로 되돌아갈 수 있다.
- 취소: 소비자 `cancel_order`(494행) — 입금 전이면 환불 없이 `CANCELED`, 입금 뒤면 `_refund`(444행)로 `REFUNDED`가 되고 농가가 직접 송금해야 한다(`refund-settled`). 기한 만료 `expire_overdue_deposits`(660행)는 조회 때 지연 검사 + 운영자 일괄 API로만 돈다(스케줄러 없음).
- 출하 `ship_order`(1297행), 배송 완료(운영자) `mark_delivered`(533행), 구매 확정 `confirm_order`(523행).

**농가가 "새 주문"을 알아야 하는 순간은 `AWAITING_DEPOSIT`으로 바뀌는 때다.** 결제는 농가 계좌 무통장 입금이고, 농가가 통장과 입금자명을 대조해 확인해야 주문이 진행된다(FEAT-09 정상 흐름). `PENDING_PAYMENT`는 아직 주문서 단계라 알릴 대상이 아니다. 농가가 할 일이 실제로 생기는 두 번째 순간은 소비자가 '입금을 마쳤어요'를 누른 때다.

**농가가 지금 주문을 보는 방법**
- 현황 탭 할 일 '입금 확인할 주문' → `/ship?status=AWAITING_DEPOSIT`(`apps/producer/src/app/(tabs)/index.tsx` 220~222행).
- 탭 배지는 채팅 탭에만 있고(안 읽은 메시지 + AI 답변 확인 요청), 앱이 앞에 있을 때 8초마다 읽는다(`apps/producer/src/app/(tabs)/_layout.tsx` 62~125행). 주문 배지는 없다. 앱 밖으로 나가는 알림은 없다.

### 설계

**1. 1차에 보내는 알림 (추천: 두 가지)**

| 이벤트 | 일어나는 곳 | 받는 사람 | 보내는 이유 |
| --- | --- | --- | --- |
| `ORDER_AWAITING_DEPOSIT` 새 주문 | `request_deposit`에서 `AWAITING_DEPOSIT`로 바꾼 직후 | 그 상품 농가 | QA가 말한 "주문이 들어왔는데 모름". 입금 기한 24시간이 이때부터 간다 |
| `DEPOSIT_REPORTED` 입금했다고 알림 | `report_deposit`에서 `deposit_reported_at`을 처음 채운 때 | 그 상품 농가 | 농가가 통장을 보고 '입금 확인'을 눌러야 주문이 진행된다. 이 주문은 기한이 지나도 자동 취소되지 않아 농가가 놓치면 운영자가 전화해야 한다(AC-09-7) |

- 버튼 하나(웹 링크 WL) '주문 보기' → `https://farm.farmclub.kr/ship?status=AWAITING_DEPOSIT`. 버튼 이름에는 변수를 쓸 수 없다.
- 변수 값: `#{농가명}` 농가 이름, `#{상품명}` 상품 이름(옵션 무게 포함, 40자에서 자름), `#{수량}` "3박스", `#{입금자명}` `deposit_code`(없는 옛 주문은 주문 번호), `#{입금금액}` 천 단위 쉼표, `#{입금기한}` "11월 28일 오후 3시"(KST).
- 대체 문자는 같은 내용을 짧게 줄인 LMS(한글이 많아 SMS 90바이트를 넘음). 대체 문구는 솔라피 콘솔 템플릿 설정에서 정하고 승인 뒤에도 바꿀 수 있다.
- 템플릿은 승인 뒤 고칠 수 없어서 문구를 바꾸면 새 템플릿을 검수받고 코드(템플릿 ID 변수)를 바꾼다.

**4. 한 번만 보내기(멱등)**
- `notifications` 테이블의 `dedupe_key` UNIQUE: 새 주문은 `order_awaiting_deposit:{orderId}`, 입금 알림은 `deposit_reported:{orderId}:{deposit_reported_at ISO}`(미승인 뒤 다시 알리면 그건 새 알림).
- 넣을 때 savepoint + `ON CONFLICT DO NOTHING`. `run_idempotent` 재생은 `run()`을 다시 부르지 않아 두 번 생기지 않고, 실행 취소(DEV-455)로 입금 대기로 돌아가도 `request_deposit`을 거치지 않으며 키도 막는다.

**5. outbox와 재시도**
- 테이블(새 모델): `id`, `event`, `dedupe_key`(UNIQUE), `order_id`, `farm_id`, `template`, `variables`(JSON, 위 변수만 — 이름·주소·전화 없음), `status`(`PENDING`·`SENDING`·`SENT`·`FAILED`·`SKIPPED`), `skip_reason`, `attempts`, `next_attempt_at`, `lease_until`, `phone_last4`, `provider_group_id`, `provider_message_id`, `last_error`(업체 상태 코드·예외 종류만), `created_at`, `sent_at`.
- 알림 행은 주문 변경과 **같은 트랜잭션**에서 `PENDING`으로 넣는다. 주문이 롤백되면 알림도 없고, 주문이 커밋되면 알림 행이 반드시 있다. 외부 호출은 커밋 뒤에만 한다.
- 보내는 쪽: API 프로세스 안 발송 루프 하나(결정 4 추천). lifespan에서 데몬 스레드로 시작, 5초마다 `PENDING`·만료된 `SENDING`을 `FOR UPDATE SKIP LOCKED`로 몇 건 가져와 임대(60초) 뒤 커밋하고 보낸다(자료 분석 워커와 같은 방식, 여러 개가 떠도 안전).
- 보내기 직전에 주문을 다시 읽어 아직 해당 상태인지 본다(새 주문 알림인데 이미 취소·확인됐으면 `SKIPPED`, 늦게 가서 헷갈리지 않게). 만들어진 지 6시간이 지난 행도 `SKIPPED`.
- 재시도: 연결 오류·시간 초과·5xx·429만 1분 → 5분 → 30분, 3번 실패하면 `FAILED`. 4xx(번호·템플릿·변수 오류)는 바로 `FAILED`. 시간 초과는 업체가 받았을 수도 있어 다시 보내면 두 번 갈 수 있다 — 놓치는 것보다 낫다고 보고 재시도한다(결정 7).
- 알림톡이 카카오 쪽에서 실패하면(카카오톡 미사용 등) 업체가 대체 문자로 보낸다(`disableSms=false`, 발신번호 필요). 우리 재시도와 별개다.

**6. 주문과 떼어 놓기**
- 주문 API는 알림 행을 넣을 뿐 외부 호출을 기다리지 않는다. 업체 장애·키 없음·잘못된 템플릿이 주문을 실패시키거나 느리게 하지 않는다.
- 알림 행 넣기가 실패하면(예: 예상 못 한 DB 오류) savepoint만 되돌리고 경고 로그를 남긴 뒤 주문은 그대로 커밋한다. 알림을 못 남기는 것보다 주문이 깨지는 쪽이 더 나쁘다.

**7. 키가 없을 때와 테스트**
- `NOTIFY_PROVIDER` 기본 `none`: 보내지 않고 행을 `SKIPPED`(`provider_disabled`)로 남긴다. 로컬·CI·테스트·키 넣기 전 운영 모두 이 값이다. 그래서 업체 계정이 생기기 전에도 머지할 수 있다.
- `solapi`일 때만 키를 쓴다. `APP_ENV`가 local이 아니고 `solapi`인데 키·채널·발신번호·템플릿 중 하나라도 비면 서버가 뜨지 않는다(기존 `_source_settings` 검사와 같은 방식).
- **테스트는 절대 네트워크로 나가지 않는다.** `conftest.py`가 `NOTIFY_PROVIDER=none`을 고정하고, 솔라피 클라이언트는 `httpx` transport를 주입받아 테스트에서는 `httpx.MockTransport`만 쓴다. `api.solapi.com`으로 실제 연결을 열면 실패하는 고정 장치(autouse)를 둔다.

**8. 로그 가림**
- 로그·관리 응답에는 알림 id·주문 id·이벤트·상태·업체 상태 코드·끝 4자리만. 전체 번호, 변수 값(입금자명 포함), 요청 본문, API 키·서명 헤더는 남기지 않는다. `masking.py`에 `phone_tail(phone) -> "●●●●1234"`를 더한다.

**9. 남용·비용 막기**
- 농가당 1시간 30건(`NOTIFY_FARM_HOURLY_LIMIT`), 서버 전체 하루 1,000건(`NOTIFY_DAILY_LIMIT`). 넘으면 `SKIPPED`(`rate_limited`)로 남기고 경고 로그. 입금 안내는 물량을 잡아야 해서 이미 비싼 동작이지만, 주문하고 취소를 반복하는 사람을 막는 마지막 선이다.

**10. 받지 않기와 동의**
- 자기 농가 주문 안내는 계약 이행에 따른 정보성 안내라 따로 동의를 받지 않는다(마케팅 동의와 무관). 결정 5대로 농가 단위로 끌 수 있게 한다.

**11. 처리방침(위탁 고지)**
- `legalContent.ts` 처리방침 제1조 목적에 "생산자에게 주문·입금 알림 발송(카카오 알림톡, 실패 시 문자)", 생산자 신청 연락처의 이용 목적에 같은 내용, 제5조 위탁 표에 발송 업체(법인명은 계약 때 확인해 적음)와 알림톡 전달자(카카오), 제14조 변경 기록과 시행일 상수 하나. 솔라피는 국내 업체로 보여 제6조 국외 이전은 바뀌지 않을 것으로 보인다(계약 때 확인).
- 웹은 Vercel 배포로, 원스토어 앱은 `eas update --channel preview`로 나간다(DEV-436과 같은 길). 문구만 바뀌므로 네이티브 빌드는 필요 없다.

**12. 운영**
- 환경 변수(값은 사람이 Railway에만 넣는다): `NOTIFY_PROVIDER`, `SOLAPI_API_KEY`, `SOLAPI_API_SECRET`, `SOLAPI_PFID`, `SOLAPI_SENDER_NUMBER`, `SOLAPI_TEMPLATE_ORDER_AWAITING_DEPOSIT`, `SOLAPI_TEMPLATE_DEPOSIT_REPORTED`, `NOTIFY_FARM_HOURLY_LIMIT`, `NOTIFY_DAILY_LIMIT`.
- 관리 API: `GET /admin/notifications?orderId=&status=`(상태·시도 횟수·끝 4자리·업체 코드·시각), `POST /admin/notifications/{id}/retry`(`FAILED`만, `Idempotency-Key`, `run_manager_action` 감사).
- 운영 확인(사람): `ops_tester` 농가에 테스트 상품 하나 → 같은 사람이 `ops_tester` 소비자로 1개 주문 → 입금 안내 → 농가 폰에 알림톡이 오는지, 관리 API에 `SENT`와 업체 메시지 id가 있는지, 솔라피 콘솔 발송 내역과 맞는지 본다 → '입금을 마쳤어요' → 두 번째 알림 → 주문은 입금 전 취소로 정리. 운영 데이터에 남으므로 한 건만.

**13. 비용**
- 한 달 비용 ≈ (주문 수 × 1차 이벤트 수) × 알림톡 단가 + 그중 대체 문자 비율 × LMS 단가, 부가세 별도.
- 솔라피 공개 단가(VAT 별도, 2026-11-27 확인): 알림톡 13원, SMS 18원, LMS 45원. 예: 한 달 주문 300건 × 2 = 600건 × 13원 = 7,800원, 대체 10%면 60 × 45원 = 2,700원 → 약 10,500원 + VAT.

**14. 나가는 순서**
1. 이 이슈 파일(지금 PR) → PM 확인.
2. outbox·모델·마이그레이션·no-op 발송자·주문 훅·관리 API·테스트. `NOTIFY_PROVIDER=none`이라 업체 계정 없이 머지·배포 가능, 운영에서는 `SKIPPED` 행만 쌓인다(주문 흐름 확인용).
3. 솔라피 클라이언트(`MockTransport` 테스트만). 역시 키 없이 머지 가능.
4. 처리방침 문구 → 업체 계약 전에 법인명을 확인하고 시행일을 정한 뒤 머지.
5. 사람: 업체 준비가 끝나면 Railway 변수 → 위 "운영 확인" 한 건 → `NOTIFY_PROVIDER=solapi` 유지.

### 결정 사항
**정해진 것 (PM, 11/27)**
- 채널은 카카오 알림톡, 실패하면 업체 대체 발송으로 문자. 앱 푸시는 범위 밖(새 네이티브 빌드 필요), 웹 푸시는 하지 않는다. 업체 후보 솔라피.

**정해진 것 (PM, 11/28 "추천대로")** — 아래 1~9를 모두 추천안으로 확정했다. 다른 안의 비용은 판단 근거로 남겨 둔다.
1. 1차 이벤트 — 결정(추천): 새 주문 + 입금했다고 알림 두 가지. 새 주문만 하면 템플릿 하나·비용 절반이지만, 소비자가 알린 뒤 농가가 놓친 주문은 자동 취소도 안 돼 운영자가 전화해야 한다.
2. 입금 뒤 소비자 취소(농가가 환불 송금해야 함) 알림 — 결정(추천): 1차에서 빼고 2차. "환불 금액을 보내 주세요" 문구는 카카오의 송금 유도 템플릿(추가 소명자료 필요)으로 볼 수 있어 검수가 늦어질 수 있다. 넣으면 농가가 환불을 늦게 알아채는 일을 줄이지만, 검수가 막히면 1차 전체가 늦어질 수 있다(템플릿은 따로 검수되므로 나눠 낼 수는 있다).
3. 받는 번호 — 결정(추천): `Farm.contact_phone`(운영자가 가입 확인 전화로 쓰는 번호). 카카오 `User.phone`은 카카오톡 등록 번호라 알림톡 도달은 더 확실하지만 아이디 생산자에겐 없고 소비자에게 보이는 번호와 달라질 수 있다. 어느 쪽이든 농가가 승인 뒤 번호를 바꾸는 길이 없어서, 바꿔 달라는 요청은 당분간 운영자가 DB로 처리해야 한다(관리 API를 더하면 범위가 는다).
4. 보내는 곳 — 결정(추천): API 프로세스 안 발송 루프(새 서비스·비용 없음, 지금 API가 한 프로세스). 다른 안은 Railway 서비스 하나 더(자료 분석 워커처럼): 배포·감시할 것이 늘고 사용료가 든다. API 재시작 중 몇 초 늦어지는 것 말고는 행이 남아 있어 잃지 않는다.
5. 끄기 — 결정(추천): 1차는 농가 단위 끄기 칸을 서버에만 두고 운영자가 요청받아 끈다(앱 화면 없음). 앱에서 직접 끄게 하면 디자인 보드·승인·OTA까지 일이 는다.
6. 발송 결과 — 결정(추천): 1차는 업체 접수 결과(`SENT`=접수)만 기록하고 실제 도착은 솔라피 콘솔에서 본다. 웹훅은 공개 주소·서명 검사·저장이 더 들고, 요금표에 웹훅 부가 상품이 있어 유료일 수 있다(확인 못함).
7. 시간 초과 재시도 — 결정(추천): 재시도(드물게 두 번 갈 수 있음). 재시도하지 않으면 그 주문 알림을 놓칠 수 있다.
8. 처리방침 시행 — 결정(추천): DEV-436처럼 테스트 단계라 배포일 시행, 처리 근거가 계약 이행이라 동의 버전은 올리지 않음. 7일 사전 고지를 하면 알림을 켜는 날이 그만큼 늦어진다.
9. 한도 숫자 — 결정(추천): 농가당 시간 30건, 전체 하루 1,000건(지금 주문량보다 넉넉하고 실수로 반복 발송될 때 비용을 몇만 원 안으로 막음).

### 구현 중 결정 (11/28)
- `NOTIFY_PROVIDER=none`이면 넣을 때 바로 `SKIPPED`(`provider_disabled`)로 남기고 발송 루프를 시작하지 않는다. 운영자 재시도도 409 `NOTIFY_DISABLED`. 설계 7의 "보내지 않고 SKIPPED로 남긴다"를 넣는 쪽에서 한다 — 키 넣기 전 운영에 PENDING이 쌓이지 않고 테스트에서 백그라운드 스레드가 돌지 않는다.
- 재시도 횟수: 첫 시도 + 1분·5분·30분 뒤 세 번 = 최대 네 번, 그래도 안 되면 `FAILED`(설계 5 "3번 실패하면 FAILED"를 '다시 보내기 세 번'으로 읽었다).
- 설계 표에 없던 칸 `lease_token`(늦게 끝난 옛 루프가 결과를 덮어쓰지 않게), `retried_at`(운영자 재시도 뒤 6시간을 다시 센다)을 더했다.
- 한도는 보내기 직전에 센다(최근 1시간·KST 오늘의 `SENT`+`SENDING`). 두 프로세스가 동시에 세면 한두 건 넘을 수 있다.
- 받는 사람 번호는 숫자만 보내고, `SKIPPED`로 넣는 행에는 변수를 남기지 않는다.
- `notifications`의 주문·농가 FK는 `ON DELETE CASCADE`(시드 초기화·`purge_except`가 깨지지 않게). `purge_except` RULES에 두 표를 더했다.
- 솔라피 엔드포인트는 `send-many/detail` + `showMessageList: true`. 인증·발송·알림톡 형식은 공식 문서(solapi.com/developers/api/authentication-api-key, messages, messages-ata)와 공식 SDK 소스(solapi-nodejs·solapi-python·solactl)로 11/28 다시 확인했다. 인증 오류는 403이라 다시 보내지 않는다. 미확인 항목(접수 실패 코드 전체 목록, 버튼·대체 문구를 요청에 넣어야 하는지, 테스트 모드)은 `solapi.py` 머리 주석.
