## DEV-245 [I3][DEV-242 1/5] Define and persist an authorized paid-order conversation context

- 이슈: [DEV-245](https://linear.app/sswp6/issue/DEV-245)
- 브랜치: `minsunkim/dev-245-order-chat-restoration`

- 상태: 진행 중

### 목표
An order-detail conversation must work without following the farm. Today the only durable exception is an OrderInquiry row. Opening “농가에 물어보기” is not submission of a problem inquiry; creating a fake inquiry would change business state. A durable order connection is needed before the first message so reload, chat list, read markers, and private photos can use the same authorization.

### 작업
1. Document the two explicit start modes: general chat and owned paid-order chat.
2. Add a small thread–order context model and additive migration.
3. Add a read-only eligibility helper that validates each recorded connection against the current order owner, payment history, thread consumer, and farm.

### 완료 조건
- [ ] Contract specifies POST /api/messaging/chats {farmId, orderId?}. Omitted orderId keeps the existing general auto-follow behavior. A supplied valid orderId starts/reuses a conversation without adding a follow; response remains {farmId, autoFollowed}, with autoFollowed=false for order mode.
- [ ] New thread_order_contexts records have thread_id and order_id foreign keys, a composite unique/primary key (thread_id, order_id), and created_at. A thread can link several orders. Context is not stored as a fake message or OrderInquiry. New association foreign keys use child-row cleanup on parent deletion; verify compatibility with existing account/data cleanup so the table does not introduce shadow retention.
- [ ] Eligibility uses an owned order with paid_at != null and a product belonging to the same farm. A paid-then-refunded/canceled order retains payment history eligibility. Never infer permission from an arbitrary client flag or merely having any paid order at that farm.
- [ ] Define list/history/read/photo behavior for an empty recorded order conversation; generic sends while unfollowed still require an explicit valid orderId.
- [ ] Existing legitimate OrderInquiry conversations remain usable. Validate their order ownership/payment/farm when using the exception. No speculative backfill or creation of follows, messages, inquiries, or escalations.
- [ ] Migration upgrades a fresh local database and one at current head 0025, keeps existing data unchanged, and passes alembic check. Exercise downgrade/re-upgrade only on a disposable database; document that downgrade removes the new context records.
- [ ] Unit/model tests cover duplicate context prevention, several orders in one thread, invalid ownership/farm/unpaid links rejected by the helper, and existing inquiry compatibility.
