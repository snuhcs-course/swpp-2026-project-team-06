# pr-review — AI 1차 리뷰 + 사람 1명 승인

리뷰 흐름: **작성자가 AI 1차 리뷰 → must 해결 → draft 해제 → 사람 1명 Approve → 머지**.

## 1. AI 1차 리뷰 (작성자가 실행)
입력: PR 번호 또는 현재 브랜치. `tasks.md`, `gh pr view <번호>`, `git diff main...HEAD`.

아래 순서로 본다. 스타일보다 앞의 항목이 우선이다.
1. **spec 일치**: `tasks.md`의 작업·완료 조건 중 diff에 빠진 것, diff에 있는데 spec에 없는 것.
2. **범위 이탈**: "범위(수정 허용 경로)" 밖 파일 변경.
3. **정확성**: 버그, 경계값, 에러 처리 누락, 동시성, 잘못된 가정.
4. **테스트**: 변경을 검증하는 테스트가 있는지, 지우거나 약하게 만든 테스트는 없는지.
5. **보안·데이터**: 비밀값, 개인정보, 권한 검사 누락.
6. **유지보수**: 중복, 불필요한 복잡도, 이름. (사소하면 nit)

결과 형식 — 항목마다 한 줄, 근거가 되는 파일:줄 포함:
```
- [must] path/file.ts:42 — <문제> → <제안>
- [should] ...
- [nit] ...
```
- **must**: 머지 전 반드시 해결 (spec 누락, 범위 이탈, 버그, 보안)
- **should**: 가능하면 해결, 아니면 이유를 답글로
- **nit**: 선택

확신이 낮은 지적은 must로 올리지 말고 "확인 필요"로 표시한다. 문제가 없으면 "지적 없음"이라고 쓴다.
결과는 `gh pr comment <번호> --body-file <파일>`로 PR에 남긴다(제목: `AI 1차 리뷰 (<도구/모델>)`). must를 모두 해결한 뒤 `gh pr ready <번호>`.

## 2. 사람 리뷰 (리뷰어 1명)
- [ ] PR 본문과 `tasks.md`만 읽고 무엇을 왜 바꿨는지 이해되는가
- [ ] diff가 spec과 맞고 범위 밖 변경이 없는가
- [ ] AI 1차 리뷰의 must가 해결됐는가
- [ ] 직접 실행·테스트해 봤는가 (못 했으면 코멘트에 명시)
- [ ] 위험한 변경(데이터, 인증, 배포 설정)이 있으면 한 번 더 확인했는가

코멘트에도 must / should / nit 표기를 쓴다. must가 없으면 Approve, 있으면 Request changes.

## 3. 리뷰 반영 (작성자)
- 코멘트마다 수정 커밋(`fix(scope): 리뷰 반영 — <요약> (DEV-12)`)으로 해결하거나, 하지 않는 이유를 답글로 남긴다.
- 반영 중 생긴 결정은 `tasks.md`의 "결정 사항"에 적는다.
- 해결한 스레드는 리뷰어가 resolve한다.
- 반영 후 다시 리뷰를 요청한다.

## 4. 머지 직전
1. `git fetch && git merge origin/main`으로 branch를 최신화하고 충돌·테스트를 확인해 push한다.
2. `tasks.md`의 상태를 "완료"로, 완료 조건을 체크한다.
3. 사람 1명 Approve 확인 후 머지한다. 에이전트는 사람의 지시 없이 머지하지 않는다.
4. Linear 이슈 "결과"(산출물·시간·커밋·배운 점)를 채운다.
