# spec — 작업 폴더 `tasks.md` 작성·갱신

`tasks.md`는 이 작업의 기준(spec)이다. 코드보다 먼저 쓰고, 작업 내내 갱신한다.

## 입력
- Linear 이슈 키(예: `DEV-12`). 이슈 본문의 **왜 / 완료 조건**이 원천이다.
  - Linear MCP가 있으면 이슈를 직접 읽는다. 없으면 사용자에게 본문을 붙여 달라고 한다.
  - 이슈에 왜·완료 조건이 비어 있으면 tasks.md를 쓰기 전에 사용자에게 채워 달라고 한다(시작 전에 끝을 정한다).
- 작업 폴더: 이번 변경의 중심 폴더. 애매하면 사용자에게 묻는다.

## 절차
1. 작업 폴더에 `tasks.md`가 있는지 확인한다.
   - 다른 이슈의 진행 중 spec이면 멈추고 사용자에게 알린다(같은 폴더 동시 작업 금지).
   - 끝난 이전 작업의 spec이면 아래 템플릿으로 덮어쓴다.
2. 관련 코드·README를 읽고 **범위(수정 허용 경로)**를 최소한으로 정한다.
3. 아래 템플릿을 채운다. 각 섹션 1~5줄, 추측은 "결정 필요"로 표시한다.
4. 사용자 확인을 받은 뒤 `docs(scope): add DEV-12 spec` 형태로 첫 커밋·push한다.

## 갱신 규칙
- 작업 항목을 끝내면 체크한다.
- 계획에 없던 결정은 "결정 사항"에 날짜와 함께 적는다.
- 범위를 넓혀야 하면 코드를 고치기 전에 "범위"를 먼저 고치고 사용자에게 알린다.
- 세션을 마칠 때 "기록"에 다음 사람이 이어받을 수 있는 한 줄을 남긴다.

## 템플릿
```markdown
# tasks.md — DEV-12 <이슈 제목>

- 이슈: [DEV-12](https://linear.app/sswp6/issue/DEV-12)
- 브랜치: `<Linear에서 복사한 브랜치명>`
- 상태: 진행 중 | 리뷰 중 | 완료

## 목표
<이슈의 "왜"를 한두 줄로>

## 범위 (수정 허용 경로)
- `path/to/dir/**`

## 비범위 (건드리지 않음)
- <헷갈리기 쉬운 인접 영역>

## 결정 사항
- MM/DD <결정과 이유>

## 작업
- [ ] <검증 가능한 단위로>

## 완료 조건
- [ ] <이슈의 완료 조건>
- [ ] 테스트 통과
- [ ] 리뷰 1명 승인 후 main 머지

## 기록
- MM/DD <한 줄>
```
