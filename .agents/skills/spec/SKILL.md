# spec — 작업 폴더 `spec.md`·`tasks.md` 작성·갱신

작업 폴더의 스펙은 두 파일이다. 동작·규칙·인수 조건은 `docs/spec/`에 있고, 여기에 다시 쓰지 않는다.
- `spec.md`: 이 폴더의 구현 결정. 계속 유지한다.
- `tasks.md`: 이슈별 작업 기록. 이 이슈 섹션이 이 작업의 기준(spec)이다. 코드보다 먼저 쓰고, 작업 내내 갱신한다.

## 입력
- Linear 이슈 키(예: `DEV-12`, `SWPP-34`). 이슈 본문의 **왜 / 완료 조건**이 원천이다.
  - Linear MCP가 있으면 이슈를 직접 읽는다. 없으면 사용자에게 본문을 붙여 달라고 한다.
  - 이슈에 왜·완료 조건이 비어 있으면 tasks.md를 쓰기 전에 사용자에게 채워 달라고 한다(시작 전에 끝을 정한다).
- 작업 폴더: 이번 변경의 중심 폴더(기능을 구현하는 코드 폴더). 애매하면 사용자에게 묻는다.

## 절차
1. 이슈의 왜·완료 조건과 관련 FEAT·규칙(`docs/spec/`)을 읽는다. 읽는 순서는 `docs/spec/README.md`를 따른다.
   - 문서끼리 다르거나 스펙에 없으면 추측하지 말고 사용자에게 묻는다.
2. 작업 폴더에 `spec.md`가 없으면 `templates/spec.template.md`로 만든다.
3. `tasks.md`가 없으면 `templates/tasks.template.md`로 만들고, 있으면 맨 아래에 이 이슈 섹션을 추가한다. 이전 섹션은 지우지 않는다.
   - 다른 이슈 섹션이 진행 중이면 멈추고 사용자에게 알린다(같은 폴더 동시 작업 금지).
   - 관련 코드·README를 읽고 **범위(수정 허용 경로)**를 최소한으로 정한다.
   - 아래 템플릿을 채운다. 각 항목 1~5줄, 추측은 "결정 필요"로 표시한다.
   - 사용자 확인을 받은 뒤 `docs(scope): add DEV-12 spec` 형태로 첫 커밋·push한다.
4. 범위·결정이 바뀌면 이 이슈 섹션을 갱신한다(아래 갱신 규칙).
5. 머지 전 오래 남을 결정을 `spec.md` "구현 결정" 표로 옮긴다. 이 이슈 섹션은 그대로 둔다.

## 갱신 규칙
- 작업 항목을 끝내면 체크한다.
- 계획에 없던 결정은 "결정 사항"에 날짜와 함께 적는다. 오래 남을 구현 결정이면 머지 때 `spec.md`로 옮긴다.
- 범위를 넓혀야 하면 코드를 고치기 전에 "범위"를 먼저 고치고 사용자에게 알린다.
- 세션을 마칠 때 "기록"에 다음 사람이 이어받을 수 있는 한 줄을 남긴다.

## 템플릿 (`tasks.md` 이슈 섹션)
```markdown
## DEV-12 <이슈 제목>

- 이슈: [DEV-12](https://linear.app/sswp6/issue/DEV-12)
- 브랜치: `<Linear에서 복사한 브랜치명>`
- 기능·인수 조건: FEAT-xx / AC-xx-1, AC-xx-2
- 상태: 진행 중 | 리뷰 중 | 완료

### 목표
<이슈의 "왜"를 한두 줄로>

### 범위 (수정 허용 경로)
- `path/to/dir/**`

### 비범위 (건드리지 않음)
- <헷갈리기 쉬운 인접 영역>

### 결정 사항
- MM/DD <결정과 이유>

### 작업
- [ ] <검증 가능한 단위로>

### 완료 조건
- [ ] <이슈의 완료 조건>
- [ ] 테스트 통과
- [ ] 리뷰 1명 승인 후 main 머지

### 기록
- MM/DD <한 줄>
```
