## DEV-341 Make producer photo add and load fast with display-size previews instead of full PNG (producer app)

- 이슈: [DEV-341](https://linear.app/sswp6/issue/DEV-341) · 주 기록·측정 `server/tasks/DEV-341.md`
- 브랜치: `jangjinuite/dev-341-light-photos`
- 기능·인수 조건: FEAT-03/04 · AC-SRC-5/6/11
- 상태: 구현·로컬 검증 끝, 커밋 전(사람 리뷰 대기)
- 위험 등급: 일반

### 왜
- 새 상품 화면(대표사진·편집기·첨부 칸)이 같은 사진의 원본 PNG를 각자 받고, 시간 제한이 없으며, 편집기는 `Promise.all`이라 한 장이 실패하면 사진이 모두 비었다.
- 판매페이지 작업 공간은 원본 사진(최대 20MB)을 그대로 올리고 한 장씩 처리했다. 진행 표시는 '수정본 저장' 버튼에 돌았고, `row`가 바뀔 때마다(저장 응답 등) 사진을 전부 다시 받았으며, 한 장 실패가 전체를 오류로 만들었다.

- 새 상품 화면의 원본 사진 업로드 크기 — 분석·공개 반영이 무손실 원본을 쓰므로 줄이지 않는다
- 앱(iOS·Android)의 업로드 축소 — picker가 quality 0.8로 압축한다. 새 의존성(expo-image-manipulator)을 넣지 않는다
- Figma — 새 문구는 진행·실패 안내뿐이라 아래 후속에 적는다

### 결정 사항
- 11/17 사진 받기는 `privatePhotoBlob` 한 곳: 로그인 토큰 + 주소가 같으면 진행 중·받은 Blob을 함께 쓴다(최대 60개, 오래 안 쓴 것부터 지움). 실패하면 기억하지 않는다. 진행이 30초 동안 멈추면 끊는다(idle 시간 제한: 응답을 조각으로 읽고 조각마다 시계를 다시 맞춤, 느려도 계속 받는 큰 사진은 끝까지 받음). 조각 읽기를 못 하는 환경(React Native fetch)은 전체 120초 제한이고, 끊기면 '시간이 너무 오래 걸려요'. 화면은 각자 blob URL을 만들어 자기가 해제한다(공유 URL을 다른 화면이 해제해 깨지는 일 없음).
- 11/17 새 상품 화면: 대표사진·편집기는 `variant=display`, 첨부 칸은 `variant=thumb`, 주소에 자료 `revision.sanitizationVersion`. 대표사진과 편집기는 같은 요청을 공유한다.
- 11/17 실패는 사진마다: 편집기·판매페이지 모두 실패한 사진 수와 사진별 '사진 (n) 다시 불러오기' 버튼을 보이고, 누르면 그 사진만 다시 받는다. 다른 사진은 그대로 보인다. 편집기에서 업로드는 됐는데 미리보기만 실패하면 사진은 넣고 실패 칸에 둔다.
- 11/17 판매페이지 작업 공간 업로드: 웹은 긴 변 1600px 넘는 사진을 JPEG(0.9)로 줄여 보내고, 투명이 있을 수 있는 형식(PNG·WebP 등)은 작아도 흰 바탕 JPEG로 바꾼다(미리보기가 서버의 RGB 사본과 같게)(`pick.ts readImage`와 같은 `<img>`→canvas 방식, 브라우저가 EXIF 방향 적용). 읽지 못하는 형식(Chrome의 HEIC)은 원본을 보내 서버가 변환한다. 2장씩 동시에 올리고 순서는 고른 순서를 지킨다. 줄인 사진을 바로 화면에 보여 다시 받지 않는다. 실패한 장은 건너뛰고 '사진 n장을 올리지 못했어요'.
- 11/17 진행 표시: '새 사진 추가'/'사진 추가' 버튼 글자가 '사진 올리는 중 1/2'(스피너는 글자를 가려 글자로 보임). 하단 '수정본 저장'·'상품에 반영'은 사진 올리는 동안 스피너를 돌리지 않는다(누를 수 없는 것은 그대로).
- 11/17 판매페이지 사진 받기는 보여 줄 사진 주소 목록(저장본·반영본·지금 고치는 내용)이 바뀔 때만, 아직 없는 사진만 받는다. 글 수정·저장 응답으로는 다시 받지 않는다.
- 11/17 대표사진 바꾸기: `setRepresentative` 응답의 batch 버전을 바로 써서 batch 다시 읽기 1회를 없앤다(그 밖의 순서는 DEV-329 그대로).

- 11/17 PM이 남은 화면 3건을 아래 기본안으로 진행하라고 함(최종 리뷰에서 확인):
  - 새 상품 화면 편집기의 사진 실패 안내·'사진 다시 불러오기' 버튼은 둘레 내용과 같은 좌우 여백(`tokens.space.gutter` 16px)을 준다(새 상품 화면의 `emptyHint`일 때만. 판매페이지 작업실(`SourceWorkspace`)은 이미 여백 안에 있음).
  - 판매페이지에서 올린 직후에는 앱이 줄인 사진을 그대로 보인다(서버 사본을 다시 받지 않음). **알려진 한계**: 색 정보(ICC 프로필)가 든 사진은 올린 직후 화면이 서버 사본(ICC 없음)보다 조금 진하게 보이고, 다시 열면 서버 사본 색으로 보인다.
  - `BuyerPreview`(판매·가격 화면의 구매자 화면)도 사진을 한 장씩 받는다. 한 장이 실패해도 나머지는 보이고, 실패한 사진은 기존 기본 자리로 남는다(다시 불러오기 버튼은 두지 않음).

### 머지 순서·충돌 정책 (DEV-346과)
- DEV-346(`farmclub-page-editor`, 진행 중)이 `apps/producer/src/lib/sourcePhoto.ts`를 새로 만들어 `sourcePageImage(batch.id, source.id, 1)`을 부르고, `NewProductComposer`·`SourceAttachments`·`SourceDetailsEditor`의 사진 받는 줄과 worker cleanup 반복문을 같이 고친다.
- 순서: **DEV-341을 먼저 머지**하고, DEV-346이 main을 받아(rebase/merge) `sourcePhotoUrl`(또는 그 자리)에서 `sourcePageImage(..., { variant: "display" | "thumb", source })`로 미리보기 인자를 넘긴다. 대표사진·편집기는 `display`, 첨부 칸은 `thumb`.
- `sourcePageImage`의 미리보기 인자는 **필수**다(원본 PNG를 화면에서 받는 길 없음). 충돌을 DEV-346 쪽으로 풀어 인자를 빠뜨리면 `npm run typecheck`가 실패하므로, 16~30MB PNG로 조용히 돌아가지 않는다. 충돌 때는 인자를 지우지 말고 넘긴다.
- worker cleanup: 두 쪽 변경을 합칠 때 `variant_keys(key)`로 미리보기 키를 지우는 줄과 `used`에 미리보기 키를 넣는 줄을 남긴다(빠지면 미리보기가 매일 지워졌다 다시 만들어지고, 지운 자료의 미리보기는 고아 정리 때까지 남음).
- 반대로 DEV-346이 먼저 머지되면, DEV-341이 main을 받으면서 `sourcePhoto.ts`의 호출에 미리보기 인자를 넣는다(같은 규칙).
