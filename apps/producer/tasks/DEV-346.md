### 왜
- 새 상품 화면(composer, `NewProductComposer`)은 초안을 상품에 묶인 자료 작업(batch)에 저장하고, `ProductWorkspace.snapshot`에는 저장하지 않는다. 그런데 상품 카드 '판매페이지 수정'·SCR-25·딥 링크 `/products/:id/detail`은 예전 편집기(`ProductPageEditor`)를 열었다. 그래서 composer로 만든 작성 중 상품을 다시 열면 빈 페이지가 나왔다(같은 composer 주소를 새로고침해야만 보임).
- 판매 중이 아닌 상품 카드 썸네일(반영한 `/api/source-media/…`)이 404였다(공개 주소는 판매 중 상품만).

### 결정 사항
- 11/16 PM: 새 상품과 판매페이지 수정은 같은 화면. '판매페이지 수정'은 작성 중·반려·판매 중 모든 상태에서 composer를 연다. 판매 중 상품은 저장 → '상품에 반영'의 명시적 반영 단계를 유지(반영 전 구매자 화면 그대로).
- 11/16 구현 결정(프로토타입 리뷰 후 11/17 PM 확인): composer는 원래 임시 저장·나가기 때 상품 PATCH(상품명·원산지·보관·품종·당도)를 바로 보냈다. 판매 중 상품이면 구매자 화면이 즉시 바뀌므로, 판매 전(DRAFT·REJECTED)이 아닌 상품은
  - 상품명·원산지·보관 칸을 잠그고 SCR-25에서 고친다(칸 아래 '상품명·원산지·보관은 상품 편집에서 바꿔요').
  - 품종·당도는 비공개 기본 정보에만 저장하고, '반영하고 다음으로'를 누른 뒤 상품에 넣는다. 이미 반영한 초안이어도 넣지 않은 품종·당도가 있으면 다시 확인한다.
  - AI가 상품명·보관을 미리 채우지 않는다. 주 버튼 이름은 '상품에 반영'.
- 11/17 PM: '이어서 채우기'는 쓰지 않는다. 카드·SCR-25 버튼은 모든 상태 '판매페이지 수정'.
- 11/17 PM: composer 밖에서 만든 예전 상품도 composer로 연다('그냥 옮겨라'). 옮기기는 서버가 한다(`server/tasks/DEV-346.md`). 앱은 `productWorkspace.open(id, key, false, undefined, true)`(=`composer: true`) 응답의 `composer`가 true일 때만 composer로 가고, false(옮기지 못한 페이지)·값 없음(예전 서버)·자료 분석 꺼짐·Mock은 기존 편집기. 앱이 직접 판단하던 프로토타입 규칙(초안 있음·빈 페이지)은 서버 판단으로 바꿨다.
- 옮긴 사진은 바이트가 없어 `sourcePhotoUrl`이 주소를 고른다: `/api/source-media/…`는 생산자 인증 주소(`productWorkspace.photo`), 그 밖의 `/api/…`는 API 주소, `/photos/…`·https는 그대로. 올린 사진은 지금처럼 `sourcePageImage`. DEV-341(사진 가볍게, 다른 브랜치)과 겹치지 않게 호출 줄만 바꿨다.
- 11/17 사전 스캔 반영: 서버가 기존 편집기로 반영된 페이지를 다시 옮기고 기본 정보를 상품 값으로 맞춘다(`server/tasks/DEV-346.md`). 앱은 구매자에게 보이는 상품이면 반영 때 이 화면에서 고친 품종·당도만 넣고(`varietyEdited`·`brixEdited`), 측정 당도는 생산자가 측정 당도 칸에 적었을 때만 넣는다(예상 당도를 측정값으로 옮기면 가짜 실측 기록이 생겼다). `composer`를 모르는 예전 서버가 400(`fields.composer`)으로 거절하면 기존 편집기로 연다.
- 11/17 2차 스캔: 미리보기의 측정 당도는 생산자가 당도 칸을 고쳤을 때만 입력값, 아니면 상품 측정값. e2e `page-editor-unified`는 끝나면 p-house·p-cheonhye를 시드 상태로 되돌린다.
- 11/17 3차 스캔:
  - 구매자에게 보이는 상품에서 반영 때 넣을 품종·예상 당도는 서버 상태로 정한다: batch `basicInfo`가 서버가 기록한 `productBasicInfo`와 다른 칸 = composer에서 고친 칸(`composerEdits`). 그래서 고침 → 임시 저장 → 나갔다 다시 열기 → 반영해도 구매자에게 간다(전에는 화면 안 ref라 다시 열면 빠졌다). 재확인 판단도 같은 함수. 측정 당도는 이번 화면에서 측정 당도 칸을 고쳤을 때만(다시 연 뒤에는 예상 당도만 넣는다, 예상→측정 옮김 없음).
  - 구매자에게 보이는 상품은 `productPatch`가 품종·당도만 만든다(상품명·원산지·보관·옵션 안 보냄). 반영 뒤 최신 버전으로 저장하므로 화면의 옛 값이 SCR-25·판매 설정 수정을 되돌리던 것을 막는다.

- 11/17 5차 스캔: 구매자에게 보이는 상품에서 composer가 고친 당도(이번 화면 입력 또는 서버 상태로 안 고침)는 상품에 측정값이 있으면 측정 당도에도 같은 값을 넣는다(이 칸 이름이 '측정 당도'이고 구매자·SCR-25는 측정값을 먼저 보임, DEV-287 두 칸 맞추기와 같은 규칙). AI가 채운 예상 당도만으로는 측정값을 만들지 않는다. `displayBrix`는 그대로(반영 뒤 두 값이 같아 같은 값을 보임). e2e: 당도 고침 → 임시 저장 → 다시 열기 → 반영 → 공개 측정·예상 당도 바뀜.

- **11/17 PM 결정(동기화 걷어냄)**: 구매자에게 보이는 상품(판매 중·승인 대기·판매 종료)은 composer에서 상품명·원산지·보관·품종·당도·대표사진을 모두 잠그고 상품의 지금 값을 보인다(당도는 측정값 먼저). 이 칸들은 상품 편집(SCR-25)에서만 고친다. 이유: composer와 상품이 서로 다른 값을 들고 맞추는 동기화(`productBasicInfo`·`productCover`·`composerEdits`·`writesMeasuredBrix`, 반영 뒤 상품 PATCH)가 스캔마다 새 버그를 만들었다.

  - 반영은 상세만 바꾼다: 상품 PATCH 없음, 대표사진·사진 순서 그대로(서버 `apply_draft`도 판매 전 상품만 composer 대표사진을 적용). 확인 문구 '판매 중인 상품이라 상세페이지가 구매자에게 바로 보여요. 가격·재고와 대표사진은 바뀌지 않아요.'

  - 지운 것: `basicInfoEdits.ts`(`composerEdits`·`writesMeasuredBrix`·`basicInfoLocked`)와 `scripts/test-composer-basic-edits.mjs`, `productPatch`, 반영 뒤 `saveProduct`, 재확인 조건의 품종·당도 비교, `varietyEdited`, 승인 대기·판매 종료 전용 잠금 문구, `SourceTarget.productBasicInfo` 타입, 그 기능을 보던 e2e 2개(품종·당도 다시 열고 반영). 새 e2e: 판매 중 상품의 잠긴 칸·대표사진 시트 → 상품 편집으로 가기.
