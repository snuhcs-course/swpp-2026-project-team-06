### 결정 사항
- 11/24 원인: 홈 카드는 먼저 `/api/home` 목록 값('30,000원')을 그리고, `productPrices`가 상품 상세를 읽어 `priceFrom`을 채우면 '30,000원~'(+취소선 36,000원)으로 바뀐다(DEV-348). 시드 p-house는 10kg도 살 수 있어 다 채운 뒤에는 늘 '~'가 붙는다. 테스트는 `getByText("30,000원", { exact: true })`로 '~' 없는 값을 기다려서, 상세를 읽는 수십 ms 동안 Playwright가 확인하면 통과하고 놓치면 10초 내내 실패했다. 샤드·앞선 spec·시각과는 관계가 없었다(DB 상태 공유·고정 시계 아님).
- 11/24 근거(머지 큐 45382950015 트레이스, ms): '발견' 탭 클릭 뒤 확인 시작 131591 → `/api/home` 응답 약 131612 → 상세 3건 응답 끝 약 131665 → Playwright 다음 확인 약 131700. '~' 없는 30,000원은 약 50ms만 보였다. 실패 화면 접근성 트리는 "30,000원~ 36,000원".
- 11/24 화면을 고치지 않고 테스트가 다 채운 값('29,000원~'·'30,000원~')을 기다린다. 같은 카드를 보는 `conversation-ui.spec.ts`도 이미 '29,000원~'을 본다.

### 따로 볼 것
- 홈 카드 가격 깜빡임: '발견'으로 돌아올 때마다 카드가 이전 '29,000원~' → '30,000원'(취소선·'~' 없음) → '30,000원~'으로 약 50ms 바뀐다. `useAsync`(`packages/ui`)가 deps가 바뀌면 data를 null로 비워 `products.data ?? home.data.recommended`가 목록 값으로 떨어지기 때문이다. 가격 자체는 맞게 바뀐다. 고치면 화면 동작이 바뀌므로 이 이슈에서는 다루지 않는다.
- '~'는 첫 옵션 말고도 지금 살 수 있는 옵션이 있을 때만 붙는다. 이 테스트와 `conversation-ui.spec.ts`는 p-house 1단계 10kg(20개 중 6개 예약)이 남아 있다는 전제에 기댄다. 같은 샤드의 앞선 spec이 10kg을 다 팔게 되면 '~'가 빠져 다시 실패한다.
