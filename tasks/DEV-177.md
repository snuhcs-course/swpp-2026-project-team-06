### 판정: 간헐 실패(테스트 쪽 경쟁·외부 CDN). DEV-229·225·232 회귀 아님
- 1차 trace(아티팩트 13388205839): 끊긴 자원은 앱 API가 아니라 `https://cdn.jsdelivr.net/npm/pretendard@1.3.9/.../pretendardvariable-dynamic-subset.min.css`. 30,016ms 뒤 `net::ERR_TIMED_OUT`, 그동안 API 요청은 전부 200·수십 ms. 두 앱 `public/index.html`이 받는 외부 글꼴이라 세 PR과 무관하다. `X-Server-Time`은 응답 헤더라 preflight도 새로 생기지 않는다.
- 2차 trace: 전송 POST는 `04:22:49.861`에 시작해 42ms 걸렸는데, 운영자 `GET /admin/support`는 `49.876`(POST 응답 전)에 나갔다. 클릭 뒤 `getByText(question).last()` 검사가 4ms 만에 통과했기 때문이다.
  - 원인: react-native-web 여러 줄 입력은 `<textarea>`이고 React가 값을 textContent로도 넣어, `getByText(입력한 글).last()`가 말풍선이 아니라 DOM 마지막인 입력창에 바로 걸린다. 확인용 probe에서 전송 직후 이 locator가 `TEXTAREA` 1개에 걸렸다. DEV-192가 소비자 쪽 `consumer-support.spec.ts`에서 고친 것과 같은 원인이고, 생산자 쪽 쌍둥이 테스트는 그때 빠졌다.
  - 서버가 POST를 GET보다 먼저 끝내느냐에 달린 경쟁이라, 머지와 상관없이 오래전부터 있던 문제다.
- CI 느림만으로는 설명되지 않는다: 1차 15.1분 / 2차 12.1분 차이 중 30초는 CDN 대기. 실패 원인은 위 두 가지다.

### 반복 결과 (로컬, CI와 같은 `run-integration` env, 반복마다 시드 리셋, workers 1)
- 시드를 바꾸는 테스트라 `--repeat-each`는 2회차부터 상태 때문에 실패한다(안 읽음 1). 그래서 반복마다 `seed --reset` 뒤 스펙을 돌렸다.
- `c28d325` farmclub-support 10/10 통과, `6ea1dd0` 10/10 통과(로컬은 POST가 빨라 경쟁에서 진 적 없음). producer-and-privacy `c28d325` `--repeat-each 10` 30/30 통과.
- 전송 POST를 200ms 늦추면 고치기 전 테스트는 `c28d325`·`6ea1dd0` **둘 다 1/1 실패**(CI 2차와 같은 메시지) → 회귀가 아니라 테스트 순서 문제. bisect는 필요 없었다.
- CDN을 `abort("timedout")`로 끊으면 고치기 전 하네스는 CI 1차와 같은 `net::ERR_TIMED_OUT`로 실패한다.
- 고친 뒤: 두 스펙 10회(시드 리셋) 10/10 통과. 전송 POST 1.5초 지연에서도 farmclub-support 통과. probe로 CDN을 `timedout`으로 끊으면 `monitor`가 통과하고, 앱 사진(`/photos/farmer.jpg`)을 끊으면 그대로 실패하는 것도 확인했다.

### 결정 사항
- 11/05 farmclub-support: DEV-192와 같은 방식으로 전송 뒤 입력창이 비워질 때까지(`toHaveValue("")`, ChatThread는 전송 성공 뒤에만 비운다) 기다린 다음 말풍선·문의함을 본다. 검사는 줄이지 않았다.
- 11/05 외부 글꼴 CDN: `monitor()`가 콘솔 오류 중 "Failed to load resource"이면서 그 자원 주소(`message.location().url`)가 `https://cdn.jsdelivr.net/npm/pretendard@`인 것만 뺀다. 앱 자원·API·스크립트 오류는 그대로 실패다. 글꼴은 제품 동작이 아니라 외부 서비스 가용성이라 검사 대상에서 뺐다.
- 11/05 처음에는 픽스처에서 `context.route`로 CDN 응답을 캐시·대체했다. 그런데 라우트가 하나라도 있으면 Playwright가 모든 요청을 Node에서 판정하고, `source-analysis.spec.ts` 등이 `execFileSync`로 워커를 돌리는 동안 Node가 멈춰 화면의 분석 시작 POST가 워커 실행 뒤로 밀렸다. 그 결과 `AC-SRC-1/2/7/8` 3개가 로컬 전체 실행에서 실패(라우트 없이 같은 스펙은 통과)해 이 방식은 버렸다. 글꼴 파일을 저장소에 넣는 안은 용량 때문에 쓰지 않았다.
- 후속 질문(이번에 고치지 않음): CDN이 끊기면 렌더 차단 스타일시트라 페이지가 최대 30초 늦게 뜬다. 이번 1차 실패에서도 다른 검사는 통과했다. 운영 화면에도 같은 의존이 있으니 글꼴을 앱이 직접 서빙할지는 따로 정한다.
- 후속 질문: `source-analysis.spec.ts`는 '자료 준비·분석 시작' 클릭 뒤 분석 시작 POST를 기다리지 않고 바로 워커를 돌린다(이미 비활성인 버튼의 `toBeDisabled`는 즉시 통과). 지금은 워커 기동 시간이 POST보다 길어 통과하는 순서 의존이라 따로 고치는 게 좋다.
