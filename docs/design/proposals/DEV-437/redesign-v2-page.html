사람이 하는 일

이슈 파일 범위, AI 1차 리뷰, spec-check는 모두 에이전트가 쓴 이슈 파일을 기준으로 삼는다. 이슈 파일이 틀리면 셋이 같이 놓친다. 그래서 아래는 사람이 직접 하고, 사람 리뷰는 diff와 함께 이슈 파일도 읽는다.

  • 범위 확인(3단계). 이슈 파일의 수정 허용 경로를 첫 커밋 전에 본다. 범위 밖 변경을 기계가 막지는 않는다.
  • 사람 리뷰(7단계). 다른 팀원의 GitHub Approve, 또는 작성자가 diff를 직접 읽고 PR 본문 사람이 한 일:에 적은 것. 에이전트는 사람이 실제로 한 것만 그 줄에 적는다.
  • 머지 지시(8단계). 에이전트는 사람의 지시 없이 머지하지 않는다. 고위험 PR은 사람 리뷰가 없으면 지시가 있어도 머지하지 않는다.
  • 배포 확인(8단계). 배포 로그의 첫 줄 Comparing, 마지막 줄 Deploying/Skipping, 그리고 curl로 운영 응답을 본다. Actions 목록의 커밋 라벨은 믿지 않는다.

AI 사용 기록

Linear 결과와 PR 본문에 Agent 시간 / Tokens / Human 시간을 0.5시간 단위로 적는다. 실행 기록이 없으면 시각으로 어림해 약을 붙이고, Tokens는 도구가 준 값이 없으면 비워 둔다. Human 시간은 자기 보고다. 이 기록으로 결과물의 품질은 알 수 없다(SWPP-130).

이름 규칙

브랜치 이름, 커밋 메시지, PR 제목에 이슈 키를 넣으면 PR이 Linear 이슈에 붙는다. 나머지는 영어로 쓴다. Linear의 "Copy git branch name"은 한글 제목을 브랜치에 넣어 링크 인코딩과 셸 따옴표가 깨져서 쓰지 않는다(SWPP-119).

브랜치<github 아이디>/<이슈 키 소문자>-<영어 요약 2~5단어>예: nemodleo/dev-434-split-withdraw-kept-line
커밋type(scope): 요약 (DEV-12)type은 feat fix docs refactor test chore 중 하나. 예: feat(ui): split withdraw sheet kept line by role (DEV-434)
PR 제목[DEV-12] <English summary>예: [DEV-434] Split the withdraw sheet kept line for consumers and producers. squash 커밋 제목이 된다

PR을 연 뒤에는 브랜치 이름을 바꾸지 않는다. 바꾸면 GitHub가 PR을 닫는다. main 직접 push와 force push는 main ruleset이 막는다(2026-11-23 GitHub 설정 확인).

PR 체크와 머지

main ruleset의 필수 체크는 ci-ok figma-line checker-tests다. CI는 바뀐 경로에 따라 job을 건너뛰기 때문에, job마다 필수로 걸면 건너뛴 job이 머지를 막는다. 그래서 마지막 job ci-ok 하나로 모은다. 건너뛴 job은 통과, 실패·취소는 실패로 센다(DEV-234, CI.md CI 길).

체크보는 것
ci-ok그 길에서 고른 server·apps·admin-web·integration과 guide(이 페이지 대조). 문서만 바꾼 PR은 server·apps·integration을 건너뛴다.
figma-line화면 코드가 바뀐 PR 본문에 Figma: 줄이 하나 있는지. 머지 큐에서는 건너뛴다.
checker-testsspec-check 도구 자체의 계약 테스트(모델·키 없이).
spec-code-review필수 아님. 결과는 PASS, NO_FINDINGS, MISMATCH, INCOMPLETE, SKIPPED 중 하나이고, NO_FINDINGS와 SKIPPED는 PASS가 아니다.

spec-check는 모델이 판단하므로 틀릴 수 있다. 그래서 결과로 머지를 막지 않는다. fail이면 작성자가 처리 결정(고침·스펙 변경·오탐·사람 리뷰 대체)을 PR 코멘트로 남기고, 리뷰어는 그 코멘트 전에는 Approve하지 않는다. ready PR의 push·본문 수정·draft 해제 때 돈다(DEV-196, spec-check 1.1, 3). 표 형식은 push 전에 python3 .agents/skills/pr-context/check_table.py <본문 파일>로 확인한다(PR 템플릿).

머지 큐와 배포

낡은 main 위에서만 통과한 PR이 들어오면 main이 깨진다. 머지 큐는 앞에 줄 선 PR까지 합친 커밋을 검사하고, 통과한 그 커밋으로 main을 옮긴다. main push의 CI는 같은 커밋이 큐에서 통과했으면 validated 길로 다시 돌지 않는다.

배포는 이동 태그 뒤로 바뀐 대상만 올린다. server/**는 Railway, 앱은 Vercel, scripts/admin-web/는 Vercel 관리자 페이지다. 태그보다 오래된 커밋은 건너뛰어, 늦게 돈 실행이 운영을 되돌리지 않는다(DEV-139). 배포 확인은 사람이 하는 일에 적은 대로 로그와 curl로 한다.

main CI가 깨지면 머지한 사람이 바로 고치거나 revert한다. 깨진 동안 다른 사람의 배포가 멈춘다. PR 쌓기는 DEV-126(CI·spec-check 트리거 수정) 전까지는 쌓지 않는다(원문). 그런데 DEV-126은 취소됐다. 알려진 한계 참고.

화면을 바꿀 때

DEV-74(PR #158)가 생산자 로그인 화면을 바꿨지만 Figma는 옛 화면으로 남았다. 그 뒤로 화면 모양이나 문구가 바뀌는 일은 제안 보드, 승인, 개발 순서로 하고, 같은 PR에서 Figma v6를 고치거나 후속 이슈를 적는다. 바뀐 화면의 대표 상태는 전후로 찍어 PR과 Linear에 붙인다.

PR 본문 Figma: 줄언제
Figma: 반영함 — <링크 또는 node-id>같은 PR에서 Figma v6를 고쳤을 때
Figma: 해당 없음 — <이유>화면 모양·문구가 그대로일 때
Figma: 후속 — DEV-xx다음 이슈에서 고칠 때

figma-line은 줄의 형식만 본다. Figma가 코드와 같은지는 사람이 본다. docs/design/의 HTML 화면은 I1 기록이다.

무엇을 만드나, 어떻게 만드나

docs/spec/은 동작·규칙·인수 조건의 원본이다. prd.md, functional/FEAT-xx-*.md, rules.md, ia.md 순서로 읽는다. 문서끼리 다르면 추측해 구현하지 않고 질문한다.

코드 폴더의 spec.md는 구현 결정, tasks/<이슈 키>.md는 이슈 하나의 기록이다. 테스트 이름에 AC ID를 넣는다(test_AC_09_1_...). 이슈마다 파일을 따로 두는 이유는 ADR 0014.

읽는 순서, 문서끼리 다를 때, AGENTS.md 파일 구조, ADR, 로컬 실행 README Local run

AGENTS.md와 개인 규칙

규칙 원본은 AGENTS.md 하나다. Codex는 바로 읽고, Claude Code는 CLAUDE.md의 @AGENTS.md로 읽는다. 개인 규칙은 덧붙이기만 하고, 충돌하면 공용 규칙이 이긴다. 레포에 AGENTS.override.md는 만들지 않는다.

공용 스킬은 spec(이슈 파일), pr-context(draft PR과 본문), pr-review(AI 1차 리뷰) 셋이다. 원본은 .agents/skills/.

cp .agents/examples/claude-settings.local.example.json .claude/settings.local.json
cp .agents/examples/codex-AGENTS.example.md ~/.codex/AGENTS.md

자동화

언제 도는지만 적는다. 안의 동작은 .github/CI.md와 워크플로 머리 주석이 원본이다.

  • ci.yml: PR push, 머지 큐, main push
  • ci-full.yml: 매일 03:00 KST, hotfix 머지 뒤, 수동
  • spec-check.yml: PR 열기·push·본문 수정·ready, 머지 큐
  • deploy-railway.yml, deploy-vercel.yml: main push의 CI가 성공한 뒤
  • wiki-sync.yml: main에서 docs/wiki/**가 바뀔 때
  • GitHub Pages(설정): main push마다 docs/를 올린다. 이 페이지도 여기로 나간다

회의록과 위키

원본은 docs/wiki/이고 main 머지 때 위키를 덮어쓴다. 위키 화면에서 고친 내용은 사라진다. 회의록은 docs/wiki/meetings/_template.md를 YYYY-MM-DD-영문-요약.md로 복사해 영어로 쓴다. TA가 보므로 개인정보·법인·세무는 쓰지 않는다.

docs/wiki/README.md, wiki-sync.yml

자주 막히는 것

  • 머지 버튼이 안 눌린다: 빨간 필수 체크의 로그를 본다. 눌려도 사람 리뷰는 따로다.
  • PR이 Linear에 안 붙는다: 브랜치·커밋 메시지·PR 제목의 이슈 키.
  • spec-check가 INCOMPLETE다: check_table.py로 표 형식부터.
  • 배포가 건너뛰어졌다: 배포 로그 첫 줄. 이동 태그 뒤 경로가 안 바뀌었거나 main CI가 실패했다.
  • 마이그레이션 head가 둘이다: main 병합 후 alembic heads. 뒤에 머지하는 쪽이 번호를 올린다.
  • guide 체크가 빨갛다: 로그의 키·줄·실제값·기대값을 보고 아래대로 고친다.
  • 커밋이 Insights에 안 잡힌다: git config user.email이 GitHub 계정 이메일과 같은지.
  • 1시간 넘게 막혔다: PM에게 알린다.

이 페이지를 고칠 때

CI guide job(check-guide.mjs)이 매번 두 가지를 대조한다. 표시한 값 11개 키(branch commit pr-title checks high-risk steps skills ai-log spec-check test-urls stacking)를 AGENTS.md 해당 절에서 뽑은 값과, 저장소 링크를 그 파일·제목과 맞춰 본다. PR과 머지 큐에서는 어긋나면 막고, main push에서는 경고만 한다.

기본 판인 영어판도 같은 규칙으로 검사하고, 두 판의 절 id·단계 id·페이지 안 링크·저장소 링크·값이 다르면 CI가 막는다. 두 판을 같은 PR에서 같이 고친다.

설명 문장, CSS로 숨긴 요소, 저장소 밖 링크의 내용은 보지 않는다. 규칙을 바꾸는 PR의 작성자와 리뷰어가 관련 절을 같이 고친다.
