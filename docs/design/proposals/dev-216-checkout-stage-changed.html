주문서를 보는 동안 가격이 바뀌면, 바뀐 금액을 보여 주고 한 번 더 묻는다

주문서에 29,000원이 떠 있는 동안 농가가 가격을 30,000원으로 바꾸면, 지금은 예약하기 한 번에 30,000원 주문이 생기고 입금 안내로 넘어간다(I3-PRE-05 FAIL). 판매 중지 409를 받으면 금액은 그대로인데 버튼이 ‘바뀐 금액으로 예약하기’로 켜진 채 남는다(I3-PRE-03 관찰). 서버가 소비자가 본 기간·가격·중량을 받아 비교하고, 앱은 409 종류마다 다른 안내와 다음 행동 하나를 보인다. 왼쪽은 main 코드 그대로 다시 그린 화면, 오른쪽은 제안이다.

기준: Figma v6(보기 권한만) · docs/design/README.md 토큰 · main 87792b7 근거: I3-PRE-05.md, I3-PRE-03.md (PR #406, baseline i3-b2-87792b7) 코드: apps/consumer/src/app/checkout/[productId]/index.tsx · server/app/orders/service.py create_order·request_deposit 화면 속 이름·주소·가격·날짜는 모두 예시 데이터
BEFORE · 지금 요청 순서
  1. 주문서가 상품을 읽음: 5kg 29,000원
  2. 농가가 PUT /api/products/p-house/stages로 30,000원
  3. 예약하기 → POST /api/orders: 본문에 본 가격이 없어 서버가 지금 가격 30,000원으로 주문 생성, 200
  4. POST …/deposit: 방금 만든 주문(30,000)과 지금 가격(30,000)을 비교하니 같음, 200
  5. 입금 안내 ‘입금할 금액 30,000원’. 바뀌었다는 말이 없다
AFTER · 제안 요청 순서
  1. 주문서가 상품을 읽음: 5kg 29,000원, 기간 st-house-1, 5,000g
  2. 농가가 30,000원으로 바꿈
  3. 예약하기 → POST /api/orders 본문에 expectedStageId·expectedUnitPrice·expectedUnitWeightGrams → 서버 비교, 다름 → 409 STAGE_CHANGED(이전·지금 값), 주문 없음
  4. 주문서가 안내·합계를 30,000원으로 다시 그리고 버튼 ‘바뀐 금액으로 예약하기’
  5. 누르면 새 멱등 키 + 새 기대값으로 다시 보내 200 → 입금 안내 30,000원

디자인 무브

  1. 1

    서버는 ‘소비자가 본 값’과 비교한다

    주문 생성 본문에 본 기간 ID·단가·옵션 중량을 싣는다. 다르면 주문을 만들지 않고 409 STAGE_CHANGED와 이전·지금 값을 돌려준다. R-17·capacity-1.4 3장 “기간·가격·옵션 중량이 달라졌으면 재확인”을 주문 생성 시점까지 당긴다. 상품 version은 소개 글만 고쳐도 올라가서 쓰지 않는다.

  2. 2

    바뀐 값은 화면 맨 위와 금액 줄 두 곳에서만

    위 안내에 ‘29,000원 → 30,000원’을, 금액 섹션에는 상품 금액·합계를 새 값으로 다시 계산해 이전 합계를 취소선으로 한 줄 남긴다. 하단 바 합계도 새 값. 받는 곳·동의는 그대로라 다시 보여 주지 않는다.

  3. 3

    ‘바뀐 금액으로 예약하기’는 STAGE_CHANGED에서만

    지금은 409면 무엇이든 그 버튼이 된다. 버튼 문구를 응답의 details.reason에 묶는다. 가격·기간·중량이 실제로 바뀌고 지금 예약할 수 있을 때만 이 문구가 나온다.

  4. 4

    409 종류마다 다음 행동은 하나

    판매 중지는 잠깐 쉬는 것이라 버튼을 끄고 안내 안에 ‘다시 확인하기’. 기간 종료·전체 소진은 ‘상품으로 돌아가기’. 한 옵션만 품절이면 ‘옵션 바꾸기’. 같은 409를 다시 받는 버튼을 켜 두지 않는다.

  5. 5

    입력은 언제나 그대로

    받는 사람·주소·배송 메모·동의 5개·수량은 어떤 409에서도 지우지 않는다. 동의는 가격이 아니라 예약 조건에 대한 것이라 다시 체크하게 하지 않는다(PM 확인 질문 2).

  6. 6

    검사 순서는 ‘못 사는 이유’ 먼저, 가격은 마지막

    서버는 판매 중지 → 지금 기간 없음 → 전체 물량 → 기간 물량 → 본 값 비교 순으로 본다. 그래서 ‘바뀐 금액으로 예약하기’를 눌렀는데 곧바로 품절이 뜨는 일이 없다. 409도 멱등 결과로 저장되므로 앱은 409 뒤 키를 새로 만든다(지금도 그렇게 한다).

  "expectedStageId": "st-house-1",      // 주문서가 본 지금 기간
  "expectedUnitPrice": 29000,           // 그 기간·옵션 단가
  "expectedUnitWeightGrams": 5000       // 옵션 중량
}
  • 세 값 모두 선택 필드(None 허용)로 시작한다. 보내면 비교, 안 보내면 지금처럼 동작(배포된 오래된 PWA·네이티브 빌드 보호). 앱은 항상 보낸다. 필수로 바꿀 시점은 질문 1.
  • Mock assertSale는 이미 같은 이름의 expected(stageId·unitPrice·unitWeightGrams)를 받는다(입금 안내 단계). 주문 생성에서도 본문 값을 넘긴다.

409 STAGE_CHANGED details

{ "code": "CONFLICT", "message": "예약 기간 또는 가격이 바뀌었어요.",
  "details": {
    "reason": "STAGE_CHANGED", "productId": "p-house", "optionId": "opt-5",
    "previous": { "stageId": "st-house-1", "unitPrice": 29000, "unitWeightGrams": 5000 },
    "current":  { "stageId": "st-house-1", "unitPrice": 30000, "unitWeightGrams": 5000,
                  "startsAt": "2026-10-01", "endsAt": "2026-10-14" },
    "nextStageStartsAt": null } }
  • 지금 기간이 없으면 current: null, nextStageStartsAt에 다음 기간 시작일(없으면 null).
  • 입금 안내의 STAGE_CHANGED도 같은 모양(previous = 주문 스냅샷).
  • 검사 순서: 판매 중지 → 지금 기간 없음 → 전체 물량 → 기간 물량 → 본 값 비교(무브 6). 지금 순서에 비교 한 단계를 맨 뒤에 더한다.

멱등 키와의 관계

  • 기대값은 본문 해시에 들어간다. 같은 키 + 같은 본문은 첫 결과(409 포함)를 그대로, 같은 키 + 다른 기대값은 409 IDEMPOTENCY_MISMATCH(server/app/orders/spec.md 10-08 결정 그대로).
  • 그래서 앱은 409를 받으면 주문·입금 키를 둘 다 새로 만든다(지금 코드 유지). 네트워크 오류 재시도는 같은 키·같은 본문이라 첫 결과가 온다.
  • 성공 재전송은 그사이 가격이 또 바뀌어도 첫 주문을 돌려준다(contracts 1장 그대로). 재확인은 새 키에서만 일어난다.
  • 입금 안내 단계에서 409가 나면 결제 전 주문(PENDING_PAYMENT) 1건이 남는다. 물량을 잡지 않아 영향은 없고 지금도 같다(질문 4).

PM 확인 질문

  1. 기대값 필드를 언제 필수로? 제안: 이번에는 선택(없으면 지금 동작), 앱 배포가 끝난 다음 이터레이션에 필수로. 바로 필수로 하면 캐시된 오래된 PWA가 400을 받는다.
  2. 가격이 바뀌면 동의 5개를 다시 받나? 제안: 안 받는다. 동의는 받는 시기·환불·취소 조건에 대한 것이고 가격 재확인은 버튼이 한다.
  3. 서버 상품 응답 soldOut을 Mock처럼 판매 중지·전체 소진까지 포함하게 맞출까? 제안: 이번에는 앱이 availability를 쓰고, catalog 정의 변경은 별도 이슈(상품 카드·목록 영향이 넓다).
  4. 입금 안내 단계 409로 남는 결제 전 주문을 이번에 정리할까? 제안: 범위 밖(물량을 잡지 않고 지금도 같음).
  5. 입금 기한이 지나 주문서로 돌아온 경우(SCR-11 → changed=1)도 지금은 ‘예약 기간 또는 가격이 바뀌었어요’와 ‘바뀐 금액으로 예약하기’가 뜬다. 같은 화면이라 이번에 ‘입금 기한이 지나 예약이 취소됐어요 · 같은 내용으로 다시 예약할 수 있어요’ / 버튼 ‘다시 예약하기’로 고칠까? 제안: 고친다(앱만, 서버 변경 없음).
  6. 스펙 표기: 작업 지시의 ‘E2 판매 중지·품절’은 FEAT-08에서 E1(단계 변경·품절)이고, E2는 중복 요청(멱등)이다. 판매 중지는 FEAT-08에 없고 contracts-1.2 필수 시나리오에만 있어 AC-08-9로 FEAT-08에 올리자는 제안. I3-PRE-05가 인용한 AC-08-6은 수량 상한 AC라 재확인 AC를 새로(AC-08-8) 만든다.
