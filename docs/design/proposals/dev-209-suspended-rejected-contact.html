디자인 무브

  1. 1

    새 연락처를 박지 않고, 있는 대화방을 연다

    운영자가 실제로 답하는 곳은 관리자 문의함 하나입니다(FEAT-34, DEV-111). 정지·반려 생산자도 자기 farmclub 대화방만 /support에서 열 수 있게 합니다. 화면에 연락처 값이 없으니 레포에 사업자 정보를 쓸 일이 없고, 문의 기록도 문의함 한 곳에 남습니다(H9 오류 회복, H10 도움말).

  2. 2

    강조 버튼은 그 화면의 다음 행동 하나

    정지 화면에서 할 수 있는 일은 문의뿐이므로 '운영팀에 문의하기'가 주 버튼입니다. 반려 화면은 '다시 신청하기'가 주 버튼으로 남고, 문의는 로그아웃 옆 굵은 글자 버튼입니다. "강조색은 화면당 주요 버튼 하나, 화면 아래" 규칙을 지킵니다.

  3. 3

    두 상태 화면의 순서를 맞춘다

    상태 화면 머리 규칙(뒤로 없이 큰 제목)은 그대로 둡니다. 순서는 메타 → 큰 제목 → 결과 한 줄 → 사유 상자 → 도움 문장 → 하단 버튼으로 같게 맞춥니다. 정지 사유도 반려와 같은 면색 상자와 오류색 라벨에 넣어, 한 번 본 모양으로 읽히게 합니다.

  4. 4

    자리표시자 대신 버튼을 가리키는 문장

    "[운영팀 연락처]로 문의해 주세요"를 지우고, 무엇을 물을 수 있는지(사유가 다르면, 궁금하면)와 정지 중에도 방이 열려 있다는 사실을 적습니다. 문장이 아래 버튼과 같은 말('운영팀에 문의')을 씁니다.

  5. 5

    메일은 보조, 값이 있을 때만

    대화방이 기본이고 메일은 보조 수단입니다. 값은 이미 있는 빌드 변수 EXPO_PUBLIC_BUSINESS_EMAIL(packages/ui/src/legalContent.ts의 business.email, 사이트 하단 사업자 정보와 같은 값)에서 오고, 비어 있으면 줄을 그리지 않습니다. 새 서버 설정은 만들지 않습니다.

  6. 6

    평가용 반려 예시는 사람이 읽는 문장 하나로

    시드의 반려 예시는 박순자 한 명이고 사유도 문장입니다. 오미숙은 시드상 '확인 중' 계정(FEAT-01 사전 조건의 5가지 상태 중 하나)이므로, 시드는 그대로 두고 운영 DB의 "테스트" 반려를 확인 중으로 되돌립니다(사람이 실행). 반려 화면 문구도 "아래 사유를 고쳐서"로 바꿔 사유 상자를 먼저 읽게 합니다.

연락 수단과 값이 오는 곳

  • 대화방(기본): 값이 필요 없습니다. 서버의 farmclub 방(thread-support-{farmId}, 상대 u-farmclub)을 씁니다. 운영자는 관리자 페이지 문의함(/inbox)에서 지금처럼 답합니다. 문의함은 이미 정지·숨김 농가의 방도 보여 줍니다(FEAT-34 정해 둔 것).
  • 메일(보조): 생산자 앱 빌드 변수 EXPO_PUBLIC_BUSINESS_EMAIL을 씁니다(Vercel 생산자 프로젝트, 사이트 하단 사업자 정보와 같은 값). 레포에는 변수 이름만 둡니다. 값 등록·확인은 사람이 합니다.
  • 서버가 바꿀 것: 지금 생산자 채팅 API는 APPROVED만 받습니다(require_approved_producer, messaging/service.py). 정지·반려 생산자가 자기 farmclub 방만 읽고 보내고 읽음 처리하는 좁은 API 3개를 messaging 라우터에 더합니다. 다른 1:1·소식방은 계속 막습니다. 반려 농가는 방이 없으니 처음 열 때 만듭니다(AC-34-1 변경).
  • 앱 관문: lib/session 관문에서 /support를 정지(SUSPENDED)·반려(REJECTED) 상태에 허용합니다. 확인 중(PENDING)은 운영팀이 전화하므로 이번 범위가 아닙니다.
  • 연락처 가림: 이 방에도 M-16 자동 가림이 그대로 적용됩니다.

시드와 운영 데이터

  • server/app/core/seed.py: 오미숙(u-misook/f-wimi)은 PENDING, 반려 사유 없음이고 바꾸지 않습니다. 박순자(f-reject)의 반려 사유가 평가용 반려 예시입니다. 테스트(test_admin.py·test_support.py)도 f-wimi가 PENDING이라고 가정합니다.
  • 운영 DB의 "테스트"는 관리자 페이지에서 손으로 반려한 값입니다. 운영은 시드를 다시 넣지 않으므로(server/README.md) 시드를 고쳐도 사라지지 않습니다.
  • 사람이 할 일(운영 DB): f-wimi를 approval_status='PENDING', reject_reason=NULL, decided_at=NULL로 되돌립니다. 실행 명령과 확인 쿼리는 개발 PR의 server/tasks.md에 적어 둡니다.
  • 후속 후보: 관리자 반려 사유에 최소 글자 수(예: 10자)를 두어 같은 일이 다시 생기지 않게 합니다. 이번 범위에는 넣지 않고 질문으로 남깁니다.
