DEV-231 · HE-06(사전 점검 P1 심각도 4, P12) · 스펙 결정 B · 디자인 제안 (PM 승인 대기)

수확을 시작하면, 그 기간의 예약 주문이 출하 준비로 넘어간다

지금은 입금을 승인한 주문이 '예약' 탭에 들어간 뒤 아무 데도 갈 수 없다. 줄에는 '예약 완료' 글자뿐이고, '출하 준비' 탭에는 시드 주문만 있어 평가자가 만든 주문으로는 출하·송장 과제를 끝낼 수 없었다(FQ-06·AC-17-3이 수확 시작 UI를 일부러 뺐다). PM 결정 B는 "수확 시작 = 출하 준비 시작"이다. 예약 기간 카드에 결과를 말하는 버튼 하나를 두고, 현황과 예약 탭에서는 그 버튼으로 데려간다. 서버에는 이미 있던 수확 시작 API를 기간 단위로 좁혀 다시 쓴다. 왼쪽은 main 코드 그대로 다시 그린 화면, 오른쪽은 제안이다. 이름·금액·건수는 모두 예시다.

디자인 무브

  1. 1

    버튼은 예약 기간 카드 안, 저장 폼과 선으로 나눈다

    주문은 기간(단계)에 묶여 있으니(Order.stage_id) 기간 카드 맨 아래에 '수확' 칸을 둔다. 위 가격·물량 칸과 굵은 선으로 갈라 '저장'과 다른 일임을 보인다. 강조색은 하단 '예약 기간 저장' 하나로 두고 이 버튼은 테두리 버튼이다.

  2. 2

    버튼 글자가 결과를 말한다

    「수확 시작 · 출하 준비 3건」. 무엇을 누르는지(수확 시작)와 무엇이 바뀌는지(3건이 출하 준비로)를 한 줄에. 위 줄에 '예약 완료 3건 · 입금 대기 1건'을 두어 3에 들어가지 않는 주문도 보인다.

  3. 3

    확인 시트에 옮겨질 주문과 소비자 쪽 변화를 적는다

    입금 승인·출하 확인과 같은 시트, '아니요' 1 : '수확 시작 · 3건' 2. 주문 줄(최대 3줄 + '외 n건'), 소비자 주문 상세가 '수확·포장 중'이 된다는 것, 보내기 전까지 소비자는 취소할 수 있다는 것, 되돌릴 수 없다는 것을 적는다.

  4. 4

    찾아오는 길은 둘, 누르는 곳은 하나

    현황 할 일 줄 「수확을 시작할 예약 3건」과 주문 현황 '예약' 탭 안내 줄 「하우스 감귤 1단계 · 3건 수확 시작하기 ›」는 모두 그 기간 카드로 데려간다. 상태를 바꾸는 버튼은 기간 카드에만 있다(주문별 버튼은 이번에 없음, 후속).

  5. 5

    수확을 시작한 뒤에도 카드가 상태를 말한다

    다 옮기면 「수확 시작함 · 출하 준비 3건 보기 ›」(출하 준비 탭으로). 시작한 뒤에 입금 승인된 주문이 생기면 「남은 예약 1건도 출하 준비로」. 저장 안 한 값이 있으면 버튼을 막고 「저장한 뒤 수확을 시작할 수 있어요」.

  6. 6

    소비자 화면은 손대지 않는다

    출하 준비는 이미 소비자에게 '수확·포장 중'이고 상세 본문은 「농가가 수확을 시작했어요. 11월 10일 ~ 11월 20일 사이에 받아요.」다(orderText.ts, 주문 상세). 결정 B와 그대로 맞는다. 외부 알림은 지금 보낼 수단이 없다.

요청 실패시트 안 오류 줄 「수확을 시작하지 못했어요. 다시 눌러 주세요.」, 같은 멱등 키로 다시. 409/404면 시트를 닫고 카드 새로 읽기 + Notice 「이미 상태가 바뀌었어요. 최신 상태로 다시 보여 드려요.」(주문 현황과 같은 문구)

'수확 시작함'은 저장된 칸이 아니라 계산이다: 그 기간에 출하 준비·출하·배송 완료·구매 확정 주문이 하나라도 있으면 시작함(마이그레이션 없음, 질문 ②).

서버 설계 (고위험 경로 server/app/orders/**)

엔드포인트: 있던 것을 기간 단위로

200 { "changed": 3,
      "stageId": "st-1-2026-10-01",
      "orderIds": ["…", "…", "…"] }
  • 지금 harvest_start(db, farm_id, product_id)는 상품의 RESERVED 전체를 PREPARING으로 바꾸고 {changed}만 준다. 감사·멱등 없음. 프론트는 안 부르고 테스트 4곳이 시드 준비용으로 부른다.
  • 새 경로를 만들지 않고 본문에 stageId를 더한다. 기존 호출(테스트·Mock)이 그대로 돈다. 새 앱은 항상 stageId를 보낸다.
  • 대상: product_id·stage_id가 맞고 status = 'RESERVED'. 입금 대기·환불·취소는 그대로. SELECT … FOR UPDATE 뒤 바꾼다(지금과 같음).

오류·멱등·감사

  • 다른 농가 상품·없는 상품: 404 「찾을 수 없는 상품이에요.」(지금 load_my_product). 기간이 그 상품 것이 아님: 404 「찾을 수 없는 예약 기간이에요.」
  • 옮길 주문 0건: 200 changed: 0(자연 멱등, 오류 아님). 같은 키 재시도는 첫 응답 그대로, 감사 중복 없음. 키 없이 오면 400(다른 멱등 엔드포인트와 같음).
  • 감사: changed > 0일 때 ManagerEvent(event_type="orders.harvest_started", target_type="stage", target_id=stageId, actor_id, result={productId, orderIds, changed}) 한 행. update_tracking과 같은 방식이라 모델 변경 없음.
  • 소비자 알림: 보내지 않는다(지금 외부 알림 수단 없음). 주문 상세가 바뀌는 것으로 끝.
  • 상태 전이표: 예약 완료 → 출하 준비는 이미 표에 있다(server/app/orders/spec.md 계약). 새 전이 없음.

읽기 쪽 (앱이 버튼 글자·할 일을 그리려면)

  • 생산자 상품 GET /api/products/mine/{id}의 stages[]에 reservedOrderCount·awaitingOrderCount·preparingOrderCount·harvestStarted를 더한다(catalog/schemas.py·service.py, 모델 변경 없음). 질문 ⑦: 앱이 주문 목록에서 셀 수도 있다.
  • 현황 GET /api/orders/producer/dashboard의 todo에 toHarvest(예약 기간 끝난 기간의 예약 완료 주문 수)와 harvestTargets: [{productId, stageId, stageName, count}](끝난 순).
  • 예약 탭 안내 줄은 앱이 harvestTargets를 그대로 쓰고, 아직 열린 기간도 보이도록 같은 모양을 기간 끝 조건 없이 한 번 더 받는다(?status=RESERVED 목록에서 stageId로 묶어도 됨, 주문 응답에 stageId·stageName 추가).

바뀌지 않는 것

  • server/app/*/models.py, server/migrations/**: 손대지 않는다.
  • 출하(/ship)·송장 수정·취소: 그대로. 출하 준비에서도 소비자 취소 = 전액 환불(FEAT-11 사전 조건 그대로).
  • R-06 물량: 상태만 바뀌고 reserved_count·kg 집계는 그대로(출하 때 옮겨짐).

PM 확인 질문

  1. ① 기간 단위가 맞나? 기간(단계)은 같은 '받는 시기'를 나누는 얼리버드 가격 구간이다(Mock 하우스 감귤 1~3단계 모두 11.10~11.20 배송). 농가 입장에서 수확은 보통 상품 단위다. 제안: 결정대로 기간 단위로 두되(먼저 예약한 분부터 보낼 수 있음), 기간이 여럿이고 모두 끝났으면 맨 아래 「모든 기간 수확 시작 · n건」을 둘지 정해 주세요. 서버는 stageId 없이 부르면 상품 전체라 둘 다 된다.
  2. ② '수확 시작함' 기록 칸: 제안은 칸 없이 계산(출하 준비 이후 주문이 있으면 시작함). 시작 시각을 소비자에게 보여 주거나, 시작한 뒤 입금 승인되는 주문을 바로 출하 준비로 보내려면 stages.harvest_started_at과 마이그레이션이 필요하다(고위험 경로 추가).
  3. ③ 예약 기간이 아직 열린 기간도 수확을 시작할 수 있나? 제안: 된다(시트에 「그 뒤 들어온 주문은 다시 눌러 옮겨요」). 막으면 마지막 기간은 받는 시기 전날까지 열려 있어 시작이 늦어진다.
  4. ④ 시트의 n과 실제 수가 다를 때(그사이 입금 승인·취소): 제안은 막지 않고 그때의 예약 완료를 모두 옮기고 토스트가 실제 수를 말한다. 정확히 본 주문만 옮기려면 expectedOrderIds를 받아 다르면 409로 바꿀 수 있다.
  5. ⑤ 받는 시기 변경에 아직 답하지 않은 주문(proposedDeliveryStart)도 옮기나? 제안: 옮긴다(출하 준비에서도 답할 수 있음). 출하를 그 답 뒤로 막을지는 이번 범위 밖.
  6. ⑥ HE-06의 나머지(탭 구분이 헷갈림, P12)는 이번에 안내 문구 한 줄만 바꾸고 탭 이름은 그대로 둔다. 탭 이름까지 바꿀지?
  7. ⑦ 기간별 주문 수를 서버 상품 응답에 더할지(제안), 앱이 주문 목록(stageId 추가)에서 셀지.
  8. ⑧ 후속 이슈: 주문 줄마다 '출하 준비로' 버튼(일부만 먼저 보낼 때)을 따로 등록해 둘까? Figma v6 반영은 승인 뒤 후속 요청.
