농가 검색이 실패하면 실패라고 말하고, 다시 시도는 처음부터

I3 탐색 여정 I3-DISC-03(오류) FAIL, baseline i3-b2-87792b7. 농가 목록(SCR-02)에서 검색 요청 하나가 실패하면 검색 전 목록이 새 결과인 것처럼 남고 안내가 없다. 맨 아래 ‘다시 시도’를 누르면 결과가 기존 목록 뒤에 붙어 같은 농가가 두 번 보이고 ‘농가 5곳’이 된다. 이 보드는 개발 전에 PM 승인을 받기 위한 제안이다.

I3-DISC-03 FAIL FEAT-06 · AC-06-2 · SCR-02 screens.md 3장 목록 규칙 부모: DEV-177 (I3-T20)

정할 것 (요약)

실패를 어디에검색칸 바로 아래 오류 상자(Notice)공용 Notice tone="error" + 테두리 ‘다시 시도’. 토스트는 쓰지 않는다(결정 37).
남은 목록지우지 않고 ‘이전 목록’이라고 이름 붙임완료 조건 “기존 목록 위에 실패 안내”. 대안 B(목록을 지우고 오류만)는 아래 열린 질문 1.
다시 시도실패한 검색을 처음부터 받아 목록을 바꿈덧붙이기(load(false))는 ‘더 보기’ 실패에만.
중복같은 농가는 한 번만, 늦게 온 응답은 버림요청 번호로 지난 검색 응답 무시, 페이지 합칠 때 farmId로 거름.

지금 (BEFORE) — 코드 apps/consumer/src/app/(tabs)/farms/index.tsx FarmList에서 재현

시드 데이터 그대로(기록 화면 I3-DISC-03-01-search-failed.png, -02-search-retried.png, 390×844). 첫 GET /api/farms?q=한라네만 503으로 실패시킴.

바꾼 뒤 (AFTER)

A1→A2→A3이 기록과 같은 흐름(한라네 검색 실패 → 다시 시도 → 1곳). A4는 공통 목록 규칙(다음 페이지 실패), A5는 PM이 고를 대안 B.

디자인 무브

1

실패는 검색칸 바로 아래, 결과 머리줄 자리에 오류 상자로

목록이 이미 있을 때 새 검색(검색어 바뀜)이 실패하면 검색칸 아래에 Notice tone="error"를 둔다. 제목에 사용자가 친 검색어를 그대로 넣어 “무엇이” 실패했는지 말한다. accessibilityRole="alert"라 스크린 리더도 읽는다.

왜: 지금은 실패 신호가 마지막 카드 아래 글자 버튼 하나뿐이라 스크롤하지 않으면 안 보인다(I3-DISC-03 “Failure is visible” ✗). 눈이 가는 자리(입력 바로 아래)에 원인과 행동을 함께 둔다. 새 컴포넌트를 만들지 않고 생산자 앱·주문서에서 이미 쓰는 Notice를 재사용한다.

2

남은 목록은 ‘이전 목록’이라고 이름을 바꾼다

머리줄 ‘마감 임박순 · 농가 4곳’을 ‘이전 목록 · 농가 4곳’으로 바꾼다. 카드는 그대로 누를 수 있고 흐리게 하지 않는다(대비 유지).

왜: 지금은 검색칸에 ‘한라네’, 머리줄에 ‘농가 4곳’이 함께 보여 검색 결과가 4곳인 것처럼 속인다. 지우면 보던 것을 잃고(완료 조건과도 어긋남), 흐리게 하면 15px 보조 글자 대비가 무너진다. 이름만 바꾸는 것이 가장 작고 정직한 변경이다.

3

‘다시 시도’는 실패한 그 검색을 처음부터

오류 상자 안의 ‘다시 시도’는 load(true): cursor 없이 실패한 검색어로 다시 받아 목록을 바꾼다. 성공하면 오류 상자가 사라지고 머리줄이 ‘마감 임박순 · 농가 1곳’으로 돌아온다. 맨 아래 덧붙이기 ‘다시 시도’는 ‘더 보기’가 실패했을 때만 남는다(A4).

왜: 버그의 직접 원인(검색 실패를 페이지 실패처럼 load(false)로 재시도)을 없앤다. 실패의 종류(새 검색 / 다음 페이지)에 따라 재시도 위치와 방식이 달라야 screens.md 3장 “다음 페이지 실패는 하단에 다시 시도” 규칙과도 맞는다.

4

다시 시도 중엔 버튼을 잠그고 머리줄로 진행을 보인다

재시도 중 버튼은 로딩(Button loading, 누를 수 없음), 머리줄은 ‘‘한라네’ 찾는 중’. 처음 검색할 때(목록이 있는 채 검색어를 바꿀 때)도 같은 머리줄을 써서, 응답 전의 옛 목록이 새 결과처럼 보이는 순간을 줄인다.

왜: 공통 규칙 “처리 중에는 버튼을 잠근다”(screens.md 3장 중복 방지). 연타로 같은 요청이 여러 번 가면 응답 순서에 따라 다시 섞일 수 있다. 지금은 검색 중 표시가 전혀 없어 300ms 디바운스 뒤 응답까지 옛 목록이 그대로다.

5

보이지 않는 보증: 늦은 응답은 버리고, 같은 농가는 한 번만

요청마다 번호를 붙여 마지막 요청의 응답만 반영한다. 페이지를 합칠 때 farmId로 이미 있는 농가를 거른다. 화면 변화는 없지만 콘솔 “two children with the same key” 경고가 다시 나올 길을 막는다.

왜: ‘한라네’ → ‘한라’처럼 빠르게 바꾸면 앞 요청이 늦게 와서 목록을 덮을 수 있다. 서버가 같은 농가를 두 페이지에 걸쳐 줄 가능성(정렬 키 동률)도 막는다. 키 중복은 React가 카드를 잘못 재사용하는 원인이라 리스트의 키 보장은 화면 정확성 문제다.

코드 변경 계획 (승인 뒤)

  1. 순수 로직 분리 apps/consumer/src/lib/farmSearch.ts: farmListReducer(state, action) — 상태 {items, cursor, shownQuery, pending: {seq, query, mode}|null, failed: {mode: "reset"|"more", query, offline}|null}, 동작 start·success·fail. 그리고 listHeader(state), failureCopy(failed). React Native 없이 node 테스트가 import한다(DEV-207 orderText.ts와 같은 방식).
  2. reset vs append: success가 mode === "reset"이면 items = page.items(바꿈), "more"면 기존 뒤에 붙이되 farmId 기준으로 이미 있는 것은 거른다(Map, 순서 유지).
  3. 늦은 응답 무시: useRef 요청 번호. success/fail의 seq가 pending.seq와 다르면 상태를 바꾸지 않는다.
  4. FarmList 화면: error && !items → LoadError(그대로). failed.mode === "reset" && items → 검색칸 아래 Notice tone="error" + Button variant="outline" loading, onPress={() => load(true)}. failed.mode === "more" → 목록 아래 한 줄 + 글자 버튼 load(false). 맨 아래 공용 ‘다시 시도’(error && items → load(false))는 지운다.
  5. 키: 카드 키는 지금처럼 farmId. 2번의 거름 덕에 같은 키가 두 번 생기지 않는다.
  6. 서버·API 타입은 바꾸지 않는다(GET /api/farms 그대로).

열린 질문 (PM)

  1. 남은 목록: A(유지 + ‘이전 목록’) vs B(지우고 오류만, A5)? 제안은 A(이슈 완료 조건 “기존 목록 위에 실패 안내”). B는 오해 여지가 0이지만 보던 목록을 잃는다.
  2. 오류 본문에 서버 메시지를 쓸지? 첫 불러오기의 LoadError는 ApiError.message를 그대로 보인다. 검색 오류 상자는 고정 문구(연결 끊김/그 밖) 두 가지를 제안한다 — 503 등에서 기술적인 문장이 나오지 않게.
  3. 머리줄 ‘찾는 중’(무브 4)을 이번 범위에 넣을지? 버그 수정에 꼭 필요하진 않지만 같은 오해(옛 목록이 새 결과처럼)를 막는다. 빼면 무브 1·2·3·5만.
  4. 새 AC를 만들지? 이슈 지시대로 테스트 이름은 AC-06-2를 쓴다. 실패·재시도 자체를 AC로 남기려면 FEAT-06에 AC-06-7을 새로 둘 수 있다(제안은 E4 예외 흐름만).
