2이름 규칙

이슈 키를 세 곳에 넣어요

브랜치 이름·커밋 메시지·PR 제목에 이슈 키를 넣으면 PR이 Linear 이슈에 자동으로 연결돼요. 나머지는 영어로 적어요. Linear의 "Copy git branch name"이 한글 제목을 브랜치에 넣어 URL 인코딩된 PR 링크·셸 따옴표·도구 호환 문제가 생겼고, SWPP-119에서 영어 이름으로 바꿨어요. PR 제목은 squash 때 main 커밋 제목이 되므로 영어로 맞춰요.

브랜치<github 아이디>/<이슈 키 소문자>-<영어 요약 2~5단어>실제 예: nemodleo/dev-434-split-withdraw-kept-line
커밋type(scope): 요약 (DEV-12)type은 feat fix docs refactor test chore · 실제 예: feat(ui): split withdraw sheet kept line by role (DEV-434)
PR 제목[DEV-12] <English summary>실제 예: [DEV-434] Split the withdraw sheet kept line for consumers and producers

  • PR을 연 뒤에는 브랜치 이름을 바꾸지 않아요. 바꾸면 GitHub가 PR을 닫아요.
  • main에 직접 push하거나 force push하는 것은 main ruleset이 막아요(GitHub 설정, 2026-11-23 확인).

3작업 순서

PR 하나를 끝내는 8단계

순서의 중심은 이슈 파일 tasks/<이슈 키>.md예요. 코드보다 먼저 쓰고, 범위·결정·작업을 여기에 둬요. 범위는 에이전트가 지키기로 한 경계예요. 기계로 막지는 않고, AI 1차 리뷰와 사람 리뷰가 봐요.

이슈마다 파일을 따로 두는 이유는 충돌이에요. 예전에는 폴더마다 tasks.md 하나에 이슈 절을 덧붙였고, 같은 폴더를 건드린 PR 둘이 동시에 열리면 반드시 충돌했어요(11/4 PR #393~#396은 머지마다 충돌을 손으로 풀었어요). ADR 0014·DEV-219에서 이슈별 파일로 나눴어요.

  1. Linear 이슈사람

    왜·완료 조건을 채우고 In Progress로 바꿔요.

  2. 브랜치사람

    origin/main에서 이름 규칙대로 직접 만들어요.

  3. specspec 스킬사람 확인

    이슈 파일(없으면 폴더 spec.md도)을 만들고, 사람이 범위를 확인한 뒤 첫 커밋으로 push해요.

  4. draft PRpr-context 스킬

    branch → main draft PR.

  5. 구현사람AI

    계획에 없던 결정은 코드보다 이슈 파일에 먼저 적어요.

  6. 리뷰 요청pr-review 스킬사람

    AI 1차 리뷰 반영 → draft 해제 → 사람 리뷰어 1명 지정.

  7. 리뷰 반영사람

    코멘트마다 수정 커밋이나 답글로 닫아요.

  8. 머지사람자동

    main 병합으로 최신화 → 머지 → 자동 배포 → 배포 확인.

완료의 기준(테스트를 실행하지 못하면 미완료), 병렬 작업의 git worktree와 브랜치별 DB는 원문의 Spec-Anchored 원칙과 브랜치·커밋·PR 절에 있어요.

5사람과 AI의 역할

에이전트는 이슈 파일부터 구현·1차 리뷰까지 하고, 확인은 층마다 나뉘어요

작성자는 에이전트가 쓴 줄도 자기 코드로 책임지고, 에이전트 없이 diff를 설명할 수 있어야 해요. 아래 층 중 앞의 셋(이슈 파일 범위, AI 1차 리뷰, spec-check)은 모두 에이전트가 쓴 이슈 파일을 기준으로 삼아요. 이슈 파일이 틀리면 셋이 함께 놓쳐요. 그래서 사람 리뷰는 diff를 FEAT 인수 조건·폴더 spec.md와도 대조하고, 이슈 파일만 읽고 무엇을 왜 바꿨는지 이해되는지를 따로 봐요(pr-review 2절).

에이전트가 읽는 순서

  1. AGENTS.md

    Codex는 바로, Claude Code는 CLAUDE.md의 @AGENTS.md로 세션 시작 때 읽어요.

  2. 스킬

    spec·pr-context·pr-review가 단계별 절차와 산출물 형식을 정해요.

  3. 제품 스펙

    docs/spec/README.md의 읽는 순서대로 FEAT·규칙.

  4. 폴더 spec.md → 이슈 파일

    구현 결정과 이번 작업의 범위.

사람이 정하는 것

이슈의 왜·완료 조건, 이슈 파일의 범위, 디자인 승인, 사람 리뷰, 머지 지시, Human 시간. 에이전트가 멈추고 사람에게 묻는 때(범위 밖 파일, 스펙끼리 다름, 실행이 막힌 테스트, 반복 실패)와 하지 않는 일은 원문 Spec-Anchored 원칙과 9절에 있어요.

Agent · Tokens · Human 시간

이터레이션 AI 협업 리포트와 시트 기록에 쓰는 값이에요. Linear 결과와 PR 본문에 Agent 시간 / Tokens / Human 시간을 0.5시간 단위로 적어요. Agent 시간은 실행 기록이 없으면 시작·끝 시각으로 어림해 약을 붙이고, Tokens는 도구가 준 값만 적고 없으면 비워요. Human 시간은 작성자의 자기 보고예요. 에이전트가 마무리한 PR·Linear에 "미계측"만 남고 Human 시간이 빠지던 문제로 정했어요(SWPP-130). 이 값은 시간과 양이고, 결과의 품질이나 재작업은 재지 않아요.

7PR 체크와 spec-check

머지 큐가 기다리는 필수 체크

main ruleset의 필수 체크는 ci-ok figma-line checker-tests예요.

CI는 job마다 필수 체크로 걸지 않고 마지막 job ci-ok 하나로 모아요. 바뀐 경로에 따라 job을 건너뛰고, job 이름이 바뀌어도 보호 설정을 고치지 않게 하려는 것이에요(DEV-234, ci.yml 머리 주석). 건너뛴 job은 통과로, 실패·취소는 실패로 모아요.

체크무엇을 보나
ci-okCI가 그 길에서 고른 server·apps·admin-web·integration과 이 페이지 대조(guide) 결과를 모아요. 문서만 바꾼 PR은 server·apps·integration을 건너뛰어요.
figma-lineapps/*/src·packages/ui/src·scripts/admin-web가 바뀐 PR 본문에 Figma: 줄이 정확히 하나인지. PR에서만 돌고 머지 큐에서는 건너뛰어요(통과로 봄).
checker-testsspec-check 도구 자체의 계약 테스트(모델·키 없이)
spec-code-review필수 아님. 결과는 PASS · NO_FINDINGS · MISMATCH · INCOMPLETE · SKIPPED. NO_FINDINGS(못 본 문맥이 남음)와 SKIPPED는 PASS가 아니에요.

spec-check가 도는 때

repository variable SPEC_CHECK_ENABLED가 켜져 있을 때(2026-11-23 확인) ready PR의 push·본문 수정·draft 해제마다 돌아요. draft에서는 돌지 않고, fork·bot PR은 SKIPPED예요. fail이어도 머지를 막지 않는 대신, 작성자가 보고서를 읽고 처리 결정(고침·스펙 변경·오탐·사람 리뷰 대체)을 PR 코멘트로 남기고, 리뷰어는 그 코멘트가 없으면 Approve를 미뤄요(DEV-196).

표 형식은 push 전에

checker는 PR 본문 "Spec ↔ Code 확인" 표의 backtick 경로만 읽고, 바뀐 파일이 모두 표에 있어야 해요.

8머지 큐와 배포 확인

Merge when ready 다음에 일어나는 일

머지 큐(DEV-234)는 낡은 main 위에서만 통과한 PR이 머지되는 일을 막아요. 큐는 앞에 줄 선 PR까지 합친 커밋을 검사하고, 통과한 그 커밋으로 main을 옮겨요. main push의 CI는 같은 커밋이 큐에서 통과한 기록을 찾으면 다시 돌지 않고(validated 길) 배포로 넘어가요.

배포는 이동 태그 이후 바뀐 대상만 올려요(DEV-139). 마지막 커밋만 보던 때는, 자기 CI가 취소되거나 뒤에 온 문서 커밋에 밀린 변경이 배포에서 빠졌어요. 태그보다 오래된 커밋은 건너뛰어 늦게 끝난 실행이 운영을 되돌리지 않아요.

  1. 큐가 검사자동

    바뀐 경로로 고른 필수 체크를 돌려요. 관련 변경이 있으면 integration은 spec 전체를 돌아요.

  2. 바뀐 대상만 배포자동

    main CI가 성공하면 server/** → Railway, 앱 → Vercel 앱, scripts/admin-web/ → Vercel 관리자 페이지. 바뀐 게 없으면 건너뛰고 성공으로 끝나요.

  3. 배포 확인사람

    배포 job의 변경 감지 단계 로그에서 첫 줄 Comparing <base>..<head>와 마지막 줄 Deploying/Skipping, 이동 태그가 머지 커밋을 가리키는지, 그리고 운영 응답(curl 먼저)으로 확인해요. Actions 목록의 커밋 라벨은 실제로 올린 커밋과 다를 수 있어요.

  4. Linear 결과사람

    산출물·시간·커밋·배운 점과 배포 확인.

hotfix 길

운영 장애 급한 수정에만 hotfix 라벨을 붙여요. integration 없이 머지·배포되고, 머지 뒤 CI full이 그 커밋을 전체로 검사해 실패하면 알림 이슈가 열려요. 고위험 경로의 사람 리뷰 규칙은 hotfix도 같아요.

PR 쌓기

DEV-126(CI·spec-check 트리거 수정) 전까지는 쌓지 않는다. 지금은 base가 작업 브랜치인 PR에서 CI·spec-check가 돌지 않아요.

main CI가 깨지면 머지한 사람이 바로 고치거나 revert해요

main push CI가 실패하면 배포 워크플로가 건너뛰어, 깨진 동안 다른 사람의 배포도 멈춰요.

13회의록 · 위키

회의록은 레포에 쓰면 위키에 올라가요

위키에서 바로 고치면 PR 리뷰를 거치지 않고 저장소와 위키가 갈라져요. 그래서 원본은 레포 docs/wiki/이고, main에 머지되면 위키를 덮어써요. 회의록은 docs/wiki/meetings/에 파일로 쓰면 위키 "Meeting-Logs" 한 페이지에 최신순으로 합쳐져요.

위키를 GitHub에서 직접 고치지 마세요

위키 화면에서 고친 내용은 다음 동기화 때 사라져요. 오타 하나라도 docs/wiki/의 파일을 고쳐 PR로 올려요.

회의록 쓰는 순서

  1. 템플릿 복사

    docs/wiki/meetings/_template.md를 YYYY-MM-DD-영문-요약.md로

  2. 영어로 작성

    첫 줄은 템플릿의 ## YYYY-MM-DD HH:MM — Meeting title 형식

  3. 커밋·PR

    회의 이슈 키를 넣어 docs(meetings): 10/02 meeting notes (SWPP-71)처럼

  4. 머지 후 확인

    위키 Meeting-Logs에 올라왔는지

지킬 것

  • 파일 이름이 YYYY-MM-DD-로 시작해야 합쳐지고, _로 시작하는 파일은 건너뛰어요
  • 위키는 TA가 봐요. 개인정보, 회사·법인·세무 이야기는 쓰지 않아요
  • 할 일 표의 개발 이슈는 GitHub 이슈 번호(#n)로. TA는 Linear 링크를 못 열어요

머지 큐는 필수 체크(7절)가 통과해야 PR을 넣어요. 빨간 체크의 로그를 열어 봐요. 버튼이 눌려도 사람 리뷰는 따로예요(4절).

브랜치 이름·커밋 메시지·PR 제목에 DEV-xx 같은 이슈 키가 있는지 확인해요.

배포가 건너뛰어졌어요

이동 태그 뒤 그 대상의 경로가 안 바뀌었으면 Skipping이에요. main CI가 실패해도 배포 워크플로가 건너뛰어요(8절).

마이그레이션 head가 두 개예요

main을 병합하고 alembic heads를 봐요. 리비전 번호가 겹치면 뒤에 머지하는 쪽이 올려요.

guide 체크가 빨개요

로그에 키·페이지 줄·실제값·기대값이 찍혀요. AGENTS.md를 바꿨거나 링크된 파일의 제목을 바꿨다면 같은 PR에서 이 페이지를 고쳐요.

내 커밋이 Insights에 안 잡혀요

git config user.email이 GitHub 계정 이메일과 같아야 해요.

오래 막혀요

사람은 1시간 이상 막히면 PM에게 알려요. 에이전트가 멈추는 기준은 원문 Spec-Anchored 원칙에 있어요.
