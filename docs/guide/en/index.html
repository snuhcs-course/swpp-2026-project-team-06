Collaboration map

How the four people on the farmclub team (SWPP 2026, Team 6) work with AI coding agents. The rules themselves live in AGENTS.md. This page explains the order and the reasons, then links to the rule.

Code an agent writes still has to pass human review and the merge queue before it reaches main. Only two places actually block it by machine: the merge queue and the main ruleset. The rest is held by team rules.

AGENTS.md and the issue files are in Korean. Where this page shows a rule value that CI compares with AGENTS.md, it keeps the Korean original and gives an English gloss in parentheses. Everything else is paraphrased and links to the Korean section. The Korean edition of this page is the source.

  • A failing spec-check does not block the merge. Instead, the reviewer does not approve until the author has posted a decision on it (PR checks and merging).
  • A PR that touches a high-risk path does not reach step 8 without human review. GitHub settings do not enforce this. The team rule does.
  • Only urgent production fixes use the hotfix label. They merge without integration tests, and CI full runs everything after the merge.

What people do

The issue file scope, the first AI review and spec-check all take the issue file as their reference, and an agent wrote that file. If the issue file is wrong, all three miss the same thing. So people do the four things below, and human review reads the issue file as well as the diff.

  • Scope check (step 3). Read the allowed paths in the issue file before the first commit. Nothing blocks a change outside the scope by machine.
  • Human review (step 7). Either another member's GitHub Approve, or the author reading the diff and writing it on the 사람이 한 일: (what the human did) line of the PR body. The agent only writes there what a person actually did.
  • Telling it to merge (step 8). The agent does not merge unless a person tells it to. A high-risk PR without human review is not merged even then.
  • Deploy check (step 8). Read the first line of the deploy log (Comparing), the last line (Deploying/Skipping), and the production response with curl. Do not trust the commit label in the Actions list.

AI usage record

The Linear result and the PR body record Agent 시간 / Tokens / Human 시간 (agent time / tokens / human time) in 0.5시간 단위 (half-hour units). Without a run log, the time is estimated from start and end times and marked 약 (about). Tokens are written only when the tool reports them, otherwise left blank. Human time is self-reported. This record says nothing about the quality of the result (SWPP-130).

Commits and PRs do not carry Co-Authored-By: Claude (SWPP-115). How AI was used, and cases where it was wrong, go in one line under "AI 사용" (AI usage) in the PR body. These lines feed the AI collaboration report for each iteration (source).

Naming

Put the issue key in the branch name, the commit message and the PR title, and the PR links itself to the Linear issue. Write the rest in English. Linear's "Copy git branch name" put the Korean issue title into branch names, which broke link encoding and shell quoting, so the team does not use it (SWPP-119).

PR checks and merging

The required checks in the main ruleset are ci-ok figma-line checker-tests. CI skips jobs depending on which paths changed, so making each job required would let a skipped job block the merge. The last job, ci-ok, collects them instead. A skipped job counts as passed; a failed or cancelled job counts as failed (DEV-234, CI.md lanes).

CheckWhat it looks at
ci-okThe server, apps, admin-web and integration jobs picked for that lane, plus guide (this page). A docs-only PR skips server, apps and integration.
figma-lineWhether a PR that changes screen code has exactly one Figma: line in its body. Skipped in the merge queue.
checker-testsContract tests for the spec-check tool itself (no model, no key).
spec-code-reviewNot required. The result is one of PASS, NO_FINDINGS, MISMATCH, INCOMPLETE, SKIPPED. NO_FINDINGS and SKIPPED are not PASS.

spec-check is a model's judgement and can be wrong, so its result does not block the merge. When it fails, the author posts a PR comment with a decision (고침·스펙 변경·오탐·사람 리뷰 대체: fix, spec change, false positive, or human review instead), and the reviewer does not approve before that comment exists. It runs on push, body edits and leaving draft for ready PRs (DEV-196, spec-check 1.1, 3). Check the table format before pushing with python3 .agents/skills/pr-context/check_table.py <body file> (PR template).

Merge queue and deploys

A PR that only passed on an old main can break main once it lands. The merge queue tests the commit that combines the PRs ahead of it in line, and moves main to that commit if it passes. CI on the main push does not run again (the validated lane) when the same commit already passed in the queue.

Deploys ship only the targets that changed since the moving tag: server/** to Railway, the apps to Vercel, scripts/admin-web/ to the Vercel admin page. Commits older than the tag are skipped, so a late run cannot roll production back (DEV-139). The deploy check is done with the log and curl, as described under what people do.

If CI on main breaks, whoever merged fixes it or reverts right away. Other people's deploys stop while it is broken. On stacking PRs AGENTS.md says DEV-126(CI·spec-check 트리거 수정) 전까지는 쌓지 않는다 (no stacking until DEV-126, the CI and spec-check trigger fix) (source). DEV-126 was cancelled, though. See known limits.

docs/spec/ is the source for behaviour, rules and acceptance criteria. Read prd.md, functional/FEAT-xx-*.md, rules.md, then ia.md. When documents disagree, ask instead of guessing.

In a code folder, spec.md holds implementation decisions and tasks/<issue key>.md is the record of one issue. Test names carry the acceptance criterion ID (test_AC_09_1_...). Why each issue gets its own file: ADR 0014.

Common snags

  • The merge button does nothing: read the log of the red required check. Human review is separate even when it works.
  • The PR does not show up in Linear: the issue key in the branch, commit messages and PR title.
  • spec-check says INCOMPLETE: check the table format with check_table.py first.
  • A deploy was skipped: the first line of the deploy log. Either nothing changed since the moving tag or CI on main failed.
  • Two migration heads: merge main, then run alembic heads. Whoever merges second renumbers.
  • The guide check is red: read the key, line, actual and expected values in the log and fix as described below.
  • Commits do not count in Insights: check that git config user.email matches your GitHub email.
  • Stuck for over an hour: tell the PM.

Editing this page

The CI guide job (check-guide.mjs) compares two things on every run. It checks the marked values for 11 keys (branch commit pr-title checks high-risk steps skills ai-log spec-check test-urls stacking) against the matching AGENTS.md sections, and checks repository links against the files and their headings. On PRs and in the merge queue a mismatch blocks; on a main push it only warns.

This English edition is checked the same way, and CI also fails if the two editions differ in section ids, repository links or marked values. Change the Korean page first, then this one, in the same PR.

The check does not read prose, elements hidden with CSS or the content behind external links. Whoever changes a rule, and their reviewer, update the related section.
