| 정상 흐름 | 0) (DEV-68) ‘입금 대기’·‘환불’ 탭의 줄마다 ‘미승인’ 1 : ‘승인’ 2 버튼. 입금 승인은 이름·옵션×수량·금액 확인 시트 후 처리하고 환불 승인은 줄에서 바로 처리한다(2026-11-02 owner 결정, DEV-179). 입금 승인 → 예약 완료(FEAT-09 AC-09-8), 환불 승인 → 입금했던 계좌로 송금을 마쳤다고 기록(AC-17-7). 미승인 → 줄 안에 ‘미승인 사유’ 토글(사유 3개 + 직접 입력, 하나 필수, 소비자에게 그대로 보임)이 펼쳐지고, 입금은 ‘입금 대기로 두기’·‘주문 취소’ 중 하나를 고른다(AC-09-9, AC-17-8) 1) 전체/입금 대기/예약/출하 준비/출하/환불 주문 조회(예약 탭은 조회만, 맨 위 ‘○○ 1단계 · n건 수확 시작하기’ 줄이 예약 기간 카드로 데려간다) 1-1) (DEV-231) 예약 기간·가격(SCR-26) 카드의 ‘수확’ 칸에서 ‘수확 시작 · 출하 준비 n건’ → 확인 시트(옮겨질 주문, 소비자에게 ‘수확·포장 중’, 보내기 전 취소 가능, 되돌릴 수 없음) → 그 기간의 예약 완료 주문이 출하 준비로. 시트 건수와 실제가 달라도 막지 않고 토스트가 실제 수를 말한다 2) 기존 출하 준비 주문 목록 표시(받는 사람·연락처·주소·배송 메모) 3) 보낸 주문을 여러 건 고르고, 줄마다 택배사·송장 번호 입력(선택) 4) ‘n건 출하로 바꾸기’ → 확인 시트 5) 확인 → 주문마다 출하 처리(주문별 API 반복), 출하일·택배사·송장 번호 기록. 소비자 주문 상세에는 ‘배송 중’과 배송 조회가 보인다. 6) 출하된 줄의 ‘송장 수정’으로 기존 택배사·송장 편집 시트를 다시 연다. 저장하면 자기 농가 SHIPPED 주문의 값만 정정하고 소비자 배송 조회가 새 값을 사용한다. 정정 전후 값·시각·행위자는 서버 감사에만 기록하며 생산자·소비자 UI에는 이력을 표시하지 않는다. (I2) 3)\~4) 대신 “김○○님 5kg 오늘 보냈어요, 송장 123-456”을 입력하면 AI가 주문과 송장 번호를 찾아 확인을 요청한다 |
| 예외 흐름 | E1 이미 바뀌었거나 허용되지 않는 상태(409) → 최신 상태로 다시 그림. E2 확인 창에서 취소 → 아무것도 바뀌지 않음. E3 다른 농가 주문 → 거부. E4 배송 완료로 바꾸려 함 → 생산자는 바꿀 수 없음(운영자, R-19) |
| 사후 조건 | 주문은 출하, 소비자는 더 이상 취소할 수 없고 주문 상세에서 송장 번호를 본다 |
| 입력·검증 | 입금 대기 줄에는 배송지를 보여 주지 않는다(R-15). 송장 번호는 없어도 되고, 있으면 50자 이하. 송장 번호를 입력할 때 택배사를 선택한다. 출하 후 정정은 택배사 필수, 번호는 같은 50자 이하 형식(생략/비우기 가능)이다. 현재 프론트의 상태 전이는 기존 출하 준비 → 출하뿐이며 SHIPPED 송장 수정은 상태를 바꾸지 않는다. 예약 완료 → 출하 준비는 예약 기간 카드의 수확 시작(기간 단위, DEV-231)으로만 바뀐다. 주문별 버튼·자동 전이는 없고, 출하 준비 → 예약 완료로 되돌리지 않는다. 받는 시기 변경에 아직 답하지 않은 주문도 함께 옮긴다 |
| 규칙 | R-07, R-15, R-19, R-28 |

- [ ] AC-17-1. (I2, 자연어 출하) **Given** AI가 주문을 찾아 확인을 요청했다 / **When** 확인을 누르기 전이다 / **Then** 어떤 주문도 상태가 바뀌지 않는다
- [ ] AC-17-2. **Given** 출하 준비 주문이다 / **When** 확인을 누른다 / **Then** 소비자 주문 상세가 ‘배송 중’(상태 `SHIPPED`)으로 바뀌고 취소 버튼이 사라진다
- [ ] AC-17-3. (DEV-231로 좁힘) **Given** 예약 완료 주문이 3건인 상품이다 / **When** 주문 현황·현황·예약 기간 화면을 열기만 한다 / **Then** 3건의 상태는 RESERVED 그대로다(자동 전이 없음). 출하 준비로는 AC-17-11의 수확 시작으로만 바뀐다
- [ ] AC-17-4. **Given** 출하된 주문이다 / **When** 생산자가 배송 완료로 바꾸는 요청을 보낸다 / **Then** 거부되고 상태는 출하로 남는다
- [ ] AC-17-5. **Given** 출하 준비 주문에 송장 번호 “123-456”을 넣었다 / **When** 출하로 바꾼다 / **Then** 출하일과 송장 번호가 기록되고 소비자 주문 상세에 송장 번호가 보인다
- [ ] AC-17-7. (DEV-68) **Given** 전액 환불된 주문이다 / **When** 생산자가 입금했던 계좌로 보낸 뒤 ‘송금 완료’를 누른다 / **Then** 환불 송금 시각이 기록되고 소비자 주문 상세·내역에 ‘환불 완료’로 보이며 현황의 환불 할 일 수가 준다. 환불이 아닌 주문은 409다. 운영자 부분 환불(주문은 계속 진행)의 농가 송금 표시는 이번 범위가 아니다(나중 고려)
- [ ] AC-17-8. (DEV-68) **Given** 송금 전인 환불 주문이다 / **When** 생산자가 줄에서 ‘미승인’을 누르고 사유를 적는다 / **Then** 사유가 없으면 400이다. 환불은 송금 대기로 남고 소비자 주문 상세에 ‘환불 송금이 늦어지고 있어요 · 사유’, 내역에 ‘환불 송금 늦어짐’이 보인다. 나중에 승인하면 사유는 지워진다. 이미 송금을 마쳤거나 환불이 아닌 주문은 409다

- [ ] AC-17-9. (DEV-179) **Given** 자기 농가의 SHIPPED 주문이다 / **When** 생산자가 현재 `trackingVersion`과 `Idempotency-Key`로 택배사·송장 번호를 수정한다 / **Then** 상태·출하일을 유지하고 소비자 배송 조회는 새 값을 사용한다. 실제 변경마다 이전/새 값·시각·actor를 서버 감사에 기록하고 이력은 DB/운영자 관리 API로만 조회한다. 타농가는 404, SHIPPED 이외는 409, 필수 택배사·50자 형식 위반은 400, 버전 불일치는 409다. 동일 키·본문 재시도는 같은 결과이며 이력은 중복되지 않는다.
- [ ] AC-17-10. (DEV-226) **Given** 같은 소비자가 이름은 다르고 옵션이 같은 두 상품을 주문했다 / **When** 생산자가 주문 현황 줄·입금 승인 시트를 본다 / **Then** ‘이름 · 상품명 옵션 × 수량’으로 상품이 갈린다. 줄에서 길면 상품명만 한 줄로 줄이고 이름·옵션 × 수량은 끝까지 보인다

- [ ] AC-17-11. (DEV-231) **Given** 한 상품의 1단계에 예약 완료 2건·입금 대기 1건, 2단계에 예약 완료 1건이 있다 / **When** 생산자가 1단계 카드에서 ‘수확 시작 · 출하 준비 2건’ → 확인 시트 → ‘수확 시작 · 2건’을 누른다 / **Then** 1단계 예약 완료 2건만 출하 준비(`PREPARING`)가 되고 입금 대기·2단계·다른 상품은 그대로다. 소비자 주문 상세는 ‘수확·포장 중’이고 보내기 전 취소(전액 환불)는 그대로 된다. 카드는 ‘수확 시작함 · 출하 준비 n건 보기’로 바뀌고, 그 뒤 승인된 예약은 ‘남은 예약 n건도 출하 준비로’로 다시 옮긴다. 저장 안 한 값이 있으면 버튼을 누를 수 없다. 예약 기간이 아직 열린 기간도 시작할 수 있다(시트: ‘그 뒤 들어온 주문은 다시 눌러 옮겨요’)
- [ ] AC-17-12. (DEV-231) **Given** 수확 시작 요청이다 / **When** `POST /api/orders/producer/harvest-start {productId, stageId}`를 보낸다 / **Then** `Idempotency-Key`가 없으면 400, 다른 농가 상품·그 상품 것이 아닌 기간은 404이고 아무것도 바뀌지 않는다. 같은 키·본문 재시도는 첫 응답 `{changed, stageId, orderIds}` 그대로이고, 옮길 주문이 없으면 200 `changed: 0`이다. 옮긴 주문이 있을 때만 감사(`orders.harvest_started`, 행위자·주문 id)를 한 행 남긴다. `stageId`가 없으면 상품 전체(이전 호환)

### I2 생산자 오류 복구 (DEV-29/34/38)

출하 요청 중에는 확인창 닫기·중복 요청·선택 변경을 막는다. 일부 요청 또는 출하 뒤 목록 갱신이 실패하면 성공한 주문은 유지하고 오류와 목록 재시도를 보여 준다. 새 조회가 실패해도 송장 입력은 유지한다.
