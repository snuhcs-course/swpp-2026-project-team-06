## 화면과 공개 계약

- 생산자 새 상품은 비공개 상품별 작업을 연다. `/products/source-analysis`는 한 화면 편집이다(DEV-184): 기본 정보(상품명·품종·사이즈·예상 당도·원산지·보관·중량 옵션)와 상세페이지(18개 모듈 직접 편집·섹션/항목 표시 제어)를 한 스크롤에 두고, 상품사진/분석 자료 두 첨부함은 화면 아래 AI 시트에 둔다. 'AI로 채우기' → 분석 → 비공개 저장('임시 저장') → '다음: 가격·판매'의 확인 후 명시적 상품 반영. 업로드 전 개인정보를 직접 가리도록 안내하며 새 자료는 가림 승인 대기를 거치지 않는다.
- 기존 파일/페이지/상품 수 제한과 권한을 유지한다. GET batches/:id/runs 및 drafts로 재진입한다. 직접 수정한 값은 PRODUCER로 기록한다.
- POST runs의 visualPages는 source ID별 이미지 페이지 번호이며 기본값은 빈 값이다. 최신 앱은 자료를 자동 분석하며 상품사진 자체는 OCR/vision에 보내지 않고 한 줄 설명만 배치 분류에 사용한다. 이전 가림본/버전 보호는 유지한다.
- 동일 자료 revision·가림버전·모델·prompt·대상·시각 선택의 성공 결과는 재사용한다. 취소/재분석으로 생산자 편집을 덮어쓰지 않는다.
- POST batches/:bid/drafts/:did/apply는 productId/productVersion/draftVersion 및 Idempotency-Key를 받는다. 소유권과 최신 batch/review/source/product 버전을 검사한다.
- Product.moduleDetail(schemaVersion=1, modules)을 별도로 저장한다. 기존 detailContent는 보존하며 새 모듈 없는 상품은 기존 렌더러를 사용한다. 가격·재고·주문·상품 공개 상태는 바꾸지 않는다.
- 상품사진은 EXIF 없는 PNG로 준비하며(비공개 분석 사본) 명시적 반영 시 독립 공개 사진으로 복사한다. 공개 사진은 비율을 유지한 채 긴 변 1600px 이하로 줄인 JPEG이며 EXIF 방향을 적용하고 메타데이터를 넣지 않는다(DEV-328). 판매페이지 작업 공간에서 올린 사진도 같다. 공개 응답에는 본문·공개 사진 URI·허용 일러스트만 둔다. 원본 삭제와 공개 사진 수명은 독립이다. 사진 접근은 현재 스냅샷 참조·상품 PUBLISHED·농가 승인을 검사한다. `/api/source-media/{id}`는 저장된 형식의 Content-Type(이전 공개분은 PNG)과 `Cache-Control: private, max-age=300`·ETag로 응답하고(보는 사람의 캐시만, 공유 프록시에는 남지 않음), `If-None-Match` 304도 접근 검사를 통과한 뒤에만 준다. 공개를 취소하면 이미 받아 간 사람의 캐시에서 최대 5분 뒤 사라진다. 생산자 화면에는 원본 PNG를 내려보내지 않는다(DEV-341): 자료 페이지 이미지는 가림본에서 만든 미리보기 사본으로 보여 준다. 대표사진·편집기는 `variant=display`(긴 변 1600px 이하 JPEG, 공개 사진과 같은 변환), 첨부 칸은 `variant=thumb`(짧은 변 480px 이하 JPEG)이며 상품사진은 올릴 때 함께 만든다. 주소에 자료 `revision.sanitizationVersion`(`v`)이 맞으면 `Cache-Control: private, max-age=86400`, 아니면 `private, no-cache`이고 둘 다 ETag·`Vary: Authorization`을 붙이며 304도 권한 검사 뒤에만 준다. 원본(`variant` 없음)·가림 전 이미지는 지금처럼 `no-store`이고 가림 전 이미지의 미리보기는 없다. 판매페이지 작업 사진 미리보기(`GET product-workspaces/{pid}/photos/{id}`)도 `private, max-age=86400`·ETag다. 판매페이지 작업 공간은 사진을 올리기 전에 앱이 긴 변 1600px JPEG로 줄여(웹) 보내고, 서버의 JPEG 변환은 상품 잠금 밖에서 한다.

## DEV-58 OCR 교체 후 검증 결과

- RapidOCR 3.10.0/ONNX Runtime 1.31.0, PP-OCRv5 mobile 한국어 모델로 교체했다. 명시적 오프라인 설치와 파일별 SHA-256 검증을 사용하며 런타임 자동 다운로드는 없다. 네트워크 차단 실측에서 긴 이미지2.377초/593.2MB, 보관 PDF0.849초/596.8MB였다(같은 프로세스 누적 peak RSS). 기존 두 자료의 Paddle2GB 초과 문제를 해소했고 기본 상한1GB/120초를 유지한다.
- PDF는 문자 좌표 기반 가림을 적용하고, OCR 중복을 제거한다. 줄바꿈과 공백 배치만 다른 인용은 원문의 정확한 부분 문자열로 복원한다. 문자·숫자·구두점이 바뀐 인용은 계속 거절한다.
- 실제12건 전처리와 모델 응답은 최종 회차에서 모두 성공했다. **정확일치 품질 게이트는 실패**: 텍스트 precision/recall100%/100%, 이미지18.75%/14.29%, PDF42.86%/37.5%. 띄어쓰기·구두점 차이도 오답에 포함하지만, `귤→굴` 오인식·누락·필드 분류 오류도 실제로 남아 있다. 자동 금지 필드 검사0건은 사람이 확인한 중요 오류0건을 뜻하지 않는다.

### 새 상품 한 화면 편집과 AI 시트 (DEV-184, 2026-10-31)
- 새 상품 버튼 → 중간 화면 없이 한 화면 편집. 비어 있는 새 상품이면 아래 AI 시트가 펼쳐진 상태로 열린다. 시트를 접어도 손잡이·요약 줄(상품사진 수·자료 수)과 하단 버튼은 남는다.
- 시트: 상품사진 첨부함(공개 전 대표 1장 필수, 분석에는 불필요) → 분석 자료 첨부함(텍스트·이미지·PDF·TXT) → 품종명(필수) → 'AI로 채우기'. 분석이 시작되면 시트를 접고 상세페이지 자리에 진행 안내와 자리표시(skeleton)를 보인다. 실패·일부 완료·취소·재시도 안내와 비용 확인은 시트 안에 둔다. 입력과 첨부는 실패해도 보존한다(AC-03-3).
- 2026-11-02 owner 결정(DEV-179): 생산자 편집기의 AI 출처 배지는 표시하지 않는다. 생산자가 고친 항목은 PRODUCER가 되어 재분석이 덮어쓰지 않고(AC-SRC-11 우선순위 유지). 재분석 전에 고친 상세 내용은 먼저 비공개 저장한다. 고친 상세 내용이 저장되기 전에는 첨부를 바꿀 수 없다(기본 정보는 아래 11/15 갱신). 2026-11-15 갱신(DEV-329, 농가 피드백 '키보드가 안 뜸'): 기본 정보 칸은 잠그지 않는다. 칸을 누르면 고친 상세 내용을 먼저 비공개 저장하고, 기본 정보는 그 저장이 끝난 뒤 저장한다. 대표 사진 바꾸기·'임시 저장'·'다음'·나가기도 상세 내용을 먼저 저장한다(review 버전을 올리는 저장보다 앞). 첨부(사진·자료)는 계속 잠근다. 저장 안 한 상세 수정은 생산자가 고친 칸이 서버에서 그대로이고 초안의 모듈 선택·숨김이 바뀌지 않았으면 새 버전으로 옮겨 저장한다(고치지 않은 칸은 새 서버 값, 예: 기본 정보로 다시 만든 specification·qualityEvidence). 고친 칸이 서버에서 바뀌었거나 다른 화면이 모듈 선택을 바꿨으면 지금처럼 거절한다. 이 규칙은 편집기를 쓰는 기존 2탭 작업 화면에도 같다. 옮길 때 모듈 켜기는 생산자가 고른 그대로 둔다.
- AI가 뽑은(EXTRACTED) 상품명(`name`)과 30자 이하 보관 방법(`storage`)은 상품 정보 칸이 기본값(빈 값·'새 상품')이고 생산자가 손대지 않았을 때만 미리 채우며 AI 출처 배지는 표시하지 않는다. 가격은 채우지 않는다(AC-03-1). 품종·예상 당도는 AI 입력용 기본 정보에 저장하고 상품 저장 때 상품 값에도 같이 넣는다. 저장은 기존 상품 PATCH(버전·멱등 키)를 쓴다. 서버 변경 없음.
- '임시 저장' = 기본 정보·첨부 저장 + 상품 PATCH + 비공개 초안 저장. 상품에는 아직 적용하지 않는다. 고친 상세 내용이 있으면 그것을 기본 정보보다 먼저 저장한다(DEV-329).
- (v2) '다음: 판매·가격' = 임시 저장 후, 최신 비공개 초안(현재 review·batch 버전과 일치)이 있으면 상품에 반영(apply)하고 SCR-24b `/products/:id/sell`로 간다. 판매 전(DRAFT/REJECTED) 상품은 반영해도 구매자에게 보이지 않아 확인 없이 반영하고 SCR-24b로 간다. 그 밖의 상태(판매 중·승인 대기·종료)는 상태에 맞는 확인 문구 뒤 반영하고 SCR-25로 간다. 이 상품에 마지막으로 반영한 초안(id:version)은 세션 저장소에 두어 같은 초안을 다시 반영하지 않는다. apply를 먼저 해야 이후 상품 PATCH·기간 저장과 버전이 꼬이지 않는다. 분석 전(또는 취소된 분석만 있고 초안이 없음)이면 상품 정보만 저장하고 이동한다. 분석 뒤인데 첨부가 바뀌어 최신 초안을 만들 수 없으면 이동하지 않고 다시 채우기를 안내한다.
- 새 상품 버튼은 `/products/source-analysis?batchId=…&composer=1`로 연다. `composer=1`이 없는 진입(배치 없는 상품 선택·이전 작업 이어하기, 여러 상품 작업)은 기존 2탭 화면을 그대로 쓴다. 자료 분석이 꺼진 서버의 `/products/manual` 경로(DEV-84)도 그대로다. 기존 상품의 `판매페이지 수정`은 DEV-346부터 같은 composer로 연다(아래 절).

### 판매페이지 수정 = 새 상품 화면 (DEV-346, 2026-11-16·17 PM 결정)
- 새 상품과 판매페이지 수정은 같은 화면(composer)이다. 상품 카드·SCR-25의 `판매페이지 수정`과 딥 링크 `/products/:id/detail`은 모든 상태(작성 중·반려·심사 중·판매 중·종료)에서 composer를 연다. 버튼 이름은 모든 상태에서 `판매페이지 수정`이다(11/17, '이어서 채우기'는 쓰지 않는다).
- 진입: `POST /api/source-analysis/product-workspaces {productId, composer: true}`가 상품에 묶인 자료 작업(batch)을 돌려주고, 응답 `composer: true`면 `/products/source-analysis?batchId=…&composer=1`로 바꿔 연다. `composer`를 보내지 않는 호출(기존 편집기·예전 앱)은 아래 옮기기를 하지 않고 응답에 `composer`가 없다. `composer`를 모르는 예전 서버는 400(`fields.composer`)으로 거절하고, 앱은 기존 편집기로 연다. `composer: false`(옮기지 못함)·자료 분석이 꺼진 서버·Mock은 기존 편집기를 연다. 여는 요청이 서버 오류(5xx·예상 밖 4xx)로 실패하면 '판매페이지를 열지 못했어요. 다시 시도해 주세요.'와 함께 '다시 열기'·'기존 편집기로 열기'를, 연결 실패면 '다시 열기'만 보인다. '기존 편집기로 열기' 아래에 '새 화면에 저장한 수정은 기존 편집기에 보이지 않아요'.
- composer 밖에서 만든 페이지(시드·직접 입력·composer 이전 상품·기존 편집기로 고친 상품)는 composer로 열 때 지금 페이지 그대로 batch 초안으로 옮긴다(11/17 '그냥 옮겨라'). 상품 잠금 안에서 판단하고, 같은 상태로 다시 열면 아무것도 하지 않는다(멱등). 규칙:
  - 기존 편집기에 반영 안 한 수정본이 있으면 그 수정본을 옮긴다(아래). 단 옮기면 사라질 composer 작업이 있으면(진행 중인 분석, 초안 없는 검토 값, 페이지와 마지막으로 맞춘 초안보다 새 초안) 옮기지 않고(응답 `composerBlocked: "LEGACY_REVISION"`) 기존 편집기로 열어 그 수정본을 거기서 반영하거나 버리게 한다. 이때 기존 편집기 위에 '새 화면에 저장한 수정이 있어요. 여기서 반영하면 그 수정은 사라져요.'를 보인다(반영하면 다음 composer 열기에서 페이지가 이긴다). 수정본 뒤 상품 버전이 바뀌었으면, 수정본의 사진이 지금 기존 편집기가 받는 사진(상품 사진·이 상품 공개 사진·지금 공개 페이지 사진)이고 대표사진을 바꾸지 않은 경우만 지금 대표사진으로 옮기고, 그 밖에는 기존 편집기(버전 충돌 안내). 상품에 사진이 하나도 없으면 옮겨 온 대표사진을 비운다.
  - 초안이 없으면: 페이지·사진·설명이 하나도 없으면 그대로 연다. 초안 없이 검토 값이 있거나 분석이 진행 중인 batch는 아래 '예외'를 따른다. 그 밖에는 옮긴다.
  - 다른 화면에서 반영한 페이지로 다시 옮길 때 진행 중인 분석(개인정보 확인 대기 포함)은, 페이지가 composer 칸에 들어가는 것이 확인된 뒤 옮기기 직전에 취소하고 품종·당도를 상품 값으로 맞춘다(칸에 안 들어가 기존 편집기로 열면 분석은 그대로). 다른 상품도 함께 분석하는 batch(대상 둘 이상)면 취소하지 않고 기존 편집기로 연다. 그 전 composer 임시 저장(마지막으로 맞춘 초안보다 내용이 다른 새 초안, 같은 내용으로 다시 저장한 것은 아님)이 있었거나 분석을 취소했으면 응답 `composerNotice`(`PAGE_REPLACED` / `PAGE_AND_AI_REPLACED`)를 주고, composer 위에 '다른 화면에서 반영한 판매페이지로 새로 불러왔어요. 이전 임시 저장은 반영되지 않았어요.'(분석을 취소했으면 '… 이전 임시 저장과 진행 중이던 AI 작업은 반영되지 않았어요.')를 한 번 보인다. 지문 기록이 없는 예전 상품은 임시 저장이 있었는지 알 수 없어 분석을 취소한 경우만 알린다. 판매 중·승인 대기·종료 상품의 composer 반영(workspace 자기 batch)은 지문이 기록돼 있고 그 사이 페이지가 바뀌었으면(지문이 다름, 설명 페이지 예외) 409 `PAGE_CHANGED` '판매페이지가 바뀌었어요. 다시 열어 주세요.' + '다시 열기'(판매페이지 수정으로 다시 열기)로 거절한다. 판매 전(DRAFT·REJECTED) 상품의 반영은 DEV-346 이전처럼 지문 확인 없이 상품·초안 버전과 대표사진만 확인한다(다음 composer 열기에서 바뀐 페이지로 다시 옮긴다). '이 상품에 이미 반영한 초안' 기억(DEV-184, 같은 초안을 두 번 반영해 사진이 다시 복사되지 않게)은 그대로 둔다: 다시 옮기면 초안 id가 새로 생긴다.
  - 초안이 있으면: 초안이 마지막으로 맞춘 페이지 지문(`source_product_workspaces.page_source`, 옮길 때와 composer 반영 때 기록)과 지금 이야기(모듈 → 블록 → 설명 순)가 같으면 그대로 연다. 다르면(기존 편집기·예전 앱으로 반영됨) 지금 페이지로 다시 옮긴다: 구매자에게 보이는 페이지가 이기고, 그 뒤 composer에 저장만 해 둔 수정은 이전 초안 기록에만 남는다.
  - 지문이 없는 예전 초안(DEV-346 전 composer 상품): 공개 페이지가 비었으면 그대로, 초안 중 하나라도 글이 공개 모듈 글과 같으면(composer로 반영한 초안, 그 뒤 초안은 비공개 작업) 지문을 기록하고 그대로. 다르면 판매 전(DRAFT·REJECTED)이고 페이지가 설명·사진뿐이면 composer 초안을 두고, 그 밖(판매 중·승인 대기·종료, 또는 기존 편집기로 반영한 모듈·블록 페이지)은 페이지로 다시 옮긴다.
  - 대표사진만 바뀐 것(SCR-25 사진 순서)은 지문에 넣지 않는다. 구매자에게 보이는 상품의 대표사진은 composer에서 바꾸지 않고(잠금, 아래) 반영도 대표사진을 건드리지 않는다.
  - 설명만 있는 페이지에서 지문을 기록한 뒤 composer 작업을 저장했거나 분석이 진행 중일 때 SCR-25에서 설명만 고쳤으면 초안을 두고 분석도 그대로 둔다(반영하면 composer 초안이 설명 이야기를 대신하므로). 모듈·블록 페이지가 composer 밖에서 바뀐 것은 늘 다시 옮긴다.
  - 알려진 동작: 여러 상품을 함께 분석하는 batch(대상 둘 이상)에서 분석이 진행 중일 때 페이지가 바뀌었으면 따로 안내 없이 기존 편집기로 연다(드물고 잃는 데이터 없음).
  - 예외: 초안 없이 검토 값이 있거나 분석이 진행 중인 batch에(끝나거나 취소된 분석만 있으면 해당 없음) 예전 페이지가 있으면 판매 중·승인 대기·종료는 계속 기존 편집기로 연다(composer가 그 페이지를 보여 줄 수 없음). 판매 전은 페이지가 설명·사진뿐이면 composer로 연다(구매자에게 안 보이고 composer 반영이 지우지 않음). 모듈·블록 페이지가 있으면 기존 편집기.
  - 다른 자료 작업(여러 상품 2탭 화면)의 초안을 반영하면 지문을 기록하지 않아, 다음 composer 열기에서 다시 옮긴다.
  - 지운 workspace batch는 새 batch로 바꿔 옮긴다.
- 옮기는 내용:
  - 사진은 복사하지 않고 상품 페이지가 쓰던 주소(`/api/source-media/…`, 앱 사진 `/photos/…`, https)를 그대로 가리키는 사진 자료(`source_assets.product_photo`)로 둔다. 바이트·쪽·분석이 없고, AI 분석 대상과 상품 연결 바꾸기에서 빠진다. 대표사진은 지금 상품 대표사진(`photos[0]`).
  - 모듈 페이지(`moduleDetail`)는 모듈마다 같은 항목 칸의 문구(같은 칸 문구가 여럿이면 빈 줄로 이음)·사진·일러스트를 생산자 확정(PRODUCER/CONFIRMED) 값으로, 켜짐·숨긴 섹션도 그대로 옮긴다.
  - 블록 페이지(`detailContent`)와 설명만 있는 페이지(구매자에게 설명이 이야기로 보임)는 `summary` 한 칸으로 옮긴다: 글 블록을 순서대로 '제목\n본문', 블록 사이 빈 줄. 사진 블록은 모두 그 칸의 사진으로. 글이 섞인 순서와 '농가 이야기' 제목은 남지 않는다.
  - 칸 하나가 3,000자나 사진 30장을 넘거나, batch 자료가 30개(업로드 한도)를 넘게 되면 자르지 않고 옮기지 않는다(`composer: false`, 기존 편집기).
  - 사진만 있고 이야기가 없는 페이지는 상품명으로 상단(hero) 모듈을 켠다(빈 초안은 반영할 수 없음).
  - 기존 편집기에 반영 안 한 수정본이 있으면 그 수정본(생산자의 최신 페이지)을 옮기고 수정본은 비운다. 그래서 composer 반영을 막던 `PAGE_DRAFT_EXISTS`가 생기지 않고, 구매자 화면은 반영 전까지 그대로다.
  - 옮긴 문구는 금액·효능 검사로 거절하지 않는다(이미 공개된 문구를 잃지 않게). 생산자가 composer에서 다시 저장할 때 기존 규칙대로 칸별 오류가 뜬다.
  - 손대지 않은 초안을 반영하면 구매자 페이지의 문구·사진 주소·대표사진이 그대로다(블록·설명 페이지는 위 규칙의 `summary` 모듈이 된다). 반영할 때 옮긴 `/api/source-media/` 사진(상대·절대 주소)은 그 상품의 공개 사진일 때만 받는다.
- 품종·사이즈·예상 당도(기본 정보): 판매 전(DRAFT·REJECTED)은 batch가 원본이라 열 때 바꾸지 않는다(composer가 먼저 batch에 저장하고 상품에는 임시 저장·다음 때 넣음, 분석도 batch에 채움). 판매 중·승인 대기·종료는 composer에서 품종·당도를 고치지 않으므로(잠금) 열 때 batch의 품종·예상 당도를 상품 값으로 맞춘다(AI 분석 입력용, 사이즈는 그대로). 분석이 진행 중이면 맞추지 않는다(다시 옮기며 분석을 취소하면 그때 맞춤). 값이 실제로 바뀐 때만 손대지 않은 품종·당도 제안을 다시 만든다.

- 판매 중·승인 대기·종료 상품(구매자에게 보이는 상품, 11/17 PM 결정): composer에서는 판매페이지(상세)만 고친다. 상품명·원산지·보관·품종·당도·대표사진은 잠그고 상품의 지금 값(당도는 측정값 먼저)을 보이며, 상품 편집(SCR-25)에서만 고친다(composer와 상품이 서로 다른 값을 들고 있다 맞추던 동기화가 계속 새 버그를 만들어서). 잠긴 칸이나 대표사진을 누르면 시트 '상품명·원산지·보관·품종·당도·대표사진은 상품 편집에서 바꿔요' + '상품 편집으로 가기'(`/products/:id/edit`). 상품명 칸 아래에도 같은 안내. 사이즈 칸은 composer 전용이라 그대로 고칠 수 있다. 주 버튼 '상품에 반영' → 확인 시트(판매 중 '판매 중인 상품이라 상세페이지가 구매자에게 바로 보여요. 가격·재고와 대표사진은 바뀌지 않아요.') → '반영하고 다음으로' → SCR-25. 반영은 상세(`module_detail`)만 바꾸고 상품 PATCH를 하지 않으며 대표사진·사진 순서도 그대로다. '임시 저장'·나가기는 비공개 초안·사이즈만 저장한다('비공개로 저장했어요. '상품에 반영'을 누르기 전까지 구매자 화면은 그대로예요.'). 판매 전(DRAFT·REJECTED) 상품은 지금처럼 모든 칸을 고치고 '다음: 판매·가격'(확인 없이 반영 → SCR-24b).

### 상품 하나를 한 화면에서 고치고 한 번에 반영 (DEV-361, 2026-11-17 PM 결정) — 서버·API
- composer('상품 수정')가 상품의 유일한 편집기가 된다. 이 절은 서버 계약(PR B)이고, 화면(잠금 제거, 판매 조건 시트, 반영 확인 시트)은 후속 PR에서 붙인다. 위 DEV-346 절의 잠금·'상품 편집으로 가기'는 그 화면 PR까지 그대로다.
- 대상: 구매자에게 보이는 상품 중 판매 중(PUBLISHED)·승인 대기(PENDING_APPROVAL). 상품 칸(상품명, 사진, 품종, 설명, 등급, 예상·측정 당도, 상품정보 원산지·보관 등)과 판매 조건(중량 옵션, 기간·가격·박스, 배송비·도서산간 운임, 전액 환불 날짜, 받는 시기)을 비공개 상품 초안(`source_product_workspaces.product_draft`)에 두고 '상품에 반영' 전까지 구매자 화면과 상품 칼럼을 바꾸지 않는다. 판매 전(DRAFT·REJECTED)은 지금처럼 저장하면 바로 상품에 들어가고(PATCH·PUT stages) 상품 초안은 409 `INVALID_TRANSITION`. 판매 종료(CLOSED)는 지금처럼 고칠 수 없다(초안 저장·반영 409 `INVALID_TRANSITION`).
- 초안에 없는 것: 한 주문 최대 박스·판매 한도·판매 중지(물량·판매 설정, 바로 적용), 공급 물량 신청(운영자 승인). 판매페이지(상세)·대표사진은 composer batch 초안이다.
- 충돌은 칸 단위다: 초안에 든 칸마다 처음 담을 때의 상품 값(기준값)을 기억하고, 반영 때 지금 상품 값이 기준값과 다르고 초안 값과도 다르면 409 `PRODUCT_CHANGED`(`details.fields`). 판매 설정·물량 신청은 product.version만 올리므로 초안을 깨지 않는다. 같은 칸을 다시 저장해도 기준값은 그대로라 충돌이 남는다. 생산자가 바뀐 값을 확인하면 저장 본문 `rebase`에 그 칸을 넣어 지금 상품 값을 새 기준값으로 삼는다(초안 값을 지킴). 초안에서 그 칸을 빼면 다른 곳의 값이 남는다.
- API(승인 생산자, 자기 상품만, 다른 농가 404; workspace를 먼저 연다):
  - `GET /api/source-analysis/product-workspaces/{productId}/product-draft` → `{productId, version, productStatus, draft: {fields, stages, savedAt} | null, changes: {now, newOrders, consent}, reservedCount, conflicts}`. version은 workspace version이다.
  - `PUT …/product-draft {version, fields, stages?, rebase?}`(멱등 키): 초안 전체를 바꾼다(stages를 빼면 초안의 기간·가격 변경도 지워짐). fields는 `PATCH /api/products`와 같은 이름(`maxQuantityPerOrder`·`detailContent` 없음), 상품과 같은 값은 빠지고, 다 빠지면 초안이 없어진다. 새 중량 옵션도 `optionId`를 앱이 정해 넣는다(기간 가격이 그 ID를 가리킴). 비울 수 없는 칸에 null은 400. 저장 때는 모양만 검사하고 규칙 검사는 반영 때 한다(만드는 중인 초안을 저장할 수 있게).
  - `DELETE …/product-draft?version=`: 초안을 버린다.
  - `POST …/apply-all {version, page?: {draftId, draftVersion}, confirmDeliveryChange?, confirmedReservedCount?}`(멱등 키): 한 트랜잭션에서 상품 초안(PATCH·PUT stages와 같은 코드: R-18 이른 기간이 더 쌈·겹침 없음, PERIOD_LOCKED, 예약 박스 이상, 필수 칸, 마지막 기간 < 받는 시기 시작)과 판매페이지 초안(page, 대표사진 포함)을 반영하고 변경 기록 한 줄을 쓴다. 어느 하나라도 실패하면 아무것도 바뀌지 않고 초안이 남는다. 대표사진은 하나다: page를 반영할 때 판매페이지 대표사진이 상품 페이지가 이미 쓰는 사진(참조 사진)이면 photos 초안 첫 장(photos 초안이 없으면 지금 대표사진)과 같아야 하고, 다르면 409 `PHOTO_CHANGED`(다른 곳에서 바꾼 대표사진을 낡은 composer 대표사진이 덮지 않게). composer에서 새로 올린 사진이 대표사진이면(반영 때 공개 주소가 생겨 앱이 미리 알 수 없음) photos 초안 순서 앞에 들어간다. 이 사진은 처음 반영할 때만 복사해 앞에 넣고, 마지막으로 반영한 판매페이지가 같은 사진을 대표사진으로 썼으면 다시 넣지 않는다(같은 사진이 늘지 않고, 그사이 다른 곳에서 바꾼 대표사진이 남는다). page 없이 반영하면 photos 초안의 순서·삭제가 그대로 들어간다. 반영 때 지금 상품 값이 이미 초안 값과 같아진 칸은 변경으로 세지 않고, 바뀐 것이 없으면 기록도 남기지 않는다. 응답 `{productId, version, productVersion, changes, pageApplied, deliveryWindowProposed, reservedCount, changeId, product}`.
- `changes` 묶음(반영 확인 시트용, 각 줄 `{field, label, before, after}` 요약 문구): `now` 바로 보임(상품명·사진·품종·당도·설명·상품정보, 중량 옵션(옵션 이름은 기존 주문도 지금 값을 보여 주고 중량은 잠김), 반영 응답에는 바뀐 판매페이지 `page`도), `newOrders` 새 예약부터(기간·가격·박스·배송비·환불 날짜, R-25: 결제한 주문은 스냅샷 그대로), `consent` 예약자 동의 필요(받는 시기, 예약자가 있을 때만, R-21). 미리보기(GET·PUT)의 changes에는 판매페이지·page 초안의 대표사진 변경이 없어 앱이 따로 보인다.
- R-21: 받는 시기를 바꾸고 동의를 물을 예약(입금 대기·예약 완료·출하 준비)이 있으면(응답 `deliveryWindowProposed`는 이때만 참) `confirmDeliveryChange` 없이 409 `DELIVERY_CONSENT_REQUIRED`(`details.reservedCount` = 사람 수). 확인 시트에서 본 사람 수 `confirmedReservedCount`를 함께 보내면 지금 수와 다를 때 다시 409. 확인하면 기존처럼 그 주문들에 새 기간을 제안한다(소비자는 동의 또는 전액 환불).
- 승인 대기 상품의 반영은 다시 승인받지 않는다: 상태·심사 중 신청은 그대로이고, 운영자는 변경 기록을 본다. 심사 중에 담아 둔 초안이 반려·철회로 판매 전이 된 상품에 남으면 그 초안은 반영(직접 저장과 같음, 반려는 작성 중으로)하거나 버릴 수 있고 새로 저장하지는 않는다(그 칸이 직접 저장으로 바뀌어 `PRODUCT_CHANGED`면 남은 수정을 버린다). 직접 PATCH·PUT stages의 승인 대기 거절(409)은 그대로다(예전 앱·e2e 호환).
- 기존 엔드포인트(`PATCH /api/products`, `PUT …/stages`, `POST …/product-workspaces/{pid}/apply`, `POST /batches/{bid}/drafts/{did}/apply`)는 그대로 둔다. 판매 중 상품을 직접 고치면 초안의 같은 칸은 반영 때 충돌로 잡힌다.
- 변경 기록 `product_change_events`(apply-all 한 번마다 한 줄, 예전 판매페이지만 반영 경로 `POST …/product-workspaces/{pid}/apply`·`POST /batches/{bid}/drafts/{did}/apply`도 판매 중·승인 대기 상품의 페이지·사진이 실제로 바뀌면 '판매페이지' 줄과 사진 줄). 칸: 상품, 반영한 사람, 시각, 반영 당시 상태, 칸별 전·후 요약, 판매페이지 변경 여부, 받는 시기 제안 여부·사람 수). 사진 주소 같은 원값은 넣지 않는다. 운영자 `GET /admin/products/{productId}/changes?limit=` 최신순, `GET /admin/capacity-requests` 각 줄 `changesSinceRequest`(신청부터 결정까지, 심사 중이면 지금까지 반영 횟수). 관리자 웹 공급 물량 카드에 '신청 뒤 변경 N번'(결정된 신청은 '심사 중 변경')과 '변경 기록 보기'(같은 기간의 기록, 최근 50건 안에서).

- 후보 수만으로 conflict를 정하지 않는다. specification(규격·원산지), composition(구성·중량), pieceCount(개수), qualityEvidence의 당도 등 **같은 사실**의 정규화 값이 다른 경우 선택기를 보인다. 현재 정리 결과가 없고 안전한 원문 서술 후보가 여러 개면 선택할 수 있게 유지한다. kg/g·12.0/12 당도·유니코드·공백 차이는 같은 값으로 보고 규격의 품종과 사이즈 같은 보완 정보는 충돌로 만들지 않는다. summary/farmStory 등 병합된 정리 서술은 ready/UNREVIEWED로 자동 저장한다. outdated와 생산자 확정/제외를 덮지 않으며 현재 refined/basicInfo 값도 선택할 수 있다. 정리 성공이 생략한 필드는 원문으로 되살리지 않는다.
- run 응답의 ocrFailedPageNumbers와 chunkFailedPageNumbers는 각각 OCR/청크 실패 쪽만 정렬·중복 제거한 목록이다. 두 종류가 함께 실패하면 각각의 안내를 모두 표시한다. 개수는 기존대로 유지하고 내부 실패 코드·진단은 노출하지 않는다.
- 대표사진 없이 자료 분석이 가능하지만 sources가 0개면 시작 버튼을 비활성화하고 ‘자료를 먼저 넣어 주세요.’를 곁에 표시한다. 대표사진 공개 적용 검사는 유지한다.
- 제외 확인 저장은 localStorage `farmclub-producer:excluded-seen:${userId}:${batchId}:${targetId}`의 마지막 refinementVersion 1개를 덮어쓴다. 커밋된 구 sessionStorage `farmclub-producer:excluded-seen:${batchId}:${refinementVersion}`만 로그인 사용자가 확인된 뒤 한 번 읽어 이관/제거한다. 사용자 정보가 없으면 이관하지 않는다. 새 버전은 다시 안내하고 칩으로 다시 열 수 있다.
