# farmclub 화면 명세 (I1-P21·P22)

I1 화면 28개(소비자 앱 15, 생산자 앱 13. 로그인은 앱별로 소비자 SCR-05, 생산자 SCR-19)와 그 하위 화면의 구성·데이터·동작·예외와 API 계약을 정한다. P21 초안(제안서 기준)을 확정 스펙(`docs/spec`)과 합친 확정본이다. 동작·규칙의 원문은 기능 명세(FEAT·R·M)에 있고, 여기서는 ID로 가리킨다.

## 3. 공통 규칙

- **날짜·금액**: API는 ISO 8601(UTC 저장), 화면은 한국 시간(`Asia/Seoul`)으로 표시한다. 금액은 원 단위 정수로 주고받고 화면에 천 단위 구분을 넣는다(N-03).
- **크기**: 누르는 영역 48px 이상, 한 화면에 주요 행동 하나(N-02). 글자 단계는 본문 17, 입력칸 16, 보조 15, 메타(날짜·칩·탭·‘n명 예약’·시각) 15이고 16 밑은 보조·메타만 쓴다. 보이는 크기가 작은 버튼(사진 위 원형 40 등)도 누르는 영역은 48로 넓힌다. 그 밖의 수치는 [디자인](/docs/design/README.md) 토큰을 따른다. 레이블은 [IA 4장](./ia.md#4-내비게이션과-진입-경로)을 쓴다.
- **계정**: 소비자 앱과 생산자 앱은 계정이 따로다(결정 22, ADR 0010). 소비자 앱은 소비자 계정, 생산자 앱은 생산자 계정으로만 로그인하고, 다른 앱 계정의 토큰으로 부르면 403이다(7.1).
- **로그인 관문**: 둘러보기는 로그인 없이 된다. 팔로우·예약·채팅하기(질문하기)·좋아요를 누르거나 소식·채팅·내 정보 탭을 열면 먼저 안내 시트(로그인 / 나중에)를 띄우고, 로그인하면 소비자 로그인(SCR-05)으로 간다. 끝나면 누른 화면과 행동으로 돌아간다(FEAT-01). 예약은 옵션·수량 시트의 ‘주문서로’에서 관문을 띄우고 로그인 뒤 고른 옵션·수량 그대로 주문서(SCR-10)로 간다. 팔로우·채팅은 로그인 뒤 그 행동을 이어서 실행한다(결정 25).
- **권한 오류**: 403이면 ‘볼 수 없는 화면이에요’와 첫 화면 이동을 보여준다(공통 권한 오류 화면). 권한은 서버가 검사한다(N-06).
- **토스트**: 성공은 검정 알약 토스트로 2초 보인다. 쓰는 곳: 소식 올림, 저장, 송장 저장, 배송지 저장·삭제, 예약 취소 완료, 팔로우 해제, 링크 복사. 네트워크 오류는 공통 토스트 ‘연결이 불안정해요’와 다시 시도. 화면 안 오류 상자가 있는 곳은 토스트를 띄우지 않는다(결정 37).
- **쓰기 요청**: 성공하면 응답의 서버 값으로 화면을 갱신한다. 화면의 합계·반응 수는 미리보기이고 서버 값이 최종이다.
- **입력값 보존**: 쓰기가 실패하면(네트워크·검증·409) 사용자가 입력한 값과 고른 사진을 지우지 않는다. 로그인으로 갔다 돌아와도 유지한다.
- **중복 방지**: 처리 중에는 버튼을 잠근다. 주문 생성·결제는 `Idempotency-Key` 헤더를 보내 같은 요청이 두 번 처리되지 않게 한다(7.1).
- **목록**: cursor 페이지네이션(7.1). 다음 페이지 실패는 이미 보인 항목을 유지하고 하단에 다시 시도를 둔다.
- **이미지**: 대체 텍스트를 둔다. 불러오기 실패면 기본 이미지를 보인다.
- **테스트 표시**: I1은 결제·주문 화면과 하단에 ‘테스트 서비스’를 표시한다([정책 0장](./policy.md#0-문서-정보)).

## 4. I1 우선순위

> **팀 확인 필요.** 제안이다. Must는 S-1·S-2를 데모로 끝까지 보여주는 최소 경로이고, 나머지는 Should다. 일정이 모자라면 Should부터 덜어낸다(PRD 8장).

| 앱 | Must | Should |
| --- | --- | --- |
| 소비자 | SCR-01 홈 → SCR-03 농가 페이지 → SCR-04 상품 상세 → SCR-10 주문서 → SCR-11 결제(Mock) → SCR-12 주문 완료, 그리고 주문하려면 필요한 SCR-05 로그인 | SCR-02, 13, 14, 15, 16, 17, 18, 32 |
| 생산자 | SCR-19 로그인 → SCR-24 AI 상품 초안 → SCR-25 상품 편집 → SCR-26 예약 기간·가격·물량(게시 요청에 필요) → SCR-22 현황, 그리고 상품 승인 관리 API | SCR-20, 21, 23, 27, 28, 29, 30, 31 |

생산자 Must 경로는 시드의 승인된 생산자 계정으로 시작한다. 가입·승인 화면(SCR-20·21)이 Should여도 승인 대기·반려·정지·농가 없는 생산자 계정과 관리 API는 시드로 둔다(기술 설계 시드 데이터).

## 5. 소비자 앱

### SCR-01 홈·발견 `/`

- **관련**: FEAT-06(AC-06-4·5) · 탭: 발견(첫 화면) · 우선순위: Must
- **목적**: 시즌 상품과 농가를 둘러보고 상품·농가로 들어간다.
- **화면 요소·데이터**: 헤더(워드마크, 오른쪽 검색 아이콘), 시즌 히어로(문구, 이미지, 연결 상품), 추천 상품 카드(사진, 상품명, 농가명, 받는 시기, 지금 가격, 단계 마감 D-day, 예약한 사람 수 ‘n명 예약’), 농가 둘러보기(농가 카드: 사진, 농가명, 지역, 팔로워 수)와 ‘모두 보기’, 하단 탭.
- **입력·출력**: 입력 없음. `GET /api/home`을 그린다. 상품 카드는 `productId`, 농가 카드는 `farmId`를 넘긴다.
- **버튼 동작**: 검색 아이콘 → SCR-02(검색칸에 포커스). 히어로 → 연결 상품이 있으면 SCR-04(없으면 누를 수 없음). 상품 카드 → SCR-04. 농가 카드 → SCR-03. 모두 보기 → SCR-02.
- **빈 상태·오류**: 판매 중 상품이 없으면 ‘현재 예약 가능한 상품이 없어요’와 농가 둘러보기만. 섹션별로 불러오기 실패를 표시하고 다시 시도를 두며 다른 섹션은 유지한다. 로딩은 스켈레톤.

### SCR-02 농가 목록 `/farms`

- **관련**: FEAT-06(AC-06-1·2) · 탭: 발견 안 · 우선순위: Should
- **목적**: 승인된 농가를 마감 임박순으로 보고 검색한다.
- **화면 요소·데이터**: 검색창, 농가 카드(농가명, 지역, 대표 상품, 지금 가격, 단계 마감일). 정렬은 FEAT-06.
- **입력·출력**: 검색어(앞뒤 공백 제거, 비면 전체). `GET /api/farms?q=&cursor=&limit=`. 카드는 `farmId`를 넘긴다.
- **버튼 동작**: 농가 카드 → SCR-03. 아래로 끝까지 → 다음 cursor. 홈의 검색 아이콘으로 들어오면 검색칸에 포커스.
- **빈 상태·오류**: 검색 결과 없음 → ‘찾는 농가가 없어요’와 전체 목록으로. 불러오기 실패 → 다시 시도.

### SCR-03 농가 페이지 `/farms/:farmId`

- **관련**: FEAT-02, 06(AC-06-3), 15(AC-15-1~5), 19(AC-19-1·2), FEAT-12(AC-12-4) · 우선순위: Must
- **목적**: 농가를 알고, 판매 중 상품과 공개 소식을 보고, 팔로우하거나 채팅을 시작한다. 농가 링크의 도착점이다.
- **화면 요소·데이터**: 사진 위 뒤로·농가 링크 공유, 프로필(농가명, 지역, 소개, 대표 사진, 팔로워 수), 팔로우 버튼(팔로우 ↔ 팔로잉), 채팅하기, 최신 공개 소식 한 개, 탭 \[상품 \| 소식\](처음은 상품). 상품 탭: 판매 중 상품(상품명, 지금 가격, 받는 시기, D-day·품절, ‘n명 예약’). 소식 탭: 공개 소식 최신순(작성일, 본문, 사진·영상, 좋아요 수와 내 좋아요).
- **입력·출력**: `GET /api/farms/{farmId}`, `GET /api/messaging/farms/{farmId}/news?cursor=`. 팔로우 `PUT`/`DELETE /api/farms/{farmId}/follow`. 좋아요 `PUT`/`DELETE /api/messaging/news/{broadcastId}/reaction`.
- **버튼 동작**: 팔로우 → ‘팔로잉’(면색 + 체크, 강조색 해제). 팔로잉을 다시 누르면 확인 없이 끊고 토스트 ‘팔로우를 끊었어요’(로그인 필요, 결정 25). 채팅하기 → 팔로우하지 않았으면 ‘팔로우하고 대화를 시작해요’ 확인 후 자동 팔로우, SCR-16. 상품 → SCR-04. 좋아요 → 켬·끔, 응답의 반응 수로 갱신.
- **빈 상태·오류**: 없는 농가·승인 취소된 농가 → ‘찾을 수 없는 농가’ → SCR-02. 판매 중 상품 없음 → ‘지금 판매 중인 상품이 없어요’. 소식 없음 → ‘아직 올라온 소식이 없어요’(채팅하기는 유지).

### SCR-04 상품 상세 `/products/:productId`

- **관련**: FEAT-07(AC-07-1·2), FEAT-12 · 규칙: R-05, R-06, R-16, R-20, M-15 · 우선순위: Must
- **목적**: 품질·받는 시기·지금 가격을 보고 예약을 시작한다.
- **화면 요소·데이터**: 사진(화면 맨 위까지)과 사진 위 뒤로·농가 링크 공유, 사진 아래 ‘11월 10일~20일 도착 예정 ›’ 띠(받는 시기), 농가 요약(사진, 이름, 지역, ‘당도 기록 n회’ `brixRecordCount` → SCR-03), 상품명·품종, 지금 가격과 단계 막대(지금·다음·마지막: 가격과 날짜), 다음 단계와의 차이·단계 마감 D-day·남은 물량, 배송비(무료·별도·도서산간) 한 줄 펼침, 당도(실측 또는 ‘예상’)·등급, 농가의 한마디, 접힌 목록(상품정보·원산지 R-16, 취소 규정), 하단 고정 바(요약 한 줄 + 채팅하기 + 예약하기). ‘최신 소식’ 칸은 없다(결정 26).
- **입력·출력**: `GET /api/products/{productId}`. 예약하기 → 옵션·수량 시트(중량 옵션, 수량 1\~한 주문 최대 수량, 합계) → ‘주문서로’는 `productId`·`optionId`·`quantity`를 SCR-10에 넘긴다. 가격·물량의 최종 확인은 서버가 한다.
- **버튼 동작**: 예약하기 → 옵션·수량 시트. ‘주문서로’ → SCR-10(로그인 필요, 비로그인이면 관문 시트 후 로그인하고 고른 값 그대로 SCR-10). 농가 요약 → SCR-03. 채팅하기 → SCR-03과 같다. 공유 → 농가 링크(`shareUrl`) 휴대폰 공유.
- **빈 상태·오류**: 지금 단계가 없거나 품절 → 예약하기를 막고 ‘품절’과 다음 단계 시작일(AC-07-1). 판매 중이 아닌 상품 → ‘판매 중이 아닌 상품’ → SCR-03. 다시 열 때 가격·물량이 바뀌었으면 새 값으로 그린다.

### SCR-05 로그인 `/login` (소비자 앱)

- **관련**: FEAT-01(AC-01-1, 4~6) · 규칙: N-06 · ADR 0009, 0010 · 우선순위: Must
- **목적**: I1 소비자 테스트 계정을 골라 로그인한다(카카오 로그인은 I2).
- **화면 요소·데이터**: 닫기, 로그인이 필요한 이유 한 줄, 소비자 테스트 계정 목록(이름, ‘소비자’), ‘농가는 생산자 앱에서 따로 로그인해요’ 한 줄, 약관·개인정보 처리방침 링크, ‘테스트 서비스’ 표시. 생산자 계정은 목록에 없다.
- **입력·출력**: `GET /api/auth/test-accounts?app=consumer`로 목록, 고르면 `POST /api/auth/test-login`(`userId`, `app: consumer`) → 액세스 토큰과 사용자. 토큰은 packages/api가 앱별로 보관한다.
- **버튼 동작**: 계정 선택 → 로그인 후 누른 화면·행동으로 복귀(관문 시트에서 왔으면 그 행동을 이어서 실행).
- **빈 상태·오류**: Mock 로그인이 꺼져 있으면(404) ‘지금은 로그인할 수 없어요’. 실패하면 다시 시도. 취소(닫기) → 원래 화면, 행동 실행 안 함.

### SCR-10 주문서 `/checkout/:productId`

- **관련**: FEAT-08(AC-08-1~5), FEAT-01(AC-01-1) · 규칙: R-03, R-06, R-17, R-20, R-23 · 정책 2장 · 우선순위: Must
- **목적**: 옵션·수량·받는 곳을 확인하고 조건에 동의해 결제로 간다.
- **화면 요소·데이터**: 상품 요약(썸네일 64, 옵션·수량, 지금 단계 가격, ‘변경’ → 옵션 시트), 받는 곳(저장한 기본 배송지 요약과 ‘변경’, 없으면 ‘받는 사람과 주소 입력’ → 배송지 입력 하위 화면), 배송 메모(선택), 금액(상품 금액 + 배송비 + 도서산간 추가금 = 합계), 결제 전 동의 4개(정책 2장)와 전체 동의, 하단 바 ‘결제하기’.
- **입력**: `optionId`, `quantity`, `recipientName`, `recipientPhone`(휴대폰 형식), `postalCode`, `address`, 선택 `addressDetail`, `deliveryNote`(100자 이하), 동의 4개, `saveAddress`. 저장한 기본 배송지가 있으면 채워 두고 바꿀 수 있다(AC-08-5, `GET /api/auth/me/addresses`).
- **출력**: `POST /api/orders`(`Idempotency-Key`) → 결제 전 주문(`orderId`, `unitPrice`, `shippingFee`, `totalAmount`). 서버 합계를 보여주고 SCR-11로 간다.
- **버튼 동작**: 옵션·수량·주소 변경 → 합계 미리보기 갱신. 결제하기 → 필수값·동의 검증 후 1회 요청, 처리 중 잠금. 뒤로 → SCR-04.
- **빈 상태·오류**: 받는 곳이 없으면 결제하기를 끄고 ‘받는 곳을 입력하면 결제할 수 있어요’. 동의 누락 → 넘어가지 않음(AC-08-1). 409(단계가 바뀜·품절·수량 초과) → 서버 최신 가격·물량으로 다시 그리고 입력값은 유지, 다시 확인받음. 네트워크 오류 → 입력 유지, 다시 시도.

#### SCR-10 하위: 배송지 입력 `/checkout/:productId/address`

- **목적**: 받는 사람과 주소를 직접 입력한다(전체 화면, 닫기 X).
- **화면 요소·데이터**: 받는 사람, 연락처, 우편번호, 주소, 상세 주소, ‘기본 배송지로 저장’, 하단 ‘이 주소로 받기’. I1은 직접 입력이고 ‘우편번호 찾기’는 없다(결정 27).
- **입력·출력**: 필드 검증은 SCR-10과 같다. ‘이 주소로 받기’ → 값을 SCR-10에 채우고 돌아간다. ‘기본 배송지로 저장’이면 주문 때 `saveAddress`.
- **빈 상태·오류**: 필드 아래 형식 오류. 닫기 → 입력 버리고 SCR-10.

### SCR-11 결제(Mock) `/checkout/:productId/pay?orderId=`

- **관련**: FEAT-09(AC-09-1~3) · 규칙: R-01, R-02, R-06, R-13, R-17 · 우선순위: Must
- **목적**: 주문 금액을 카드로 한 번에 낸다(I1 Mock).
- **화면 요소·데이터**: 결제 금액, 카드 결제(Mock) 버튼, 데모용 성공·실패 선택, ‘테스트 서비스’ 표시.
- **입력·출력**: `POST /api/orders/{orderId}/pay`(`Idempotency-Key`, `mockResult`: `success`·`fail`) → 성공이면 주문이 예약 완료, 실패면 사유.
- **버튼 동작**: 결제 → 1회 요청, 처리 중 잠금. 성공 → SCR-12. 실패 → 사유와 다시 시도 또는 SCR-10.
- **빈 상태·오류**: 결제 순간 물량 0(409) → 실패 처리, 품절 안내, SCR-10으로(AC-09-1). 응답을 못 받으면 같은 `Idempotency-Key`로 다시 보낸다(AC-09-3).

### SCR-12 주문 완료 `/me/orders/:orderId/done`

- **관련**: FEAT-09, FEAT-06 · 우선순위: Must
- **목적**: 예약이 끝났음을 확인하고 팔로우·소식·채팅으로 이어간다.
- **화면 요소·데이터**: ‘예약 완료’, 주문 번호(복사), 상품·옵션·수량·합계, 받는 시기, 배송지 요약, 농가 팔로우 권유(이미 팔로우했으면 숨김), 소식 보기·채팅하기·주문 내역 보기.
- **입력·출력**: `GET /api/orders/{orderId}`로 최신 상태를 다시 읽는다.
- **버튼 동작**: 팔로우 → 켬. 소식 보기 → 그 농가 SCR-03 소식 탭. 채팅하기 → SCR-16. 주문 내역 → SCR-13. 홈으로 → SCR-01.
- **빈 상태·오류**: 결제 성공 뒤 상세 조회만 실패하면 완료 화면을 유지하고 다시 시도. `orderId`가 없으면 이 화면으로 오지 않는다.

### SCR-13 주문 내역 `/me/orders`

- **관련**: FEAT-10(AC-10-1) · 진입: 내 정보(SCR-17) · 우선순위: Should
- **목적**: 내 주문의 진행을 보고 할 일이 있는 주문을 찾는다.
- **화면 요소·데이터**: 주문 카드(상품, 상태, 받는 시기, 합계). 할 일 있는 주문(배송 기간 변경 동의, 구매 확정)이 먼저, 그다음 최신순.
- **입력·출력**: `GET /api/orders?cursor=&limit=`.
- **버튼 동작**: 카드 → SCR-14. 다음 페이지.
- **빈 상태·오류**: 주문 없음 → ‘아직 예약한 상품이 없어요’와 홈으로. 실패 → 다시 시도.

### SCR-14 주문 상세 `/me/orders/:orderId`

- **관련**: FEAT-10(AC-10-1~3), FEAT-11(AC-11-1·2), FEAT-17(AC-17-2·5) · 규칙: R-05, R-07, R-14, R-21, R-24 · 우선순위: Should
- **목적**: 상태·받는 시기를 보고 취소·구매 확정·기간 변경 응답을 한다.
- **화면 요소·데이터**: 주문 번호·예약일, 상태 제목과 단계 막대(소비자 문구: 예약 완료 · 수확·포장 중 · 배송 중 · 배송 완료. 상태값 `RESERVED`·`PREPARING`·`SHIPPED`·`DELIVERED`는 그대로, 결정 33), 받는 시기(바뀌었으면 새 기간과 선택), 배송 중이면 ‘택배사 · 송장 번호 · 복사 · 배송 조회’, 상품(썸네일 64)·금액·받는 사람·배송 메모, 지금 할 수 있는 행동, 환불이면 사유.
- **입력·출력**: `GET /api/orders/{orderId}`(`carrier`, `trackingNumber` 포함). 취소 `POST /api/orders/{orderId}/cancel`, 구매 확정 `POST /api/orders/{orderId}/confirm`, 기간 변경 응답 `POST /api/orders/{orderId}/delivery-window-response`.
- **버튼 동작**: 취소 → 확인 시트 → 전액 환불(예약 완료·출하 준비만), 토스트 ‘예약을 취소했어요’. 구매 확정 → 배송 완료 후. 새 기간 동의 / 전액 환불 → 기록. 복사 → 송장 번호 복사. 배송 조회 → 택배사 조회 페이지를 새 창으로(택배사별 조회 주소는 앱이 둔다).
- **빈 상태·오류**: 남의 주문 주소 → SCR-13. 409(이미 상태가 바뀜) → 최신 상태로 다시 그림. 배송 중 이후에는 취소 버튼이 없다(AC-11-2). 송장 번호가 없으면 택배사만, 배송 조회는 숨긴다. 결제 이력 주문은 ‘주문 문제 문의’ → SCR-32와 해당 농가 1:1 채팅을 제공한다.

### SCR-15 1:1 채팅 목록 `/chats`

- **관련**: FEAT-12, FEAT-13 · 탭: 1:1 채팅(첫 화면) · 규칙: M-02, M-04 · 우선순위: Should
- **목적**: 농가와의 1:1 채팅을 고른다.
- **화면 요소·데이터**: 채팅 카드(농가명, 마지막 질문·답 앞부분, 시각, 안 읽음, AI 안내 여부). 팔로우 중이거나 본인 결제 주문 문의가 있는 농가, 최근 순. 일반 대화는 재팔로우하면 이전 기록이 보인다. 농가 소식은 여기 나오지 않는다(AC-12-5).
- **입력·출력**: `GET /api/messaging/chats?cursor=&limit=`.
- **버튼 동작**: 카드 → SCR-16.
- **빈 상태·오류**: 채팅 없음 → ‘농가에 궁금한 점을 물어보세요’와 농가 둘러보기(SCR-02). 실패 → 다시 시도.

### SCR-16 농가 1:1 채팅 `/chats/:farmId`

- **관련**: FEAT-12(AC-12-1·2·4·5), FEAT-13(AC-13-1~4, AC-13-5는 I2) · 규칙: M-02, M-04~M-09, M-15, M-16, M-18, N-04 · 우선순위: Should
- **목적**: 농가에 질문한다. 농가 AI ON·방 AUTO에서만 AI가 답하며 HUMAN/OFF이면 직접 답변 대기. 결제 주문 문의는 팔로우 예외를 적용한다. 활성 화면 2초 갱신·읽음 처리는 계약 4장을 따른다.
- **화면 요소·데이터**: 농가 헤더(→ SCR-03), 시간순 타임라인(내 질문, AI 안내 배지가 붙은 답과 근거 요약, 농가 답, ‘농가에 전달했어요’ 상태), 입력창(글, 사진 최대 3장), 보내기. 처음이면 ‘팔로우하고 대화를 시작해요’ 한 줄.
- **입력**: `text`(1,000자 이하), `attachmentIds`(최대 3개), 주문 문맥 `orderId`. 본문·사진 중 하나 필수. 업로드는 비공개 첨부 API.
- **출력**: 들어오면 `GET /api/messaging/chats/{farmId}/messages?cursor=`(대화는 농가·소비자당 1개라 `farmId`로 찾는다). 보내기 `POST /api/messaging/chats/{farmId}/messages` → 저장된 질문(연락처 가림)과 AI 안내 또는 전달 상태(`handoffStatus`). 직접 응대/AI OFF에서는 `reply=null`. 자동 팔로우는 여기서 하지 않고 SCR-03·04·18의 채팅하기·질문하기가 `POST /api/messaging/chats`로 한다.
- **버튼 동작**: 보내기 → 1회, 처리 중 잠금. AI 안내는 등록된 정보로만 답하고, 근거가 없거나 전달 주제면 ‘농가에 전달했어요’(M-06·M-07). 위로 → 이전 cursor. ‘틀렸어요’ 버튼은 I1에 없다(M-17, I2).
- **빈 상태·오류**: 아직 질문이 없으면 ‘궁금한 점을 물어보세요’. 본인 결제 주문 문의 예외 없이 팔로우하지 않은 농가의 채팅 주소로 바로 들어오면(403) 그 농가 SCR-03으로 보낸다(IA 5장 예외 경로). 보내기 실패 → 입력창에 글·사진 유지, 다시 보내기. AI 실패·시간 초과 → 전달로 처리(N-04). 불러오기 실패 → 이미 보인 것을 유지하고 다시 시도.

### SCR-17 내 정보 `/me`

- **관련**: FEAT-06(AC-06-3), FEAT-08(AC-08-5), FEAT-10, FEAT-01(AC-01-7) · 탭: 내 정보 · 우선순위: Should
- **목적**: 팔로우·주문·배송지를 관리하고, 농가를 열려면 생산자 앱 가입으로 간다.
- **화면 요소·데이터**: 프로필(이름, 테스트 계정 · 소비자), 주문 내역(→ SCR-13, 할 일 있는 주문 수), 팔로우한 농가 목록, 설정(배송지 관리 → 하위 화면, 농가로 시작하기, 로그아웃).
- **입력·출력**: `GET /api/auth/me`, `GET /api/farms/following`.
- **버튼 동작**: 주문 내역 → SCR-13. 팔로우한 농가 → SCR-03. 배송지 관리 → `/me/addresses`. 농가로 시작하기 → 시트 ‘생산자 앱은 따로 가입해요’(소비자 계정으로는 농가를 열 수 없고, 생산자 앱 가입 신청이 생산자 계정을 따로 만든다는 안내) → ‘생산자 앱에서 가입하기’ → 생산자 앱 SCR-19(가입 신청 링크). 로그아웃 → 토큰 삭제, SCR-01.
- **빈 상태·오류**: 팔로우 없음 → ‘팔로우한 농가가 없어요’와 농가 둘러보기.

#### SCR-17 하위: 배송지 관리 `/me/addresses`

- **목적**: 저장한 배송지를 보고 고치거나 지운다(결정 28). 작업 화면이라 탭 바를 숨긴다.
- **화면 요소·데이터**: 배송지 카드(받는 사람·연락처·주소, 기본 표시, 수정·삭제, ‘기본으로’), 새 배송지 추가(배송지 입력과 같은 화면).
- **입력·출력**: `GET`·`POST`·`PATCH`·`DELETE /api/auth/me/addresses`.
- **버튼 동작**: 수정 → 배송지 입력 화면(값 채움). 삭제 → 확인 시트 → 지움, 토스트. 기본으로 → `PATCH`(`isDefault`). 저장 → 토스트 ‘저장했어요’.
- **빈 상태·오류**: 배송지 없음 → ‘저장한 배송지가 없어요’와 추가. 저장 실패 → 입력 유지.

### SCR-18 소식방 `/news`

- **관련**: FEAT-12·15, M-19 · 탭: 소식 · Should.
- **목적·화면**: 농가 아바타·이름·마지막으로 볼 수 있는 메시지·시각의 방 목록. `/news/:farmId` 하위 화면은 작은 농가 헤더, 날짜 구분, 말풍선, 사진·영상, 좋아요, 하단 답장 입력창. 소비자에게 다른 소비자 답장은 보이지 않는다.
- **입출력**: `GET /api/messaging/rooms`, `GET/POST /api/messaging/rooms/{farmId}/messages`. 사진 소식은 기존 news API와 같은 방송이다. 상세 계약 4장.
- **동작**: 답장 → 본인과 농가만 보는 텍스트. ‘1:1 채팅’ → SCR-16. 반응은 방송에만 가능. 활성 화면 갱신·이전 메시지 보기는 공통 계약을 따른다.
- **빈 상태·오류**: 농가 없음 → 둘러보기, 메시지 없음 → 첫 소식 안내, 실패 → 글을 유지하고 재시도. 팔로우 해제 시 방 접근 종료.

## 6. 생산자 앱

모든 화면은 생산자 앱이고 생산자 계정으로만 쓴다(결정 22). SCR-19·20·21과 정지 안내 외에는 승인된 생산자만 열린다(AC-01-3).

### SCR-19 로그인 `/login` (생산자 앱)

- **관련**: FEAT-01(AC-01-3~6) · 규칙: R-22, R-24, N-06 · ADR 0009, 0010 · 우선순위: Must
- **목적**: I1 생산자 테스트 계정을 골라 로그인하거나, 처음이면 농가로 가입 신청한다.
- **화면 요소·데이터**: 워드마크 ‘농가용’, 생산자 테스트 계정 목록(이름, 농가명 · 상태: 승인됨·확인 중·반려됨·정지됨·아직 농가 등록 안 함), ‘생산자 테스트 계정만 보여요’ 한 줄, ‘처음이세요? 농가로 가입 신청 ›’, 약관·개인정보 처리방침 링크, ‘테스트 서비스’, 하단 ‘○○으로 시작하기’. 소비자 계정은 목록에 없다.
- **입력·출력**: `GET /api/auth/test-accounts?app=producer`, 고르면 `POST /api/auth/test-login`(`userId`, `app: producer`) → 토큰과 사용자(농가 상태).
- **버튼 동작**: 시작하기 → 상태에 따라 농가 없음 → SCR-20, 확인 중·반려 → SCR-21, 승인 → SCR-22, 정지 → 정지 안내 `/suspended`. 농가로 가입 신청 → SCR-20(I1은 ‘신규 생산자’ 계정으로 로그인해 신청한다. I2는 카카오로 생산자 계정을 만들며 신청).
- **빈 상태·오류**: Mock 로그인이 꺼져 있으면(404) ‘지금은 로그인할 수 없어요’. 실패하면 다시 시도.

#### SCR-19 하위: 정지 안내 `/suspended`

- **목적**: 정지된 생산자에게 사유와 처리 결과를 알린다(R-24).
- **화면 요소·데이터**: 농가명, ‘계정이 정지됐어요’, 사유와 날짜, ‘판매 중이던 상품은 내려졌고 예약한 소비자에게는 전액 환불돼요’, 운영팀 문의 안내, 로그아웃.
- **입력·출력**: `GET /api/auth/me`(농가 상태 `SUSPENDED`, 정지 사유).
- **버튼 동작**: 로그아웃 → SCR-19. 다른 생산자 화면 주소로 가도 여기로 온다.

### SCR-20 가입 신청 `/apply`

- **관련**: FEAT-01(AC-01-7) · 규칙: R-22 · 정책 3장 · 우선순위: Should
- **목적**: 농가 정보를 입력해 입점을 신청한다. 신청이 생산자 계정 만들기를 겸한다(결정 22).
- **화면 요소·데이터**: ‘신청하면 생산자 계정이 함께 만들어져요. 소비자 계정과는 따로예요’ 안내, 대표자 이름, 농가 이름, 지역, 주로 키우는 것, 연락처(확인 전화를 드릴 휴대폰 번호), 확인 절차 안내(생산자 계정이 만들어지고 승인 대기 → 전화·방문 확인 → 승인), 입점 정책 동의(내용 보기), 하단 ‘신청하기’.
- **입력·출력**: 필수 5개(`ownerName`, `farmName`, `region`, `mainItems`, `phone`)와 입점 정책 동의. 연락처는 휴대폰 형식. `POST /api/auth/producer-application` → 농가(`PENDING`). SCR-21로. I1은 시드의 ‘신규 생산자’ 계정이 신청하고, 그 계정의 이름이 대표자 이름으로 바뀐다.
- **버튼 동작**: 신청하기 → 검증·동의 확인 후 1회, 잠금.
- **빈 상태·오류**: 필드별 오류, 실패 시 입력 유지. 이미 신청했으면 SCR-21. 반려 뒤 다시 신청이면 이전 값을 채운다.

### SCR-21 승인 대기 `/pending`

- **관련**: FEAT-01(AC-01-3) · 우선순위: Should
- **목적**: 신청 상태를 보고, 반려되면 다시 신청한다.
- **화면 요소·데이터**: 농가명 · 신청일, 상태(확인 중·반려), 단계(신청 완료 → 전화·방문 확인 → 승인), ‘이 화면에 들어올 때마다 확인 결과를 새로 불러와요’, 반려면 사유와 날짜, 하단 ‘신청 내용 보기’와 ‘로그아웃’(반려면 ‘다시 신청하기’).
- **입력·출력**: 들어올 때와 당겨서 새로고침할 때 `GET /api/auth/producer-application`(상태, 반려 사유, 신청 내용).
- **버튼 동작**: 신청 내용 보기 → 읽기 전용 시트(대표자 이름·농가 이름·지역·주로 키우는 것·연락처). 로그아웃 → SCR-19. 다시 신청 → SCR-20(이전 값 채움). 승인됐으면 자동으로 SCR-22.
- **빈 상태·오류**: 승인 전에는 다른 생산자 화면 주소로 가도 여기로 온다(AC-01-3). 불러오기 실패 → 마지막 상태 유지, 다시 시도.

### SCR-22 현황 `/`

- **관련**: FEAT-14(AC-14-1·2) · 탭: 현황 · 규칙: R-15 · 우선순위: Must
- **목적**: 할 일과 상품별 판매/총 한도/잔여 박스를 한눈에 본다.
- **화면 요소·데이터**: 농가 사진 띠(농가명, 오늘 날짜, 오늘 할 일 수), 할 일 세 줄(답할 질문 수, 출하할 주문 수, 승인 대기 상품 수, 숫자 22~34), 예약 수량(상품명, 예약한 사람 수·주문 수, 단계마다 옵션별 예약 박스 / 물량 막대, 지금 단계의 마감일과 남은 물량), 최근 예약(이름 앞 글자, 옵션 × 수량, 날짜, 지역, 상태), 떠 있는 ‘+ 소식’. ‘출하 처리’ 버튼은 없다(결정 30).
- **입력·출력**: `GET /api/orders/producer/dashboard`.
- **버튼 동작**: 답변 필요한 대화 → SCR-28의 답변 필요 필터. 출하할 주문 → SCR-29. 승인 대기 상품 → SCR-23. + 소식 → SCR-27.
- **빈 상태·오류**: 판매 중 상품 없음 → ‘판매 중인 상품이 없어요’와 새 상품 만들기(SCR-24). 주문 없음 → ‘아직 예약이 없어요’. 실패 → 다시 시도.

### SCR-23 상품 목록 `/products`

- **관련**: FEAT-04(AC-04-2) · 탭: 상품 · 우선순위: Should
- **목적**: 내 상품과 상태를 보고 새 상품을 만든다.
- **화면 요소·데이터**: 떠 있는 ‘+ 새 상품’, 상품 카드(썸네일 64 또는 사진 없음 자리 표시, 상품명, 상태: 초안·승인 대기·반려·판매 중·종료, 반려 사유, 재승인 대기 여부, 판매 중이면 ‘n명 예약’ `reservedCount`, 판매/총 한도/잔여 박스, 현재 예약 기간과 중지·품절 상태). 할 일 있는 상품이 먼저.
- **입력·출력**: `GET /api/products/mine?status=&cursor=`.
- **버튼 동작**: 새 상품 → SCR-24. 카드 → SCR-25.
- **빈 상태·오류**: 상품 없음 → ‘첫 상품을 등록해 보세요’와 SCR-24.

### SCR-24 AI 상품 초안 `/products/new`

- **관련**: FEAT-03(AC-03-1~3) · 규칙: M-10~M-12, N-04 · 우선순위: Must
- **목적**: 쓰던 카톡·밴드 문구를 붙여넣어 상품 초안을 만든다(파일·사진 업로드는 P2, FEAT-29).
- **화면 요소·데이터**: 문구 입력(최대 3,000자, 글자 수), 초안 만들기, 진행 표시, 결과(상품명, 품종, 중량 옵션, 예상 당도, 등급, 받는 시기, 설명)와 빈 칸 강조, ‘가격은 예약 기간별로 정해요’ 안내, 편집으로.
- **입력·출력**: `POST /api/products/drafts`(`inputText`) → `draftId`, 추출 값, `missingFields`. 20초 안에 응답(N-04). 편집으로 → `POST /api/products`(`draftId`) → 초안 상품, SCR-25.
- **버튼 동작**: 초안 만들기 → 문구가 있을 때만, 처리 중 잠금. 편집으로 → SCR-25(값 채움). 직접 입력 → 빈 SCR-25.
- **빈 상태·오류**: 문구 없음 → 버튼 비활성. AI 실패·시간 초과 → 붙여넣은 문구를 보존하고 빈 편집 화면으로(AC-03-3). 가격이 문구에 있어도 채우지 않는다(AC-03-2).

### SCR-25 상품 편집 `/products/:id/edit`

- **관련**: FEAT-04(AC-04-1~4) · 규칙: R-16, R-18, R-20, R-21, R-23, R-25, M-13 · 우선순위: Must
- **목적**: 초안을 다듬고 게시를 요청한다.
- **화면 요소·데이터**: 상태와 반려 사유, 사진(첫 사진이 목록에서 잘려 보이는 104·64 미리보기), 기본 정보(상품명, 품종, 설명, 원산지, 보관 방법), 품질(예상·실측 당도, 등급), 중량 옵션·상품 최대 판매 박스 수·한 주문 최대 수량, 받는 시기(배송 예정 기간)와 최대 지연 기한(누르면 기간 선택 달력 시트), 배송비(무료·별도)·도서산간, 예약 기간·가격·물량 요약 줄, 판매/총 한도/잔여 요약, 판매 중지·재개, 하단 바 저장 + 게시 요청.
- **입력·출력**: `GET /api/products/mine/{productId}`, 저장 `PATCH /api/products/{productId}`, 게시 요청 `POST /api/products/{productId}/publish-request`. 판매 한도·한 주문 상한·중지는 `PUT /api/products/{productId}/sales-settings`(계약 2장).
- **버튼 동작**: 저장 → 초안 유지. 예약 기간 설정으로 → SCR-26. 게시 요청 → 필수값·단계 가격이 모두 있을 때만 활성(AC-04-1) → 승인 대기. 판매 중 가격·옵션·단계 변경은 재승인 전까지 기존 값으로 판매(R-25).
- **빈 상태·오류**: 빠진 항목 수(‘빈 칸 n개를 채우면 게시를 요청할 수 있어요’)와 칸별 오류 표시. 저장 실패 → 입력 유지. 나가기 전 저장하지 않은 변경이 있으면 확인 시트. 예약이 있는 상품의 배송 예정 기간을 바꾸면 주문자 동의·환불 안내 시트(R-21). 저장 성공 → 토스트.

### SCR-26 예약 기간·가격·물량 `/products/:id/stages`

- **관련**: FEAT-05 AC-05-1~5, R-06·18·25·26 · Must.
- **목적·화면**: 날짜 범위별 가격과 옵션 물량을 입력한다. 빈 기간 하나로 시작, 기간 추가/삭제, 날짜 선택, 옵션별 가격·박스 수, 상품 총 한도 요약, 저장. 단계 번호·프리셋·할인율 선택은 없다.
- **입출력**: 편집 상품 GET과 `PUT /api/products/{productId}/stages`(stageId, version 포함). 상세 계약 3장.
- **동작**: 날짜순 정렬, 기존 ID 유지. 이른 기간 가격은 이후보다 낮고 겹치지 않는다. 현재 판매값과 승인 대기 편집안을 구분한다.
- **빈 상태·오류**: 예약 있는 기간은 삭제·날짜·가격 변경을 막고 이유를 보여준다. 필드 오류/버전 충돌 때 입력을 유지하며 최신 값 확인 후 재저장한다.

### SCR-27 소식 올리기 `/broadcast/new`

- **관련**: FEAT-12(AC-12-2·3), FEAT-15 · 규칙: M-01, M-14, M-16 · 우선순위: Should
- **목적**: 팔로워에게 재배·수확 소식을 글·사진·영상으로 올린다.
- **화면 요소·데이터**: 본문, 사진(최대 5장, 장당 10MB)·영상(1개, 60초, 100MB) 첨부와 미리보기·제거, 공개 여부(공개: 농가 페이지에도 / 팔로워 전용), 받을 팔로워 수, 올리기.
- **입력·출력**: 본문이나 첨부 중 하나 이상. `POST /api/messaging/news` → `broadcastId`, 작성 시각. 연락처는 가려서 저장된다.
- **버튼 동작**: 올리기 → 1회, 성공 후 잠금 → SCR-22. 뒤로 → 쓰던 내용이 있으면 확인.
- **빈 상태·오류**: 형식·용량 오류는 파일별 사유(413). 첨부 실패 → 글은 유지하고 첨부만 다시 시도.

### SCR-28 농가 채팅 `/chats`

- **관련**: FEAT-12·13·33, M-09·19~21 · 탭: 채팅 · Should.
- **목적·화면**: 상단 소식방 / 1:1 채팅. 소식방은 자기 농가 하나와 전체 소비자 답장, 1:1은 모든 대화와 ‘전체 / 답변 필요’ 필터. 이름 앞 글자, 마지막 메시지, 시각, 안 읽음, AI/직접 응대 상태.
- **입출력**: 소식방 rooms API, `GET /api/messaging/producer/chats`. 상세 계약 4장.
- **동작**: 소식방 `/news/:farmId`, 소비자 대화 `/chats/:consumerId`. 소식 답장에서 1:1 시작 가능. AI 설정 → SCR-31.
- **빈 상태·오류**: 자기 소식방은 팔로워가 없어도 열린다. 대화 없음/답변 필요 없음 구분. 실패 시 기존 목록 유지·재시도.

#### SCR-28 하위: 1:1 채팅 `/chats/:consumerId`

- 작은 헤더(이름·AI 응답/직접 응대), 주문 요약·문제 문의, 날짜별 말풍선, AI 배지·근거, 사진, 하단 입력창.
- `GET/POST /api/messaging/producer/chats/{consumerId}/messages`; 성공한 답변은 HUMAN 전환. 입력창을 닫지 않고 계속 대화한다.
- 명시적인 AI 다시 켜기, 읽음 갱신, 지정한 전달 질문에 답하기, 문제 문의 해결/재열기는 계약 4·6장 API를 사용한다. 읽는 것만으로 해결 처리하지 않는다.
- 전송 실패 시 글·사진 유지, 권한 없는 대화는 404. 오래된 questions API는 1.1 계약으로 남지만 새 화면은 사용하지 않는다.

### SCR-29 출하 처리 `/ship`

- **관련**: FEAT-17(AC-17-2~5, AC-17-1은 I2) · 규칙: R-07, R-15, R-19 · 우선순위: Should
- **목적**: 수확을 시작하고, 보낸 주문을 골라 택배사·송장 번호와 함께 출하로 바꾼다.
- **화면 요소·데이터**: 상품별 ‘수확 시작’(썸네일 64, 예약 완료 주문 수), 세그먼트(출하 준비 n · 출하 n), 주문 줄(체크, 주문 번호, 받는 사람 실명 · 옵션 × 수량, 주소·배송 메모, ‘택배사·송장 번호 넣기 ›’ 또는 입력한 택배사·송장), ‘배송 완료는 farmclub이 확인해서 바꿔요’, 하단 바 ‘n건 골랐어요 · 송장 m건 입력’과 ‘n건 출하로 바꾸기’. 실명·주소·전화는 이 화면에서만(배송 목적, R-15).
- **입력·출력**: `GET /api/orders/producer?status=&cursor=`. 수확 시작 `POST /api/orders/producer/harvest-start`(`productId`). 출하는 고른 주문마다 `POST /api/orders/{orderId}/ship`(`carrier` 선택, `trackingNumber` 선택·50자 이하)을 반복한다(결정 32).
- **버튼 동작**: 수확 시작 → 확인 시트 → 그 상품의 예약 완료 주문이 출하 준비(AC-17-3). 줄의 송장 링크(줄 전체) → 시트: 택배사 선택(CJ대한통운·우체국택배·한진택배·롯데택배·로젠택배·기타)과 송장 번호(선택), 저장하면 그 주문을 고르고 토스트. n건 출하로 바꾸기 → 확인 시트(주문별 택배사·송장, ‘출하로 바꾸면 소비자는 더 이상 취소할 수 없어요’) → 출하, 출하일·택배사·송장 기록(AC-17-2). 배송 완료는 생산자가 바꿀 수 없다(AC-17-4).
- **빈 상태·오류**: 출하할 주문 없음 → ‘지금 보낼 주문이 없어요’와 현황으로. 여러 건 중 일부가 409(이미 바뀜·허용되지 않는 상태)면 나머지는 처리하고 ‘n건은 이미 상태가 바뀌었어요’ 뒤 최신 상태로 다시 그림. 자연어 입력·AI 주문 찾기는 I2.

### SCR-30 농가 프로필·링크 `/farm`

- **관련**: FEAT-02(AC-02-1·2), FEAT-19(AC-19-1~3) · 탭: 농가 · 우선순위: Should
- **목적**: 프로필을 고치고 농가 링크를 단골에게 보낸다.
- **화면 요소·데이터**: 농가 링크(글자 한 줄 + 복사·보내기), AI 응답 설정 → SCR-31, 프로필 미리보기(대표 사진과 ‘사진 바꾸기’, 농가명, 지역 · 팔로워 수), 항목 줄(농가 이름·지역·소개 ›), ‘소비자 앱에서 내 농가 보기 ›’, 떠 있는 ‘+ 소식’.
- **입력·출력**: `GET`·`PATCH /api/farms/me`. 링크는 응답의 `shareUrl`(`/s/farms/{farmId}`).
- **버튼 동작**: 복사 → 토스트 ‘링크를 복사했어요’. 보내기 → 휴대폰 공유 창. 항목 줄 → 하위 화면. 사진 바꾸기 → 사진 고르기 → 저장. 소비자 앱에서 내 농가 보기 → 소비자 앱 SCR-03.
- **빈 상태·오류**: 승인 전에는 링크를 보여주지 않는다.

#### SCR-30 하위: 프로필 항목 고치기 `/farm/edit/:field`

- **목적**: 농가 이름·지역·소개 중 하나만 고친다(결정 34). 작업 화면이라 탭 바를 숨긴다.
- **화면 요소·데이터**: 48 바(뒤로 + 항목 이름), 입력칸(소개는 여러 줄), 소비자 앱에 어디에 보이는지 한 줄, 하단 ‘저장’.
- **입력·출력**: `PATCH /api/farms/me`(그 필드만).
- **버튼 동작**: 저장 → 검증 후 저장, 토스트, SCR-30.
- **빈 상태·오류**: 필수값(이름·지역)이 비면 저장하지 않고 빈 칸 표시(AC-02-2). 실패 → 입력 유지.

### SCR-31 AI 응답 설정 `/farm/ai-settings`

- **관련**: FEAT-32 AC-32-1~4 · 생산자·승인 농가 · Should.
- **화면**: AI 사용 스위치, 소량 주문·예약 배송 응대 원칙, FAQ, 추가 전달 주제, 고정 전달 주제 안내, 저장, 질문 미리보기.
- **입출력**: `/api/farms/me/ai-settings` GET/PUT, `/preview` POST. 필드 제한·버전·우선순위는 계약 5장.
- **동작**: 저장 전 변경 표시, 나가기 확인. 미리보기는 답변/전달 사유·근거를 보여주고 임시 설정임을 표시한다.
- **오류**: 필드 오류·409·네트워크 실패 시 입력 유지. OFF여도 HUMAN 상태와 기존 대화는 보존한다.

### SCR-32 주문 문제 문의 `/me/orders/:orderId/inquiry`

- **관련**: FEAT-33 AC-33-1~4 · 본인 결제 이력 주문 · Should.
- **화면**: 주문 요약, 유형(파손·상태/품질·맛·기타), 설명, 선택 사진 3장, ‘보내면 농가가 직접 확인해요’, 문의 보내기.
- **입출력**: 비공개 attachments 업로드 후 `/api/orders/{orderId}/inquiries` POST. 조회·상태·사진 권한은 계약 6장.
- **동작**: 성공 시 주문 문맥을 가진 SCR-16으로. 생산자는 SCR-28에서 확인·답변·해결/재열기. 해결은 환불 승인이 아니다.
- **오류**: 미결제/타인 주문은 접수 불가. 업로드/전송 실패 시 입력 유지, 재시도는 같은 멱등 키 사용.

## 7. API

### 7.1 공통

- **기준 주소**: 서버의 `/api`(앱), `/admin`(운영자, Swagger UI), `/s`(공유 링크). 버전 접두어는 쓰지 않는다([server/spec.md](/server/spec.md)).
- **인증**: `Authorization: Bearer <액세스 토큰>`. I1 토큰은 Mock 로그인(`POST /api/auth/test-login`, `app` 필수)으로 받는다. 토큰에는 계정의 역할(`CONSUMER`·`PRODUCER`)이 들어 있다. 표의 ‘공개’는 토큰 없이 된다.
- **앱 간 토큰**: 소비자 계정과 생산자 계정은 따로다(ADR 0010). 소비자 API를 생산자 계정 토큰으로, 생산자 API를 소비자 계정 토큰으로 부르면 403 `FORBIDDEN`(`details.reason: WRONG_APP`). 앱은 이 응답을 받으면 토큰을 지우고 그 앱의 로그인으로 보낸다. 공개 API와 `GET /api/auth/me`는 두 계정 모두 된다.
- **오류 형식**: 모든 오류는 `{"code": "...", "message": "...", "details": {}}`. `message`는 화면에 그대로 보일 한국어 문구(정책 문서), `details`는 필드별 오류·최신 값 등.

  | 상태 | code | 언제 |
  | --- | --- | --- |
  | 400 | `VALIDATION_ERROR` | 입력 형식·필수값. `details.fields`에 필드별 사유 |
  | 401 | `UNAUTHENTICATED` | 토큰 없음·만료 → 로그인(SCR-05) |
  | 403 | `FORBIDDEN` | 역할·승인 상태 부족(N-06); 같은 역할의 타인 자원은 404. 다른 앱 계정의 토큰이면 `details.reason: WRONG_APP` |
  | 404 | `NOT_FOUND` | 없음. 남의 주문·대화도 404 |
  | 409 | `CONFLICT` | 상태·물량 충돌. `details.reason`: `STAGE_CHANGED`, `SOLD_OUT`, `QUANTITY_LIMIT`, `INVALID_TRANSITION`, `IDEMPOTENCY_MISMATCH`, 추가 판매·버전 reason은 계약 1장. 최신 값을 `details`에 담는다 |
  | 413 | `PAYLOAD_TOO_LARGE` | 첨부 개수·용량 초과 |
  | 5xx | `INTERNAL_ERROR` | 서버 오류. AI 실패는 오류로 돌려주지 않고 각 FEAT의 대체 동작(전달, 빈 초안)으로 처리 |

- **페이지네이션**: 목록은 `limit`(기본 20, 최대 50)과 `cursor`. 응답 `{"items": [...], "nextCursor": "..." | null}`. 정렬은 각 화면의 순서를 따른다.
- **멱등 키**: `POST /api/orders`와 `POST /api/orders/{orderId}/pay`는 `Idempotency-Key`(UUID) 헤더가 필수다. 같은 사용자·같은 키는 처음 결과를 그대로 돌려주고, 같은 키에 다른 본문이면 409 `IDEMPOTENCY_MISMATCH`. 키는 24시간 보관한다.
- **시간 제한**: AI 초안 20초, 문의 응답은 시간을 넘기면 전달(N-04).
- **개인정보**: 응답·로그에 필요한 것만(N-05). 생산자에게 배송 정보(실명·연락처·주소)는 출하 처리 목록의 배송 완료 전 주문만(R-15). 현황·채팅은 이름 앞 글자만.
- **세는 단위**: `reservedCount`는 그 상품을 예약한 사람 수(중복 없음, 화면 ‘n명 예약’), 단계·옵션별 수량은 박스(`StageAllocation.reservedCount`), 주문 수는 건(PRD 용어집).
- **택배사 코드**: `carrier`는 `CJ`(CJ대한통운), `EPOST`(우체국택배), `HANJIN`(한진택배), `LOTTE`(롯데택배), `LOGEN`(로젠택배), `ETC`(기타).
- **경로 순서**: 같은 prefix에서 고정 경로(`/mine`, `/me`, `/following`, `/drafts`, `/stage-presets`, `/producer`)를 경로 변수(`/{productId}`, `/{farmId}`, `/{orderId}`)보다 먼저 등록한다.

### 7.2 엔드포인트

I1 열: Must 화면(4장)이 쓰는 API는 Must, 나머지는 Should다. 단 Must 화면에 있어도 Should 기능으로 이어지는 좋아요·채팅 시작 API는 Should다. 운영자 API는 게시에 필요한 상품 승인만 Must다. 1.2의 신규·변경 API 우선순위는 아래 보충 표를 따른다. Should API를 쓰는 버튼은 API가 준비될 때까지 프론트에서 숨긴다.
