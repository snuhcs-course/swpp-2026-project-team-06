## 3. 공통 규칙

- **날짜·금액**: API는 ISO 8601(UTC 저장), 화면은 한국 시간(`Asia/Seoul`)으로 표시한다. 금액은 원 단위 정수로 주고받고 화면에 천 단위 구분을 넣는다(N-03). 하루 안 시각은 ‘오전 9:40’처럼 시 앞에 0을 붙이지 않고(소식방·1:1 모두), 입금 기한 같은 마감 시각만 ‘10월 19일 (일) 01:06’으로 쓴다(DEV-227).
- **빈 값**(M-24, DEV-227): 라벨과 값은 한 덩어리로 보고 값이 없으면 라벨째 뺀다(‘0명 예약’·‘마감 ’·‘배송비 ’·‘-Brix’·오늘 날짜 채우기 없음). 메타 조각은 ‘ · ’로 잇고 빈 조각은 버리며, 다 비면 줄도 없다. 문구는 아래 표 하나를 쓴다.

  | 값 | 상태 | 문구 |
  | --- | --- | --- |
  | 당도 | 실측 / 예상만 / 둘 다 없음 | ‘당도 실측 · 11.8 Brix · 10월 5일 측정’ / ‘당도 예상 12Brix · 실측 당도가 등록되면 이곳에서 확인할 수 있어요’ / ‘당도 등록 전 · 궁금하면 1:1 채팅으로 농가에 물어보세요’ |
  | 예약 수·마감(카드 메타) | n≥1·마감 / 0명·마감 / n≥1·마감 없음 / 둘 다 없음 | ‘38명 예약 · 마감 D-5’ / ‘마감 D-9’ / ‘12명 예약’ / 줄 없음 |
  | 받는 시기 | 확정 / 확정 전·예약 기간 있음 / 확정 전·예약 기간 없음 | ‘11월 10일~20일 도착 예정’(카드 ‘도착’) / ‘10월 중순 이후 도착 예상’ + ‘받는 시기는 예약 전에 확정돼요.’ / ‘받는 시기 확정 전’. 확정 전은 공개 전(생산자 미리보기)에만 생긴다(AC-04-1) |
  | 배송비 | 무료 / 별도+금액 / 별도·금액 없음 | ‘무료배송’ / ‘배송비 4,000원’ / ‘배송비 확정 전’(펼치면 ‘배송비는 확정 전이에요.’) |
  | 예약할 수 없음 | `NOT_OPEN`·`PERIOD_SOLD_OUT`·`TOTAL_SOLD_OUT`·`PAUSED`·`ENDED` | ‘예약 시작 전’·‘이번 기간 품절’·‘전체 물량 품절’·‘판매 일시 중지’·‘예약 종료’(ia.md 4장). 예약 가능 상품의 옵션 하나만 다 팔렸으면 ‘이번 기간 품절’ |
- **크기**(DEV-293 기준표, 당근 SEED 수치): 누르는 영역 48px 이상, 한 화면에 주요 행동 하나(N-02). 글자 단계는 화면 제목(탭 첫 화면)·상품명 22 굵게, 섹션 제목·하위 화면 머리 제목·시트 제목 18 굵게, 본문 16, 입력칸 16, 보조 14, 메타(날짜·칩·탭·‘n명 예약’·시각) 12, 숫자 강조 22(가격 18~20)이고 16 밑은 보조·메타만 쓴다. 버튼은 주요 52(두 앱 같음)·보조 48, 칩·작은 버튼은 32에 hitSlop으로 누르는 영역 48. 목록 행은 한 줄 56·두 줄 72, 카드 안 여백 12~16. 좌우 여백(왼쪽 시작선)은 16 하나다. 보이는 크기가 작은 버튼(사진 위 원형 40 등)도 누르는 영역은 48로 넓힌다. 그 밖의 수치는 [디자인](/docs/design/README.md) 토큰을 따른다. 레이블은 [IA 4장](./ia.md#4-내비게이션과-진입-경로)을 쓴다.
- **머리**(DEV-293): 탭 첫 화면은 높이 56에 왼쪽 22 굵은 제목(로고 머리는 기존 로고 애셋 그대로, 좌우 16). 하위 화면은 높이 56에 ‹ + 왼쪽 18 굵은 제목이고 가운데 정렬 제목은 쓰지 않는다. 부제는 두지 않는다. 안전 여백은 기존 `safe()`(DEV-33)를 그대로 쓴다.
- **문구**(DEV-293, 토스 라이팅 원칙 참고): 한 문장에 한 내용, 해요체. CTA 바로 위에 설명 문단을 두지 않는다. 제목·버튼에 마침표를 찍지 않는다. 확인 시트의 왼쪽 버튼은 ‘닫기’. 개발 용어(Mock·로컬 API)는 Mock 실행(`isMock`)에서만 보인다.
- **정렬**(DEV-293): 왼쪽 시작선 16, 아이콘·체크박스는 글과 세로 가운데, 금액은 오른쪽 정렬(tabular-nums), 섹션 제목과 오른쪽 링크는 같은 줄 가운데.
- **계정**: 소비자 앱과 생산자 앱은 계정이 따로다(결정 22, ADR 0010). 소비자 앱은 소비자 계정, 생산자 앱은 생산자 계정으로만 로그인하고, 다른 앱 계정의 토큰으로 부르면 403이다(7.1).
- **로그인 관문**: 둘러보기는 로그인 없이 된다. 팔로우·예약·채팅하기(질문하기)·좋아요를 누르거나 내 주문·채팅·내 정보 탭을 열면 먼저 안내 시트(로그인 / 나중에)를 띄우고, 로그인하면 소비자 로그인(SCR-05)으로 간다. 끝나면 누른 화면과 행동으로 돌아간다(FEAT-01). 예약은 옵션·수량 시트의 ‘주문서로’에서 관문을 띄우고 로그인 뒤 고른 옵션·수량 그대로 주문서(SCR-10)로 간다. 팔로우·채팅은 로그인 뒤 그 행동을 이어서 실행한다(결정 25).
- **스택에 남은 로그인 필요 화면 (DEV-222)**: 주문서처럼 로그인이 필요한 화면은 보일 때(처음 열 때·돌아올 때)만 로그인·온보딩으로 보낸다. 보는 중이나 다른 화면 아래에 남아 있는 동안 로그아웃·로그인 풀림으로 계정이 사라지면 이동은 세션이 맡는다: 로그아웃 → SCR-01, 401 → SCR-05(‘로그인이 풀렸어요’, 끝나면 보던 화면). 이어서 할 행동은 관문 시트에서 연 로그인만 쓰고, 직접 연 로그인(내 정보의 ‘로그인’, 로그인 풀림 등)은 남은 행동을 지운다.
- **시트에서 다른 화면으로 (DEV-225)**: 시트 안 버튼이 다른 화면으로 보내면(옵션 시트 ‘주문서로’, 관문 시트 ‘로그인’, 받는 곳 시트 ‘새 주소 입력’ 등) 시트는 닫힘 애니메이션 없이 바로 닫고 같은 순간 이동한다. 새 화면 위에 시트가 남지 않는다(창이 가려져 애니메이션이 멈춘 때도 같다). 여는 동작과 이동하지 않는 닫기는 그대로 아래로 미끄러진다.
- **뒤로·탭 첫 화면 (DEV-224)**: 하단 탭을 누르면 언제나 그 탭의 첫 화면이 열린다. 헤더 뒤로는 앱 안의 이전 화면, 이전 화면이 없으면(주소로 바로 열기·새로고침) [IA 4장](./ia.md#4-내비게이션과-진입-경로) 뒤로 규칙 표의 부모 화면으로 간다. 뒤로가 아무 데도 가지 않는 화면은 없다(앱은 `goBackOr`, `lib/backTargets.ts`).
- **권한 오류**: 403이면 ‘볼 수 없는 화면이에요’와 첫 화면 이동을 보여준다(공통 권한 오류 화면). 권한은 서버가 검사한다(N-06).
- **토스트**: 성공은 검정 알약 토스트로 2초 보인다(행동 버튼이 있는 토스트는 4초, 예: 팔로우 해제의 ‘되돌리기’, DEV-230). 쓰는 곳: 소식 올림, 저장, 송장 저장, 배송지 저장·삭제, 예약 취소 완료, 팔로우 해제(‘팔로우를 끊었어요 · 되돌리기’), 링크 복사. 네트워크 오류는 공통 토스트 ‘연결이 불안정해요’와 다시 시도. 화면 안 오류 상자가 있는 곳은 토스트를 띄우지 않는다(결정 37).
- **쓰기 요청**: 성공하면 응답의 서버 값으로 화면을 갱신한다. 화면의 합계·반응 수는 미리보기이고 서버 값이 최종이다.
- **시각 판단**: 화면의 시각 판단(입금 기한 지남 — SCR-13·14 ‘입금 확인 늦어짐’, SCR-29 ‘기한 지남’ — 과 ‘오늘·어제’ 같은 날짜 경계)은 기기 시계가 아니라 서버 시각을 기준으로 한다. 서버 시각은 응답 헤더 `X-Server-Time`(7.1)에서 얻는다. 기기 시계가 틀리거나 서버 시각을 고정한(`FIXED_NOW`) 평가·데모 환경에서도 서버의 기한 판단(R-28)과 화면 문구가 같다(DEV-229).
- **입력값 보존**: 쓰기가 실패하면(네트워크·검증·409) 사용자가 입력한 값과 고른 사진을 지우지 않는다. 로그인으로 갔다 돌아와도 유지한다.
- **중복 방지**: 처리 중에는 버튼을 잠근다. 주문 생성·결제는 `Idempotency-Key` 헤더를 보내 같은 요청이 두 번 처리되지 않게 한다(7.1).
- **목록**: cursor 페이지네이션(7.1). 다음 페이지 실패는 이미 보인 항목을 유지하고 하단에 다시 시도를 둔다. 검색어·탭이 바뀌어 처음부터 받다 실패하면 이전 항목을 새 결과처럼 보이지 않는다: 위에 오류를 보이고 남은 항목은 이전 것이라고 표시한다. 그 다시 시도는 처음부터 받아 목록을 바꾼다. 같은 항목은 한 번만 보인다(DEV-214).
- **이미지**: 대체 텍스트를 둔다. 불러오기 실패면 기본 이미지를 보인다.
- **테스트 표시**: I1은 결제·주문 화면과 하단에 ‘테스트 서비스’를 표시한다([정책 0장](./policy.md#0-문서-정보)).

## 4. I1 우선순위

> **팀 확인 필요.** 제안이다. Must는 S-1·S-2를 데모로 끝까지 보여주는 최소 경로이고, 나머지는 Should다. 일정이 모자라면 Should부터 덜어낸다(PRD 8장).

| 앱 | Must | Should |
| --- | --- | --- |
| 소비자 | SCR-01 홈 → SCR-03 농가 페이지 → SCR-04 상품 상세 → SCR-10 주문서 → SCR-11 결제(Mock) → SCR-12 주문 완료, 그리고 주문하려면 필요한 SCR-05 로그인 | SCR-02, 13, 14, 15, 16, 17, 18, 32 |
| 생산자 | SCR-19 로그인 → SCR-24 AI 상품 초안 → SCR-25 상품 편집 → SCR-26 예약 기간·가격·물량(게시 요청에 필요) → SCR-22 현황, 그리고 상품 승인 관리 API | SCR-20, 21, 23, 27, 28, 29, 30, 31 |

생산자 Must 경로는 시드의 승인된 생산자 계정으로 시작한다. 가입·승인 화면(SCR-20·21)이 Should여도 승인 대기·반려·정지·농가 없는 생산자 계정과 관리 API는 시드로 둔다(기술 설계 시드 데이터).

## 5. 소비자 앱

### SCR-01 홈·발견 `/`

- **관련**: FEAT-06/15, AC-06-4/5/6. 발견 탭.
- **화면**: 로고 머리·검색, 섹션 ‘농가 소식’ + 오른쪽 ‘전체’(사진 150·농가 줄·본문 2줄 카드 260 가로 스와이프, 카드 전체를 누름), 섹션 ‘제철 상품’(2열 그리드: 정사각 사진·농가 14·상품명 16 semibold·가격 16 굵게 + 취소선·마감 D-day 12 강조색), 4개 탭. 큰 제목·부제(‘오늘, 농가에서’·‘농가의 일상과 제철을 함께 만나보세요.’)와 카드 안 ‘소식방에서 이어 보기 →’는 없다(DEV-293). 프로필 나열·히어로·이어지는 대화 없음.
- **조회**: GET /api/home의 추천 순서 유지. 예약할 수 없는 상품(판매 중지·총 한도 소진·기간 공백·이번 기간 품절·종료)은 제철 상품에 넣지 않는다(서버 카드 `soldOut` = `availability`가 `AVAILABLE`이 아님, AC-07-3, DEV-215). 농가별 공개 news API 최근 항목을 합쳐 최신순. 상품 상세 API로 마지막 기간 비교 금액을 얻고 실패 시 비교만 생략한다.
- **카드**: 받는 시기 ‘11월 15일~25일 도착’, 가격(예약할 수 없으면 3장 빈 값 표의 이름), 메타 ‘n명 예약 · 마감 D-n’(예약 수는 1명부터, DEV-227).
- **동작**: 소식·작성 농가명 → `/farms/:farmId` 소식방. 상품 → SCR-04. 검색 → SCR-02. 전체 → 채팅 소식방 목록(로그인 관문).
- **상태**: 소식/상품 없음·조회 오류·다시 시도·로딩 구분. 헤더/탭 고정, 전체 세로 및 각 목록 가로 스크롤.

### SCR-02 농가 목록 `/farms`

- **관련**: FEAT-06(AC-06-1·2·7) · 탭: 발견 안 · 우선순위: Should
- **목적**: 승인된 농가를 마감 임박순으로 보고 검색한다.
- **화면 요소·데이터**: 검색창, 농가 카드(농가명, 지역, 대표 상품, 지금 가격, 단계 마감일). 정렬은 FEAT-06.
- **입력·출력**: 검색어(앞뒤 공백 제거, 비면 전체). `GET /api/farms?q=&cursor=&limit=`. 카드는 `farmId`를 넘긴다.
- **버튼 동작**: 농가 카드 → SCR-03. 아래로 끝까지 → 다음 cursor. 홈의 검색 아이콘으로 들어오면 검색칸에 포커스.
- **빈 상태·오류**: 검색 결과 없음 → ‘찾는 농가가 없어요’와 전체 목록으로. 처음 불러오기 실패 → ‘불러오지 못했어요’와 다시 시도. 목록이 있는 채 검색이 실패하면(FEAT-06 E4) 검색칸 아래 오류 상자 ‘‘{검색어}’ 검색 결과를 불러오지 못했어요’(검색어가 없으면 ‘농가 목록을 새로 불러오지 못했어요’), 본문은 ‘잠시 뒤 다시 시도해 주세요.’ 또는 연결이 끊겼으면 ‘인터넷 연결을 확인하고 다시 시도해 주세요.’에 ‘아래는 이전 목록이에요.’, 그리고 다시 시도(처음부터 받아 목록을 바꿈, 받는 동안 잠금). 남은 목록 머리줄은 ‘이전 목록 · 농가 n곳’. 목록이 있는 채 새로 받는 동안 머리줄은 ‘‘{검색어}’ 찾는 중’(검색어가 없으면 ‘농가 찾는 중’). 다음 페이지 실패는 3장 목록 규칙(하단 ‘다음 농가를 불러오지 못했어요’와 다시 시도).

### SCR-03 농가 페이지 `/farms/:farmId`

- **관련**: FEAT-02/06/12/15/19, AC-02-4/12-6/12-11/12-12/15-7.
- **화면**: 바로 소식방. 프로필 옆 팔로우/팔로잉 → 접이식 판매 품목(기본 펼침) → 채팅 본문 → 입력. 소개를 먼저 열지 않는다.
- **조회**: GET /api/farms/:id 및 GET /api/messaging/rooms/:id/messages. 기존 팔로우·좋아요·같은 방 답장 API 사용.
- **동작**: 프로필 → `/farms/:farmId/info`의 짧은 intro/지역/공유·명시적 1:1 진입. 상품 → SCR-04. 답장 → 같은 방의 본인 말풍선. 소비자 답장 범위 안내 문구는 없다.
- **상태**: 공개 읽기와 로그인/팔로우 답장 권한 분리. 해제 시 팔로워 전용 소식은 숨기고 본인 답장은 흐리게 남기며 띠 ‘팔로우를 끊어 새 소식이 오지 않아요 · 다시 팔로우’와 잠긴 입력 ‘다시 팔로우하면 답장할 수 있어요’, 헤더 ‘팔로우’는 테두리. 본인 답장이 없으면 처음 온 화면과 같다. 다시 팔로우하면 그대로 돌아온다(DEV-230, AC-06-8). 상품 없음·긴 이름·이미지 오류 처리. 없는 농가·승인 취소된 농가(404)면 그 자리에 ‘찾을 수 없는 농가예요 · 링크가 바뀌었거나 지금은 활동하지 않는 농가예요.’와 ‘농가 둘러보기’(SCR-02), 헤더는 뒤로만(팔로우·‘소식방’ 없음), 하단 탭 보임(디자인 `s-03-notfound`, DEV-224). 헤더/품목/입력 고정, 대화만 스크롤. 뒤로는 이전 화면, 직접 링크는 홈.

### SCR-04 상품 상세 `/products/:productId`

- **관련**: FEAT-07/12, AC-07-1/2/3/5/6, R-05/06/16/17/20.
- **화면**(DEV-293): 머리 없이 상품 사진 300(여러 장이면 옆으로 넘기고 ‘1 / N’)이 곧 머리이고 사진 위 왼쪽 뒤로·오른쪽 공유(결정 26, 원형 40·누르는 영역 48). 공유는 웹 공유 시트, 없으면 링크 복사(‘링크를 복사했어요’), 앱은 OS 공유 시트. 그 아래 판매자 줄(아바타 40·농가 이름·지역, ›), 상품명, 상품명 바로 아래 ‘원산지 ○○’(농가 입력값 그대로, 상품명과 같은 22/30·같은 색 #111111·굵기 400, 품절·판매 중지에도 같은 자리, 값이 비면 줄을 숨김. 원산지표시법 시행규칙 별표 3 2호가목1), DEV-258), 받는 시기 줄(아래 보조 ‘무료배송 · 마감 D-5’, 펼치면 기간 변경·지연 환불·도서산간 안내), 옵션 줄 목록(테두리 카드, 줄마다 옵션 이름·‘N박스 남음’ 또는 ‘품절’, 오른쪽 정렬 취소선 비교/현재 가격 18 굵게), 취소 규정 한 줄 ‘출하 전 전액 환불 · 출하 후 단순 변심 반품 불가 ›’(펼치면 규정 문장), 긴 상세 이야기, 품질, 상품정보(접힘). 가격표·다음 기간 이득 문구 없음. 품절에 가짜 가격 없음.
- **남은 박스**(11/09 PM 결정, DEV-292): ‘N박스 남음’은 옵션 줄마다 따로 보인다. 그 옵션의 지금 기간 남은 물량(물량 − 예약)과 전체 남은 물량(g) ÷ 옵션 중량 중 작은 값이다. 옵션끼리 남은 물량을 나눠 쓰므로 숫자 하나로 더하지 않는다(더하면 두 번 센다).
- **조회**: GET /api/products/:id의 현재 기간과 마지막 기간 동일 옵션을 비교한다. 같은/낮은 비교 금액·누락이면 비교 생략. 상세 content 없으면 description. AI 샘플은 Mock p-house에만 지정한다.
- **동작**: 농가 → 소식방, 명시적 1:1 → 기존 팔로우/로그인 관문, 예약 → 옵션·수량 → 주문서. 로그인 복귀 후 선택 값 보존. 최종 가격/수량은 서버 재검증.
- **고정**: 발견 탭 Stack 안에 같은 URL 유지, 구매 화면이라 하단 탭 바를 숨기고 하단 바에 ‘채팅’(보조)·‘예약하기’(주요, 52)만 둔다(DEV-293), 본문은 이미지 끝까지 스크롤. 사진 원비율. PAUSED/공백/품절/종료는 기존 예약 제한과 다음 시작 안내 유지. 판매 중지·총 한도 소진 상품도 상세와 SCR-03 판매 품목에는 남고 예약하기가 꺼지며 상태 줄은 ‘판매 일시 중지’·‘전체 물량 품절’, 보조 문장은 ‘지금은 새 예약을 받지 않아요.’다(SCR-03 판매 품목도 3장 빈 값 표의 같은 이름, DEV-227). 다음 기간 시작일은 기간 시작 전·이번 기간 품절일 때만 보인다(AC-07-3, R-27, DEV-215).
- **빈 값**: 당도·받는 시기·배송비·예약할 수 없는 이유는 3장 빈 값 표를 따른다(AC-07-7, M-24). 생산자 구매자 화면 미리보기도 같은 부품이라 같은 문구다. 원산지 줄도 미리보기에 같이 보인다. 원산지는 판매 요청에서 필수라 게시된 상품에는 비어 있지 않지만, 비어 있으면 줄을 숨기고 상품정보 표 줄만 남긴다(DEV-258).
- **목록 카드**: 홈·검색·농가 판매 품목 카드에는 원산지 줄을 두지 않는다. 카드에서는 예약할 수 없고 상세로 가는 링크라 상세만 대상으로 봤다. 목록도 대상인지는 농관원 질의 후속(DEV-286).

### SCR-05 로그인 `/login` (소비자 앱)

- **관련**: FEAT-01(AC-01-1, 4~6, 8~13) · 규칙: N-06 · ADR 0003, 0009, 0010 · 우선순위: Must
- **목적**: 카카오로 로그인하거나(I2, DEV-32) 소비자 테스트 계정을 골라 로그인한다(Mock 플래그가 켜진 동안).
- **화면 요소·데이터**: 닫기, 제목 ‘로그인하고 계속해요’(설명 문단 없음, DEV-293), ‘카카오로 시작하기’ 버튼(카카오 공식 문구 중 하나, 노랑 #FEE500, 설정이 꺼져 있으면 숨김), 실서버에서 카카오가 켜져 있으면 테스트 계정 로그인은 없음. 단 평가용 주소 `/login?evaluator=1`로 들어오면 카카오 버튼과 함께 테스트 계정 목록을 보인다(DEV-198, 생산자 SCR-19도 같음). 서버 Mock 플래그가 꺼져 있으면 목록 대신 아래 오류 상태가 된다. 꺼져 있을 때(CI·Mock 플래그만)만 소비자 테스트 계정 목록(이름, ‘소비자’), ‘농가는 생산자 앱에서 따로 로그인해요’ 한 줄, ‘테스트 서비스’ 표시. 카카오 버튼은 제목 아래 본문(위 간격 24)에 두고, 버튼 아래 왼쪽 정렬 12 글 ‘약관 동의와 연락처는 처음 가입할 때 한 번만 받아요’(동의는 SCR-06에서 명시적으로, Mock 실행이면 ‘Mock: 카카오로 시작하면 처음 가입하는 새 소비자로 들어가요’). 운영(카카오만)에는 하단 고정 바가 없고 사업자 정보 푸터가 화면 맨 아래에 온다(DEV-283). 테스트 계정 목록이 있을 때만 하단 바(안내 한 줄 + ‘○○로 로그인’)를 두고, 안내는 카카오가 켜져 있으면 ‘이용약관·개인정보 처리방침 동의는 처음 가입할 때 받아요 · 테스트 서비스’, 꺼져 있으면 기존 안내. 생산자 계정은 목록에 없다. Mock 모드(`npm run dev`)는 시드 데이터 시연에 계정이 필요해 카카오 버튼과 소비자 테스트 계정 목록을 함께 두고, 카카오 버튼 아래는 ‘Mock: 카카오로 시작하면 처음 가입하는 새 소비자로 들어가요’(Mock 카카오는 새 사용자, 생산자 SCR-19와 같은 규칙, DEV-136).
- **입력·출력**: `GET /api/auth/kakao/config`로 카카오 사용 여부·클라이언트 ID. 카카오 버튼 → 돌아갈 화면·행동을 sessionStorage에 두고 카카오 인가 화면(`state`=일회용 값) → `/auth/kakao?code&state`로 복귀 → `POST /api/auth/kakao`(`code`, `redirectUri`, `app: consumer`) → 토큰과 사용자. 테스트 계정은 `GET /api/auth/test-accounts?app=consumer`로 목록, 고르면 `POST /api/auth/test-login`(`userId`, `app: consumer`). 토큰은 packages/api가 앱별로 보관한다.
- **버튼 동작**: 계정 선택 → 로그인 후 누른 화면·행동으로 복귀(관문 시트에서 왔으면 그 행동을 이어서 실행). 카카오 응답의 사용자가 `needsOnboarding=true`(처음 가입)면 SCR-06을 거쳐 복귀한다.
- **카카오 복귀 `/auth/kakao`**: 닫기와 가운데 로딩 표시, 한 줄 ‘카카오 로그인 중이에요’만 둔다(제목·설명·스켈레톤 없음, 생산자 앱 SCR-19와 같은 모양). 끝나면 위 버튼 동작대로 원래 화면·행동(처음 가입이면 SCR-06)으로 간다. 이미 로그인된 채 다시 열면(새로고침·뒤로 가기, `state`는 이미 쓰임) 오류 없이 홈(온보딩이 남았으면 SCR-06)으로 간다. 서버가 15초 안에 답하지 않으면 ‘로그인이 오래 걸리고 있어요. 다시 시도해 주세요.’와 ‘다시 로그인’·‘홈으로’(DEV-112).
- **빈 상태·오류**: Mock 로그인이 꺼져 있으면(404) 테스트 계정 목록 대신 ‘지금은 로그인할 수 없어요’(카카오 버튼은 설정대로). 단 카카오가 켜진 운영에서 평가 표시(`?evaluator=1` 또는 기기에 남은 `farmclub:evaluator`)만으로 목록을 여는 경우, 테스트 로그인이 꺼져 있거나(404) 소비자 테스트 계정이 없으면 기기의 표시를 지우고 카카오만 보인다(평가가 끝난 뒤 남은 표시, DEV-283). 표시는 목록을 실제로 받았을 때만 기기에 남긴다. 카카오를 취소하거나(`error=access_denied`) 로그인되지 않은 채 `state`가 다르거나 서버가 400을 주면 `/auth/kakao`에 사유와 ‘다시 로그인’·‘홈으로’. 실패하면 다시 시도. 취소(닫기) → 원래 화면, 행동 실행 안 함.

### SCR-06 첫 가입 온보딩 `/onboarding` (소비자 앱)

- **관련**: FEAT-01(AC-01-8, 12~15) · 규칙: R-03(동의 기록 방식), R-15, N-05 · 정책 5장 · 우선순위: Must · 사용자 결정 10/18, 가입 간소화 10/23(DEV-142)
- **목적**: 카카오로 처음 가입한 소비자에게 가입에 꼭 필요한 것(닉네임·휴대폰·가입 동의)만 한 화면에서 받는다. 이름·배송지는 첫 주문서(SCR-10)에서 받는다(당근식). 다시 온 회원은 거치지 않는다.
- **화면 요소·데이터**: `/onboarding` 단계 표시 없음, 제목 ‘farmclub에서 쓸 정보예요’, 카카오계정 이메일 칩(바꿀 수 없음), 닉네임(2~12자, ‘농가 채팅과 소식방에 이 이름으로 보여요’), 휴대폰 번호(입력 중 010-0000-0000 꼴로 맞춤, ‘인증번호는 보내지 않아요’), ‘모두 동의해요’와 개별 동의 4개(이용약관·개인정보 수집·이용·만 14세 이상 필수, 농가 소식·혜택 알림 선택, 요지 ‘보기’ 시트), 하단 ‘시작하기’(필수 입력·필수 동의가 맞을 때만 켜짐). 이름 칸과 배송지 단계는 없다(DEV-142).
- **입력·출력**: `POST /api/auth/me/consents`(항목·버전·동의 여부) → `PATCH /api/auth/me`(`nickname`, `phone`) → `GET /api/auth/me`. 카카오에서 온 전화번호(DEV-78 심사 뒤)는 휴대폰 칸에 미리 채운다.
- **버튼 동작**: 시작하기 → 관문에서 왔으면 원래 화면으로 돌아가 그 행동을 잇고, 아니면 `next`. 닫기 → 계정은 남고 행동은 실행하지 않으며 원래 화면, 다음 관문에서 다시 이 화면. 예전 주소 `/onboarding/address`는 `/onboarding`으로 보낸다. 온보딩 화면에 있는 동안에는 이어서 할 행동을 실행하지 않는다.
- **빈 상태·오류**: 비로그인으로 열면 SCR-05. 이미 마친 계정이 열면 `next`로. 저장 실패 → 입력 유지, 필드 오류는 칸 아래, 연결 실패는 공통 토스트와 다시 시도.
- **가입 동의 모드 (DEV-132, AC-01-19)**: 카카오 새 사용자는 계정이 없고 가입 토큰만 있다. 이때는 프로필 칸 없이 제목 ‘약관에 동의하고 가입해요’, 안내 ‘이용약관과 개인정보 처리방침에 동의하면 계정이 만들어져요. 동의하지 않으면 아무것도 저장하지 않아요.’, 카카오계정 이메일 칩, 동의 목록, ‘동의하고 가입하기’만 보인다. `POST /api/auth/kakao/signup`으로 계정이 생기면 같은 화면이 프로필 입력(닉네임·휴대폰, 동의 칸 없음)으로 바뀐다. 닫으면 가입 대기를 지운다.
- **재동의 모드 (DEV-113, AC-01-17)**: 프로필(닉네임·휴대폰)을 이미 채운 회원이 약관·처리방침 버전이 바뀌어 `consentRequired=true`로 오면, 프로필 칸·이메일 칩 없이 제목 ‘약관이 바뀌었어요’, 안내 ‘바뀐 이용약관과 개인정보 처리방침에 동의해야 주문·팔로우·채팅을 계속할 수 있어요.’, 동의 목록, ‘동의하고 계속하기’만 보인다. 저장하면 원래 화면·행동으로. 앱을 열 때 한 번 자동으로 뜨고(약관·로그인 화면 제외), 닫아도 농가에 닿는 행동은 관문이 다시 이 화면을 연다. 동의 시트의 ‘전문 보기’는 `/terms`·`/privacy`.

### SCR-19a 약관 동의 `/consent` (생산자 앱, DEV-113)

- **관련**: FEAT-01(AC-01-18) · 정책 5장 · Figma v6 ‘현재 시안 · 생산자’ DEV-116 줄(node 481:8092·481:8122)
- **목적**: 생산자가 지금 버전의 이용약관·개인정보 처리방침에 동의해야 생산자 앱을 쓰게 한다. 새 생산자는 카카오 로그인 → 이 화면(계정 없이 가입 토큰으로 열림, 동의하면 `POST /api/auth/kakao/signup`으로 계정 생성, DEV-132) → 가입 신청(SCR-20). 가입 전 뒤로 가기는 가입 대기를 지우고 로그인으로.
- **화면 요소·데이터**: 헤더 ‘약관 동의’(뒤로 = 로그아웃), 제목 ‘약관에 동의하고 시작해요’, 안내 한 줄, ‘모두 동의해요’, 이용약관(필수)·개인정보 수집·이용(필수)과 각 ‘보기’(전문 `/terms`·`/privacy`), ‘버전 2026-10-29’, 하단 ‘동의하고 계속하기’(둘 다 체크해야 켜짐).
- **입력·출력**: `POST /api/auth/me/consents`(TERMS·PRIVACY, 지금 버전) → `GET /api/auth/me`.
- **버튼 동작**: 저장 후 관문이 농가 상태에 맞는 화면으로 보낸다. 쓰는 중에 403 `CONSENT_REQUIRED`를 받으면 내 정보를 다시 읽고 이 화면으로 온다.
- **빈 상태·오류**: 저장 실패 → 체크 유지, ‘저장하지 못했어요. 다시 시도해 주세요.’

### SCR-10 주문서 `/checkout/:productId`

- **관련**: FEAT-08(AC-08-1~5, AC-08-8·9), FEAT-01(AC-01-1) · 규칙: R-03, R-06, R-17, R-20, R-23 · 정책 2장 · 우선순위: Must
- **목적**: 옵션·수량·받는 곳을 확인하고 조건에 동의해 결제로 간다.
- **화면 요소·데이터**(DEV-293): 하위 화면 머리 ‘주문서’, ‘테스트 서비스예요 · 실제 입금·배송은 없어요’ 12 한 줄 띠. 섹션 사이는 면색 8 띠, 섹션 제목 18. 상품 줄(썸네일 64, ‘상품명 옵션 × 수량’ 한 줄, 보조 ‘농가 · 11월 10일~20일 도착’ 한 줄, 강조색 ‘변경’ → 옵션 시트, 세로 가운데), 받는 곳(제목과 같은 줄 ‘변경’, 이름 + ‘기본’ 태그 · 연락처 · ‘주소 (우편번호)’, 없으면 ‘받는 사람과 주소 입력’ → 배송지 입력 하위 화면), 배송 메모(선택 목록: 문 앞·경비실·택배함·배송 전 연락·직접 입력·선택 안 함, 직접 입력이면 입력칸), 입금 금액(‘상품 금액’ · ‘배송비’(무료면 ‘0원’, 별도인데 금액이 없으면 ‘배송비 확정 전’) · 도서산간 추가 운임 · ‘총 입금액’ 22 강조색, 금액은 오른쪽 정렬, 아래 12 한 줄 ‘농가 계좌로 직접 입금해요. 24시간 안에 입금하지 않으면 자동 취소돼요.’), 예약 전 확인(전체 동의 + 동의 5개(정책 2장: R-03 4개 + 개인정보 제3자 제공, DEV-120)는 ‘제목 (필수)’와 오른쪽 ‘보기’, 본문은 ‘보기’를 눌러 펼친다), 그 아래 12 한 줄 중개자 고지, 하단 바 ‘29,000원 예약하기’처럼 금액이 든 버튼 하나(그 위 설명 문단 없음). ‘예약한 때의 가격으로 확정돼요…’ 문장은 없다.
- **입력**: `optionId`, `quantity`, `recipientName`, `recipientPhone`(휴대폰 형식), `postalCode`, `address`, 선택 `addressDetail`, `deliveryNote`(100자 이하), 동의 5개(`thirdParty` 포함, DEV-120), `saveAddress`. 저장한 기본 배송지가 있으면 채워 두고 ‘다른 배송지’ 시트에서 저장 목록(최대 50개) 중 고르거나 새 주소를 넣는다(AC-08-5, `GET /api/auth/me/addresses`). 저장 배송지가 없으면(첫 주문) 배송지 입력의 받는 사람·연락처를 회원 정보로 채운다: 연락처는 휴대폰, 받는 사람은 이름(내 정보에서 넣은 경우, 없으면 빈 칸. 카카오에서는 이름을 받지 않는다). 가입 때 이름·배송지를 받지 않으므로 첫 주문에서 여기서 입력한다(DEV-142). ‘기본 배송지로 저장’은 처음부터 체크해 두고 끌 수 있다. 저장 배송지는 동의가 아니라 계약 이행 근거로 보관한다(처리방침 제2조, DEV-142). 50개가 찼으면 시트와 배송지 입력에 ‘이번 주문에만 쓰고 저장하지 않아요’를 보이고 저장 체크를 숨긴다. 가입 온보딩이 남은 계정이 열면 SCR-06으로 보낸다(AC-01-12).
- **출력**: `POST /api/orders`(`Idempotency-Key`, 본문에 주문서가 본 `expectedStageId`·`expectedUnitPrice`·`expectedUnitWeightGrams`) → 결제 전 주문(`orderId`, `unitPrice`, `shippingFee`, `totalAmount`), 이어서 `POST /api/orders/{orderId}/deposit`(`Idempotency-Key`) → 물량 선점·입금 대기(`AWAITING_DEPOSIT`)·계좌·기한. 서버 합계를 보여주고 SCR-11로 간다.
- **버튼 동작**: 옵션·수량·주소 변경 → 합계 미리보기 갱신. 예약하기 → 필수값·동의 검증 후 주문 생성과 입금 안내를 각 1회 요청, 처리 중 잠금. 뒤로 → SCR-04.
- **빈 상태·오류**: 받는 곳이 없거나 동의가 빠지면 예약하기 버튼이 꺼진다(그 위 개수·안내 문구는 없음, DEV-293). 동의 누락 → 넘어가지 않음(AC-08-1). 409 → 서버 최신 가격·물량으로 다시 그리고 입력값(받는 곳·메모·동의·수량)은 유지. 안내·버튼은 서버 `message`가 아니라 `details.reason`과 다시 읽은 상품 `availability`로 정한다(AC-08-8·9, DEV-216·DEV-218): `STAGE_CHANGED`(지금 기간 있음) → 제목 ‘가격이 바뀌었어요’/‘예약 기간이 바뀌었어요’/‘상자 무게가 바뀌었어요’, 본문 ‘{옵션} 한 상자 29,000원 → 30,000원. 입력한 내용은 그대로 두었어요. 바뀐 금액으로 예약할지 확인해 주세요.’, 금액에 ‘처음 본 합계’ 취소선 한 줄, 버튼 ‘바뀐 금액으로 예약하기’. `STAGE_CHANGED`(지금 기간 없음) → ‘예약 기간이 끝났어요’ · ‘다음 예약은 {M월 D일}에 열려요…’ 또는 ‘이번 예약은 모두 끝났어요.’, 금액 숨김, ‘상품으로 돌아가기’. `SALES_PAUSED` → ‘농가가 잠시 예약을 쉬고 있어요’, 예약하기 꺼짐, 안내 안 ‘다시 확인하기’(다시 읽어 열렸으면 안내를 지우고, 가격도 바뀌었으면 가격 안내로). `SOLD_OUT` → ‘{옵션}은 이번 기간 물량이 다 팔렸어요’ + ‘옵션 바꾸기’(모두 품절이면 ‘상품으로 돌아가기’). `TOTAL_LIMIT_REACHED` → 수량을 줄이면 되면 ‘수량 바꾸기’, 아니면 ‘예약 물량이 다 찼어요’ + ‘상품으로 돌아가기’. `QUANTITY_LIMIT`·`NO_FARM_ACCOUNT` → 예약하기 꺼짐 + ‘수량 바꾸기’/‘다시 확인하기’. `IDEMPOTENCY_MISMATCH` → 새 키로 한 번 다시 보냄. 409 뒤에는 주문·입금 키를 새로 만든다. 상품을 열 때부터 `availability`가 `AVAILABLE`이 아니면 같은 안내를 보인다(서버 `soldOut`은 쓰지 않음). 입금 기한이 지나 SCR-11에서 돌아오면(`changed=1`) ‘입금 기한이 지나 예약이 취소됐어요’ · ‘같은 내용으로 다시 예약할 수 있어요.’ + ‘다시 예약하기’. 네트워크 오류 → 입력 유지, 다시 시도.

#### SCR-10 하위: 배송지 입력 `/checkout/:productId/address`

- **목적**: 받는 사람과 주소를 직접 입력한다(전체 화면, 닫기 X).
- **화면 요소·데이터**: 받는 사람, 연락처, 우편번호, 주소, 상세 주소, ‘기본 배송지로 저장’, 하단 ‘이 주소로 받기’. I1은 직접 입력이고 ‘우편번호 찾기’는 없다(결정 27).
- **입력·출력**: 필드 검증은 SCR-10과 같다. ‘이 주소로 받기’ → 값을 SCR-10에 채우고 돌아간다. ‘기본 배송지로 저장’이면 주문 때 `saveAddress`.
- **빈 상태·오류**: 필드 아래 형식 오류. 닫기 → 입력 버리고 SCR-10.

### SCR-11 입금 안내 `/checkout/:productId/pay?orderId=`

- **관련**: FEAT-09(AC-09-2·3·7) · 규칙: R-01, R-02, R-28 · 정책 2·6장 · 우선순위: Must · 디자인: DEV-68 Before/After 보드
- **목적**: 소비자가 농가 계좌로 주문 금액을 직접 입금할 수 있게 계좌·입금자명·기한을 안내한다(DEV-68). 이 화면은 돈을 받지 않는다. 경로 이름 `pay`는 링크 호환을 위해 유지한다.
- **화면 요소·데이터**: ‘테스트 서비스’ 띠, 입금할 금액(큰 숫자)·상품 요약, 입금 정보 Row 목록(기존 주문 완료와 같은 부품, 순서·강조: **입금액** · **은행 계좌번호**+복사 · 예금주(농가명) · **입금자명**=주문 번호+복사 · 입금 기한 `depositDueAt`; 굵게는 이 셋만), 안내 12 한 줄 ‘입금자명: 주문 번호’(DEV-293), 판매자(농가명 · 대표자 · 지역 · 연락처, `sellerInfo`), ‘farmclub은 통신판매중개자’ 고지(Notice 부품), 구매안전서비스 고지 한 줄(13, 권유 없음), 하단 바 ‘입금을 마쳤어요’와 글자 버튼 ‘나중에 입금할게요’(그 위 설명 문장 없음). ‘결제’라는 말은 쓰지 않는다.
- **입력·출력**: `GET /api/orders/{orderId}`(`depositAccount`·`sellerInfo`·`depositDueAt`·`actions`). ‘입금을 마쳤어요’ → `POST /api/orders/{orderId}/deposit-reported`(`depositReportedAt` 기록, 상태는 그대로).
- **버튼 동작**: 복사 → 토스트 ‘계좌번호를/입금자명을 복사했어요’. 입금을 마쳤어요 → 1회 요청 후 SCR-12. 나중에 입금할게요 → SCR-12(둘 다 주문서·입금 안내를 닫고 연다. 완료 화면에서 뒤로 가도 끝난 주문서가 열리지 않는다, DEV-222). 뒤로 → 주문서(주문은 입금 대기로 남고 SCR-13·14에서 이어서 입금할 수 있다). 새로고침·주소로 연 입금 안내의 뒤로는 그 주문 상세(SCR-14, DEV-224).
- **빈 상태·오류**: 기한이 지나 취소된 주문(`CANCELED`)이면 주문서(SCR-10)로 돌려보내고 바뀐 물량으로 다시 확인받는다. 응답을 못 받으면 같은 `Idempotency-Key`로 다시 보낸다(AC-09-3). 농가 계좌가 없으면(409 `NO_FARM_ACCOUNT`) 주문서에서 안내한다.

### SCR-12 주문 접수·입금 확인 중 `/orders/:orderId/done`

- **관련**: FEAT-09/06, DEV-68. 입금 대기면 제목 ‘입금 대기’(소비자가 ‘입금을 마쳤어요’를 보낸 뒤면 ‘입금 확인 중’, DEV-207. 아이콘은 기존 검정 체크 원 그대로)과 입금 정보 Row(입금액·계좌·예금주·입금자명·기한, 복사는 계좌번호·입금자명 2개)를 보여 주고, 그 아래는 상품·배송지만(주문 번호=입금자명, 합계=입금액이라 겹치는 줄은 뺀다). 입금이 확인된 뒤 열면 ‘예약 완료’와 주문 번호·상품·합계·배송지. 주문 번호 ‘복사’ 버튼은 없앤다(쓸 데가 없다). 팔로우 권유는 그대로. 위 여백 24, 체크 원 48(DEV-293). 아래에 보조 버튼 ‘주문 상세 보기’ → SCR-14, 그 아래 글자 버튼 ‘주문 내역’·‘홈으로’.
- **조회**: GET /api/orders/:id. 상세 실패 시 다시 시도.
- **동작**: 팔로우 토글, 주문 내역 → SCR-13, 홈 → SCR-01. 소식방 입장 버튼은 없다.

### SCR-13 주문 내역 `/orders`

- **관련**: FEAT-10(AC-10-1) · 탭: 내 주문(두 번째 탭) · 우선순위: Should
- **목적**: 내 주문의 진행을 보고 할 일이 있는 주문을 찾는다.
- **화면 요소·데이터**: 탭 첫 화면 머리 ‘내 주문’(부제 없음, DEV-293), 상태 칩 32(누르는 영역 48). 주문 카드 4줄(상태 굵게 · 상품 · ‘받는 시기 · 입금·환불 사건 · 금액’ 한 줄 · 주문 번호·주문일). 카드 맨 아래 한 줄은 ‘FC-… · ○월 ○일 주문’(번호 = 입금자명·생산자 줄과 같은 글자), 입금 단계 카드는 상품 줄 아래 ‘○월 ○일~○일 도착 예정’을 더한다(받는 시기 변경 요청 중이면 빼고). 상품 줄은 한 줄이고 넘치면 상품명만 줄인다(DEV-226, AC-10-8). 상단 탭은 확정 → 미확정 → 취소·환불이며 기본은 미확정이다. 미확정은 RESERVED/PREPARING/SHIPPED/DELIVERED, 확정은 COMPLETED, 취소·환불은 CANCELED/REFUNDED/PARTIALLY_REFUNDED다. 결제 전 주문은 제외한다. 모든 페이지를 집계한 건수를 표시하고, 미확정 내 응답 필요 주문을 우선한 뒤 최신순으로 정렬한다. 선택은 filter=pending|confirmed|canceled로 상세 왕복·로그인 복귀에도 유지한다. 기존 API 반환 범위는 변경하지 않는다. (DEV-68) 입금 대기 카드 제목은 알리기 전 ‘입금 대기 · 입금해 주세요’(부제 ‘○일 (요) HH:MM까지 입금’), 알린 뒤 ‘입금 확인 중 · 농가가 확인하고 있어요’(부제 ‘○일 입금 알림’), 알렸는데 기한이 지나면 ‘입금 확인 늦어짐 · farmclub이 연락하고 있어요’, 농가가 미승인하면 ‘입금 확인 안 됨 · 사유를 봐 주세요’. 환불 카드 제목은 송금 전 ‘환불 대기 · 농가가 보낼 거예요’, 미승인 ‘환불 늦어짐 · 사유를 봐 주세요’, 송금 기록 뒤 ‘환불 완료’(흐린 글자는 취소됨·환불 완료만). 환불 부제는 ‘○일 취소’(소비자가 직접 취소)·‘○일 환불 결정’(그 밖)·‘○일 보냄’(송금 뒤). (DEV-207)
- **입력·출력**: `GET /api/orders?cursor=&limit=`.
- **버튼 동작**: 상태 탭 → 선택한 목록. 카드 → SCR-14. 제목·탭은 고정하고 목록만 스크롤한다.
- **빈 상태·오류**: 전체 주문 없음 → ‘아직 예약한 상품이 없어요’와 홈으로. 선택한 탭만 비면 ‘{탭 이름} 주문이 없어요’. 로딩 중 건수는 —, 실패는 다시 시도와 기존 목록 유지.

### SCR-14 주문 상세 `/orders/:orderId`

- **관련**: FEAT-10(AC-10-1~3), FEAT-11(AC-11-1·2), FEAT-17(AC-17-2·5) · 규칙: R-05, R-07, R-14, R-21, R-24 · 우선순위: Should
- **목적**: 상태·받는 시기를 보고 취소·구매 확정·기간 변경 응답을 한다.

### SCR-16 농가 1:1 채팅 `/chats/:farmId`

- **읽기 위치 복구(DEV-250~253)**: 같은 인증 세션에서 A → 1:1 목록 → B → 목록 → A로 돌아오면 각 방의 첫 보이는 메시지 ID·화면 상대 위치와 불러온 범위를 복구한다. 매 진입/focus에 새 권한 있는 head로 consumer/farm/thread를 검증한 뒤에만 메모리 geometry를 적용한다. 과거 위치는 최신 자동 스크롤/읽음보다 우선하며 필요한 이전 페이지를 새로 읽는다. 같은 viewport의 최종 anchor 오차는 8 CSS px 이하다.
- 늦게 뜬 사진·글 줄바꿈·이전 페이지 높이 변화는 같은 anchor를 유지한다. 사용자의 wheel/drag/스크롤 키 또는 새 메시지 보기 동작은 자동 보정을 중단한다. 과거를 보는 동안 새 메시지는 아래로 끌지 않고 기존 새 메시지 보기를 보이며, 최신으로 이동해야 읽음을 갱신한다. 원래 ID가 삭제됐으면 저장한 인접 ID, 모두 없으면 새로 검증된 범위 안의 제한된 이전 위치를 쓴다. 실패는 재시도, 401/403/404는 해당 대화의 보호된 UI/메타데이터를 폐기한다.
- 저장하는 것은 geometry와 ID뿐이며 메시지·사진 URL·draft는 캐시하지 않는다. consumer/user/session generation/thread/방문 lease로 격리하며 최대 20방·idle 30분이다. 로그아웃·token loss/401·WRONG_APP·새 로그인(동일 JWT 포함)은 동기 폐기한다. 같은 세션 auth.me 갱신은 위치를 유지한다. 새 주문 선택은 읽기 위치 identity를 바꾸지 않으며 전송 문맥/사진 규칙은 DEV-248을 따른다. hard reload는 새 시작이다.

- **주문 진입 복구(DEV-248)**: 결제 이력 주문 상세의 두 질문 버튼은 start=1과 orderId 및 원래 fromOrder를 보낸다. 구형 from=order&fromOrder도 결제 주문 시작으로 복구한다. 결제 확인 전 주문은 context=general로 일반 팔로우 안내/시작을 이용하며 주문 예외를 부여하지 않는다. 원래 주문으로의 뒤로 대상은 바뀌지 않는다.
- 시작 성공 뒤 권한 있는 첫 페이지를 확인한 후 보내기·사진을 연다. 초기 연결은 15초 이내 응답이 없으면 다시 시도를 제공한다(같은 본문/키). 명시적 연결 주문 1개는 자동 선택, 여러 개는 주문 선택 시트에서 고른다. 표시된 주문 문맥으로만 전송/사진을 연결한다. 문맥을 바꾸면 글은 유지하고 사진은 다시 첨부한다. 보내기 실패는 같은 내용/키로 다시 보내기, 성공 뒤 새로 불러오기 실패는 대화 다시 읽기다.

- **관련**: FEAT-12(AC-12-1·2·4·5), FEAT-13(AC-13-1~5) · 규칙: M-02, M-04~M-09, M-15~M-18, N-04 · 우선순위: Should
- **목적**: 농가에 질문한다. 농가 AI ON·방 AUTO에서만 AI가 답하며 HUMAN/OFF이면 직접 답변 대기. 이때 상단 한 줄은 ‘AI 안내 없이 농가가 직접 답해요 · 보통 N시간 안에’(숫자 없으면 ‘· 답이 오면 여기에 보여요’)(DEV-208). 결제 주문 문의는 팔로우 예외를 적용한다. 활성 화면 2초 갱신·읽음 처리는 계약 4장을 따른다.
- **화면 요소·데이터**: 농가 헤더(→ SCR-03), 시간순 타임라인(한국 날짜가 바뀌는 자리마다 날짜 구분 ‘2026년 10월 7일’(소식방과 같은 형식, DEV-223), 내 질문, AI 안내 배지가 붙은 답과 근거 요약, 농가 답, ‘농가에 전달했어요’ 상태, 농가 답을 기다리는 마지막 내 질문 아래 ‘농가에 전달했어요 · 보통 N시간 안에 답해요’ 상태 줄(`needsHuman`, 뒤에 농가 답이 오면 숨김, DEV-208)), 입력창(글, 사진 최대 3장), 보내기. 처음이면 ‘팔로우하고 대화를 시작해요’ 한 줄.
- **입력**: `text`(1,000자 이하), `attachmentIds`(최대 3개), 주문 문맥 `orderId`. 본문·사진 중 하나 필수. 업로드는 비공개 첨부 API.
- **출력**: 들어오면 `GET /api/messaging/chats/{farmId}/messages?cursor=`(대화는 농가·소비자당 1개라 `farmId`로 찾는다). AI 메시지에는 서버가 신고 여부 `reported`를 포함한다. 보내기 `POST /api/messaging/chats/{farmId}/messages` → 저장된 질문(연락처 가림)과 AI 안내 또는 전달 상태(`handoffStatus`). 직접 응대/AI OFF에서는 `reply=null`. 조회 응답의 `farmReply {mode, typicalReplyHours}`로 상단 문구와 예상 답 시간을 정한다(AC-13-9·13-10). 자동 팔로우는 여기서 하지 않고 SCR-03·04·18의 채팅하기·질문하기가 `POST /api/messaging/chats`로 한다.
- **뒤로 (DEV-224)**: 상품 상세(SCR-04)·짧은 농가 정보·주문 상세(SCR-14)에서 열었으면 그 화면(방 주소의 `productId`·`from=info`·`from=order&fromOrder=`로 안다, 새로고침해도 같다). 채팅 목록에서 열었거나 주소로 열었으면 1:1 목록.
- **버튼 동작**: 보내기 → 1회, 처리 중 잠금. AI 안내는 등록된 정보로만 답하고, 근거가 없거나 전달 주제면 ‘농가에 전달했어요’(M-06·M-07). 소비자는 전달되지 않은 AI 답변마다 ‘틀렸어요’를 눌러 신고할 수 있다. `POST /api/messaging/chats/{farmId}/messages/{messageId}/report`는 기존 질문함 흐름으로 오답 Escalation을 만들고, 중복 신고는 기존 신고를 반환한다. 위로 → 이전 cursor.
- **빈 상태·오류**: 아직 질문이 없으면 ‘궁금한 점을 물어보세요’. 본인 결제 주문 문의 예외 없이 팔로우하지 않은 농가의 채팅 주소로 바로 들어오면(403) 그 농가 SCR-03으로 보낸다(IA 5장 예외 경로). 보내기 실패 → 입력창에 글·사진 유지, 다시 보내기. AI 실패·시간 초과 → 전달로 처리(N-04). 불러오기 실패 → 이미 보인 것을 유지하고 다시 시도.

- **화면 요소·데이터**: 프로필(닉네임, 없으면 이름 · ‘카카오 계정’/‘테스트 계정’ · 소비자, 카카오 계정은 이름·휴대폰·이메일 한 줄), 온보딩이 남았으면 제목만 있는 안내 ‘가입을 마쳐 주세요’(본문 없음, DEV-293)와 ‘가입 마치기’ → SCR-06, 팔로우한 농가 목록(행 72), 설정(내 정보 고치기 → `/me/profile`(카카오 계정, 온보딩 끝난 뒤), 배송지 관리 → 하위 화면, 농가로 시작하기, 로그아웃, 회원 탈퇴, Mock 실행에서만 같은 왼쪽 목록 행 ‘데모 데이터 초기화’). 머리는 탭 첫 화면 ‘내 정보’ 22.
- **입력·출력**: `GET /api/auth/me`, `GET /api/farms/following`.
- **버튼 동작**: 팔로우한 농가 → SCR-03. 배송지 관리 → `/me/addresses`. 농가로 시작하기 → 시트 ‘생산자 앱은 따로 가입해요’(한 문장 ‘생산자 앱에서 가입하면 생산자 계정이 따로 만들어져요.’, DEV-293) → ‘생산자 앱에서 가입하기’ → 생산자 앱 SCR-19(가입 신청 링크). 로그아웃 → 토큰 삭제, SCR-01(스택에 남은 화면이 로그인으로 바꾸지 않아 다시 로그인해도 전에 보던 주문서로 가지 않는다, DEV-222).
- **빈 상태·오류**: 팔로우 없음 → ‘팔로우한 농가가 없어요’와 농가 둘러보기.
- **회원 탈퇴 (DEV-94, AC-01-20)**: 설정 목록 끝 ‘회원 탈퇴’(테스트 계정은 없음) → 시트 1단계 ‘탈퇴하면 바로 지워져요’(지워지는 것·남는 것·끝나지 않은 주문이 있으면 불가) → ‘다음’ → 2단계 ‘정말 탈퇴할까요?’(되돌릴 수 없음, 재가입은 새 계정) → ‘탈퇴할게요’. 성공하면 로그아웃하고 홈으로. 409면 시트에 주문 번호와 안내. 생산자 앱은 SCR-33 계정 영역과 SCR-21 하단에 같은 시트.

#### SCR-17 하위: 배송지 관리 `/me/addresses`

- **목적**: 저장한 배송지를 보고 고치거나 지운다(결정 28). 작업 화면이라 탭 바를 숨긴다.
- **화면 요소·데이터**: 배송지 카드(받는 사람·연락처·주소, 기본 표시, 수정·삭제, ‘기본으로’), 새 배송지 추가(배송지 입력과 같은 화면).
- **입력·출력**: `GET`·`POST`·`PATCH`·`DELETE /api/auth/me/addresses`.
- **버튼 동작**: 수정 → 배송지 입력 화면(값 채움). 삭제 → 확인 시트 → 지움, 토스트. 기본 배송지를 지우면 가장 최근 배송지가 기본이 된다. 기본으로 → `PATCH`(`isDefault`). 저장 → 토스트 ‘저장했어요’. 하단 ‘새 배송지 추가 (n/50)’.
- **빈 상태·오류**: 배송지 없음 → ‘저장한 배송지가 없어요’와 추가. 50개 → 추가 버튼을 끄고 ‘배송지는 50개까지 저장할 수 있어요. 안 쓰는 배송지를 지워 주세요’(서버 409 `ADDRESS_LIMIT`). 저장 실패 → 입력 유지.

#### SCR-17 하위: 내 정보 고치기 `/me/profile`

- **목적**: 카카오 계정의 닉네임·이름·휴대폰 번호를 고친다(FEAT-01 I2). 이름은 선택이라 비워 둘 수 있다(DEV-142). 이메일은 카카오계정 값이라 읽기만 한다.
- **입력·출력**: `PATCH /api/auth/me`(검증은 SCR-06과 같다). 저장 → 내 정보로 돌아가 토스트 ‘저장했어요’. 실패 → 입력 유지.

### SCR-18 소식방 목록 `/chats?view=news`

- **관련**: FEAT-12·15, M-19 · 탭: 채팅 안 소식방 · Should.
- **목적·화면**: 여러 팔로우 농가의 원형 아바타·이름·마지막으로 볼 수 있는 메시지·시각의 방 목록. `/news/:farmId` 하위 화면은 작은 농가 헤더, 날짜 구분, 말풍선, 사진·영상, 좋아요, 하단 답장 입력창. 소비자에게 다른 소비자 답장은 보이지 않는다.
- **입출력**: `GET /api/messaging/rooms`, `GET/POST /api/messaging/rooms/{farmId}/messages`. 사진 소식은 기존 news API와 같은 방송이다. 상세 계약 4장.
- **동작**: 답장 → 본인과 농가만 보는 텍스트. ‘1:1 채팅’ → SCR-16. 반응은 방송에만 가능. 활성 화면 갱신·이전 메시지 보기는 공통 계약을 따른다.
- **빈 상태·오류**: 농가 없음 → 둘러보기, 메시지 없음 → 첫 소식 안내, 실패 → 글을 유지하고 재시도. 팔로우를 끊은 농가는 목록에서 빠지고 다시 팔로우하면 나타난다(AC-06-8). 농가 페이지로 들어간 소식방은 SCR-03의 해제 상태로 보인다.

## 6. 생산자 앱

모든 화면은 생산자 앱이고 생산자 계정으로만 쓴다(결정 22). SCR-19·20·21과 정지 안내 외에는 승인된 생산자만 열린다(AC-01-3).

**공통: 도움말(DEV-109)**. 하단 탭 네 화면(SCR-22·23·28·33)의 헤더 오른쪽 위에 동그라미 물음표 버튼(‘도움말’)을 둔다. 누르면 현황으로 이동한 뒤 13단계 ‘직접 눌러 보는 안내’(스포트라이트 투어)를 시작한다.
- 화면 표시: 화면 전체를 어둡게 덮고 안내할 곳만 뚫어 밝게 보여 준다(accent 테두리). 말풍선 카드와 화살표가 그곳을 가리킨다.
- 단계 종류: 누르기 단계는 생산자가 밝은 곳을 실제로 눌러 화면이 바뀌어야 다음으로 간다. 어두운 곳은 눌리지 않는다. 설명 단계는 ‘다음’으로 넘긴다.
- 흐름: 환영 → 상품 탭 → ‘새 상품’ 버튼(설명. 누르면 판매페이지 만들기가 시작되고, 분석 자료에 글·사진·PDF를 넣으면 AI가 상품 정보와 판매페이지 초안을 채우며, 상품사진은 따로 넣는다고 안내) → 채팅 탭 → 소식방(설명) → ‘1:1 채팅’ → farmclub 대화방 → 문의 안내(설명, AC-34-5) → 뒤로 가기 → 환경설정 탭 → ‘AI 응답 설정’(반복 질문은 AI가 답하고 판단이 필요한 질문은 넘긴다는 설명) → 자동 응답 켜기/끄기(설명, 저장해야 반영) → 현황 ? 버튼(‘다시 보고 싶으면 이 버튼을 누르세요!’, 본문의 ? 자리에 실제 도움말 아이콘)과 ‘모르는 게 있으면 채팅의 farmclub 대화방에 편하게 물어봐 주세요.’(FEAT-34). 문구는 해요체이고, AI가 해 주는 일을 구체적인 예와 함께 설명한다(예: 글·사진을 넣으면 품종·원산지·보관 방법을 채우고 판매페이지 초안을 만든다. ‘배송은 언제 와요?’ 같은 질문은 AI가 답하고 ‘농약’ 같은 질문은 농가에 넘긴다).
- 예외: farmclub 대화방을 찾지 못하면 카드의 ‘다음’으로 대화 단계 세 개를 건너뛴다. 안내할 곳을 3초 동안 찾지 못하면 카드를 가운데에 띄워 ‘다음’으로 넘길 수 있게 한다. 카드의 X나 Esc로 언제든 끝낼 수 있다.
- 서버 상태: 투어는 서버 상태를 바꾸는 버튼(‘새 상품’ 열기, 초안 만들기, 분석 시작, AI 전환, 설정 저장)을 누르게 하지 않는다. 실제 서버에서는 ‘새 상품’을 여는 순간 작성 중 상품이 생기기 때문에(SCR-24) ‘새 상품’은 설명만 하고 넘어간다.
- 자동 시작: 승인된 생산자가 SCR-22에 처음 들어오면 한 번 자동으로 시작한다. 끝내거나 건너뛰면 기기(앱별 localStorage `help-guide-seen`)에 기록하고, 그 뒤로는 버튼으로만 시작한다.
- 적용 범위: 작업 화면에는 ? 버튼이 없다. 새 API는 없다.
- 앱(Android·iOS, DEV-206): 안내할 곳의 위치를 잴 수 없어 뚫린 곳·화살표 없이 가운데 카드로 단계 설명과 ‘다음’을 보여 준다(누르기 단계도 ‘다음’으로 넘긴다). 카드는 본문 위에 겹쳐 그리고 상태 표시줄·하단 내비 바 안쪽에 둔다. X로 언제든 끝낼 수 있다. 웹은 위와 같다.

### SCR-19 로그인 `/login` (생산자 앱)

- **관련**: FEAT-01(AC-01-3~6, 10, 16) · 규칙: R-22, R-24, N-06 · ADR 0003, 0009, 0010 · 우선순위: Must
- **목적**: 카카오로 시작하거나(I2, DEV-74) 생산자 테스트 계정을 골라 로그인한다. 처음이면 카카오로 시작한 뒤 농가로 가입 신청한다.
- **화면 요소·데이터**: 워드마크 ‘농가용’, 생산자 테스트 계정 목록(이름, 농가명 · 상태: 승인됨·확인 중·반려됨·정지됨·아직 농가 등록 안 함), 목록 위 ‘생산자 테스트 계정을 골라 주세요’, 목록 아래 ‘소비자는 소비자 앱에서 따로 로그인해요.’(소비자 SCR-05와 짝), ‘처음이세요? 농가로 가입 신청 ›’, 하단 사업자 정보 푸터(약관·개인정보 처리방침 링크, 사업자 정보가 없으면 ‘테스트 서비스’, 내용이 짧으면 화면 맨 아래 또는 하단 바 바로 위, DEV-116), 하단 바 ‘○○으로 시작하기’(하단 바에 따로 약관 글자를 두지 않는다). 소비자 계정은 목록에 없다. 카카오 버튼은 소비자 SCR-05처럼 설명 바로 아래 본문(위 간격 32)에 두고, 버튼 아래 13 글 ‘카카오에서는 이메일만 받아요. 대표자 이름·연락처는 가입 신청에서 입력해요.’(Mock은 ‘Mock: 카카오로 시작하면 농가 없는 새 생산자로 들어가요’)(DEV-283). 실서버에서 카카오가 켜져 있으면 제목 ‘농가로 시작하세요’, 설명 ‘처음이면 카카오로 시작한 뒤 농가 가입 신청을 해요.’, 카카오 버튼만 두고 테스트 계정 목록·가입 신청 링크·하단 고정 바는 없다(푸터는 화면 맨 아래, 로그인 실패 문구는 버튼 아래). Mock 모드와 평가 모드는 상태별 시연 계정이 필요해 카카오 버튼과 테스트 계정 목록을 함께 두고, ‘○○으로 시작하기’만 하단 바에 둔다(Mock 카카오는 농가 없는 새 생산자).
- **입력·출력**: `GET /api/auth/kakao/config`로 카카오 사용 여부. 카카오 버튼 → `state` 일회용 값을 sessionStorage에 두고 카카오 인가 화면 → `/auth/kakao?code&state`로 복귀 → `POST /api/auth/kakao`(`code`, `redirectUri`, `app: producer`) → 토큰과 사용자(농가 상태). 테스트 계정은 `GET /api/auth/test-accounts?app=producer`, 고르면 `POST /api/auth/test-login`(`userId`, `app: producer`).
- **버튼 동작**: 시작하기 → 상태에 따라 농가 없음 → SCR-20, 확인 중·반려 → SCR-21, 승인 → SCR-22, 정지 → 정지 안내 `/suspended`. 농가로 가입 신청 → SCR-20(I1은 ‘신규 생산자’ 계정으로 로그인해 신청한다. I2는 카카오로 생산자 계정을 만들며 신청).
- **카카오 복귀 `/auth/kakao`**: 가운데 로딩 표시와 한 줄 ‘카카오 로그인 중이에요’만 둔다(제목·설명·스켈레톤 없음). 로그인이 끝나면 위 버튼 동작의 농가 상태별 화면으로 바로 간다. 이미 로그인된 채 다시 열면(새로고침·뒤로 가기, `state`는 이미 쓰임) 오류 없이 같은 상태별 화면으로 간다. 서버가 15초 안에 답하지 않으면 ‘로그인이 오래 걸리고 있어요. 다시 시도해 주세요.’와 ‘다시 로그인’(DEV-108).
- **빈 상태·오류**: Mock 로그인이 꺼져 있으면(404) ‘지금은 로그인할 수 없어요’. 단 카카오가 켜진 운영에서 평가 표시만으로 목록을 여는 경우 404이거나 생산자 테스트 계정이 없으면 기기의 표시(`farmclub:evaluator`)를 지우고 카카오만 보인다(SCR-05와 같음, DEV-283). 실패하면 다시 시도. 카카오를 취소하거나 로그인되지 않은 채 `state`가 다르거나 서버가 400을 주면 `/auth/kakao`에 사유와 ‘다시 로그인’. 비로그인 관문은 `/login`과 `/auth/kakao`만 연다. 로그인된 생산자는 농가 상태와 상관없이 `/login`·`/auth/kakao`에 머물지 않고 상태별 화면으로 간다.

#### SCR-19 하위: 정지 안내 `/suspended`

- **목적**: 정지된 생산자에게 사유와 처리 결과를 알리고, 운영팀에 묻는 길을 준다(R-24, DEV-209).
- **화면 요소·데이터**: 농가명, ‘계정이 정지됐어요’, ‘판매 중이던 상품은 내려졌고, 출하 전 주문은 소비자에게 전액 환불돼요.’, 사유 상자(오류색 라벨 ‘정지 사유’ + 사유), ‘사유가 사실과 다르거나 궁금한 점이 있으면 운영팀에 문의해 주세요. 정지된 동안에도 farmclub 대화방은 열려 있어요.’, 사업자 정보 메일이 있으면 ‘메일 · {메일}’(빌드 변수 `EXPO_PUBLIC_BUSINESS_EMAIL`, 없으면 줄 없음), 하단 주 버튼 ‘운영팀에 문의하기’, 글자 버튼 ‘로그아웃’.
- **입력·출력**: `GET /api/auth/me`(농가 상태 `SUSPENDED`, 정지 사유).
- **버튼 동작**: 운영팀에 문의하기 → farmclub 문의 대화방 `/support`. 로그아웃 → SCR-19. 다른 생산자 화면 주소로 가도 여기로 온다(`/support`만 예외).

#### SCR-19 하위: farmclub 문의 대화방 `/support` (DEV-209, AC-34-9)

- **목적**: 정지·반려된 농가가 운영팀에 묻고 답을 받는다.

### SCR-24 새 상품 채우기 `/products/new`

- **관련**: FEAT-03(AC-03-1~3), AC-SRC · 규칙: M-10~M-12, N-04 · 우선순위: Must · 계약: [source-integration.md](./source-integration.md) ‘새 상품 한 화면 편집과 AI 시트’·‘두 장 흐름 v2’·‘첫 장 = 미리보기 화면’(DEV-184), [source-editor.md](./source-editor.md) DEV-179
- **목적**: 구매자가 볼 상품 페이지 모양 그대로 새 상품을 채운다. 자료(글·사진·PDF)를 넣으면 AI가 상품 정보와 상세 초안을 채운다.
- **진입**: `/products/new`는 서버 자료 분석 설정을 보고 바로 넘긴다. 켜져 있으면 비공개 작업을 열어 `/products/source-analysis?batchId=…&composer=1`(이 절의 화면), 꺼져 있으면 `/products/manual`(아래 ‘문구 붙여넣기’). `composer=1`이 없는 진입(이전 작업 이어 하기, 여러 상품 작업)은 기존 2탭 작업 화면이다.
- **화면 요소·데이터**: 구매자 상품 페이지 순서(대표사진 → 농가·상품명·원산지 → ‘가격은 다음 단계에서 정해요’ 안내 → 상세 스토리 → 상품정보 표). 편집 가능한 칸은 값을 채운 뒤에도 옅은 면색·테두리를 유지하고 포커스를 강조한다. 상품명 아래 원산지도 직접 고칠 수 있으며 상품정보 표의 원산지와 같은 값을 쓴다. 사진 위 ‘AI가 뺀 문구 N개’ 칩(0개면 숨김)과 제외 사유 모달(결과별 한 번, IA ‘SCR-24 제외 문구 안내’ 절). 상단 오른쪽 눈 아이콘으로 편집/미리보기를 전환하며 미저장 값을 보존한다. AI 시트가 열려 있어도 전환 가능하고 미리보기를 켜면 시트를 닫는다. AI 아이콘은 편집 단계에만 있으며 미리보기 중 누르면 편집으로 돌아와 자료 시트를 연다. 구매자 미리보기에는 편집 면색·테두리를 표시하지 않는다. 하단 AI 시트(처음에는 닫힘, 상단 AI 아이콘으로 열고 닫으며 접힌 띠는 표시하지 않음): 정책 안내 → 선택 상품사진(공개 전 대표 1장 필수, 분석에는 불필요) → 분석 자료 → 품종명(필수) → ‘AI로 채우기’. 분석 중에는 시트를 접고 상세 자리에 진행 안내. AI 출처 배지·원문 보기는 없다.
- **입력·출력**: 자료 분석 작업 API(`/api/source-analysis`, [source-analysis.md](./source-analysis.md)), 상품 저장은 기존 `PATCH /api/products/{productId}`(버전·멱등 키). 가격·받는 시기는 채우지 않는다(AC-03-2).
- **버튼 동작**: ‘임시 저장’ → 기본 정보·첨부·상품 PATCH·비공개 초안 저장(상품에는 아직 반영 안 함). ‘다음: 판매·가격’ → 임시 저장 뒤 최신 초안을 상품에 반영하고 판매 전(DRAFT/REJECTED) 상품은 SCR-24b로, 판매 중·승인 대기·종료 상품은 확인 문구 뒤 SCR-25로.
- **빈 상태·오류**: 분석 실패·일부 완료·취소는 시트 안에서 안내하고 입력·첨부를 보존한다(AC-03-3). 분석 뒤 첨부가 바뀌어 최신 초안이 없으면 다음으로 넘어가지 않고 다시 채우기를 안내한다.
- **문구 붙여넣기 `/products/manual`(자료 분석이 꺼진 서버, DEV-84)**: 예전 SCR-24 흐름. 문구 입력(최대 3,000자) → 초안 만들기(`POST /api/products/drafts`, 20초, N-04) → 결과와 빈 칸 강조 → 편집으로(`POST /api/products`, SCR-25). AI 실패면 문구를 보존하고 빈 편집 화면으로(AC-03-3). 가격은 채우지 않는다(AC-03-2).

### SCR-24b 판매·가격 `/products/:id/sell`

- **관련**: FEAT-04, FEAT-05 · 규칙: R-18, R-21, R-25 · DEV-184 · 계약: [source-integration.md](./source-integration.md) ‘두 장 흐름 v2’
- **목적**: 새 상품(판매 전)의 판매 조건을 한 화면에서 정하고 판매 시작을 요청한다. 판매 중·승인 대기 상품은 이 화면 대신 SCR-25·26·물량 화면에서 관리한다(상단 Notice ‘판매 중인 상품은 상품 편집에서 고쳐 주세요.’).
- **화면 요소·데이터**: 헤더 ‘판매·가격’. 중량 옵션 → 받는 시기와 ‘이 날까지 못 보내면 전액 환불’ 날짜 → 가격(기본 1기간: 오늘~받는 시기 전날, ‘얼리버드 기간 추가’로 앞 기간을 나눔, 옵션별 가격·박스 수) → 배송비(무료·따로 받기, 도서산간 추가 운임) → 물량(판매할 총 물량 kg, 한 주문 최대). 하단 ‘저장’·‘미리보기’.
- **입력·출력**: 저장 = `PATCH /api/products/{productId}`(옵션·받는 시기·환불일·배송비·한 주문 최대) → `PUT /api/products/{productId}/stages`(PATCH 응답 버전). 판매 시작 요청 = `POST /api/products/{productId}/capacity-requests`(최초 공급 물량 신청 → 승인 대기).
- **버튼 동작**: 미리보기 → 소비자 상품 상세와 같은 렌더러로 구매자 화면(편집 칸 없음), ‘판매 시작을 요청하면 운영자가 확인한 뒤 공개돼요. 그 전에는 구매자에게 보이지 않아요.’ + ‘더 고치기’·‘판매 시작 요청’ → 토스트 ‘판매 시작을 요청했어요. 운영자가 확인하면 공개돼요.’
- **빈 상태·오류**: 칸별 검증 문구(옵션 없음, 받는 시기·환불일 없음, 환불일은 받는 시기 다음 날 이후, 기간은 받는 시기 전날까지, R-18 뒤 기간이 더 비쌈, 따로 받는 배송비 금액, 한 주문 최대, 총 물량). 입금 계좌가 없으면 Notice ‘입금 계좌가 없어요’와 ‘입금 계좌 등록’(`/farm/account`), 입력은 저장할 수 있다. 저장 실패 → ‘저장하지 못했어요. 다시 시도해 주세요.’, 입력 유지.

#### SCR-23·25 하위: 물량·판매 설정 `/products/:id/sales`

- **목적**: 판매 중인 상품의 공급 물량·판매 한도·한 주문 최대·판매 중지를 관리한다([1.4](./capacity-1.4.md), [화면 구조 1.3](./navigation-1.3.md)). 작업 화면이라 탭 바를 숨긴다. 진입: SCR-23 카드 ‘판매 설정’, SCR-25.
- **화면 요소·데이터**: 헤더 ‘물량·판매 설정’, 상품명과 상태 한 줄, 승인 물량·현재 판매 한도·예약 중·출하 완료·추가 예약 가능(kg), 현재 판매 한도(kg)·한 주문 최대 박스 수와 ‘판매 설정 저장’, ‘판매 중지’/‘판매 재개’, ‘공급 물량 승인 요청’(첫 신청)·‘물량 추가 신청’과 신청 상태(심사 중·승인·반려·철회), 심사 중이면 ‘신청 철회’.
- **입력·출력**: `GET /api/products/mine/{productId}`, `PUT /api/products/{productId}/sales-settings`, `POST /api/products/{productId}/capacity-requests`(계약 2장·1.4).
- **버튼 동작**: 중지·재개·신청·철회는 확인 시트(‘판매를 중지할까요?’ 등) 뒤 처리하고 토스트(‘판매를 중지했어요. 기존 예약은 유지돼요.’ 등).
- **빈 상태·오류**: 입금 계좌가 없는 첫 신청은 409 `NO_FARM_ACCOUNT` 안내(SCR-25 절). 버전 충돌이면 ‘최신 상태 확인’. 입력 유지.

#### SCR-23·25 하위: 판매페이지 수정 `/products/:id/detail`

- **목적**: 이미 있는 상품의 구매자 상세(판매페이지)를 고친다. 진입: SCR-23 카드·SCR-25 ‘판매페이지 수정’.
- **화면 요소·데이터**: 헤더 ‘판매페이지 수정’, 상단 ‘구매자 화면 미리보기’/‘편집으로 돌아가기’, 상태 안내(‘저장한 수정본이 있어요. 아직 구매자에게 보이지 않아요.’ 또는 ‘현재 상품에 반영된 내용을 수정해요.’), 대표사진·상세 스토리 편집(사진 추가·설명 추가), ‘상품 정보·판매 설정’, 하단 ‘수정본 저장’·‘상품에 반영’.
- **입력·출력**: 상품별 비공개 작업(`productWorkspace` open·save·apply, [source-integration.md](./source-integration.md)). 자료 분석이 꺼진 서버는 예전 블록 편집기(헤더 ‘상품 상세 편집’, 상세 초안 생성·글 섹션·상세 사진·‘상세 저장’)를 쓴다(DEV-84).
- **버튼 동작**: 수정본 저장 → 토스트 ‘수정본을 저장했어요. 아직 상품에는 반영되지 않았어요.’ 상품에 반영 → 확인 시트(판매 중이면 ‘반영하면 구매자가 보는 판매페이지가 바로 바뀌어요.’) → ‘확인 · 상품에 반영’. 저장 안 한 채 나가면 ‘계속 편집’/‘수정 내용 버리고 이동’.
- **빈 상태·오류**: 불러오기 실패 → ‘다시 불러오기’. 실패 시 입력 유지.

### SCR-25 상품 편집 `/products/:id/edit`

- **관련**: FEAT-04(AC-04-1~4) · 규칙: R-16, R-18, R-20, R-21, R-23, R-25, M-13 · 우선순위: Must
- **목적**: 초안을 다듬고 게시를 요청한다.
- **화면 요소·데이터**: 상태와 반려 사유, 사진(첫 사진이 목록에서 잘려 보이는 104·64 미리보기), 기본 정보(상품명, 품종, 설명, 원산지(자리표시자 ‘예: 서귀포시’, 칸 아래 ‘‘국산’·‘제주산’처럼 시·도, 시·군·구 이름으로 적어요.’, 다음 줄 ‘구매자 화면에는 상품명 바로 아래 같은 크기로 보이고, 비어 있으면 판매 요청을 할 수 없어요.’(DEV-258)와 ‘표시 방법 보기 ›’ → `/origin-notice`, DEV-121, 시행령 별표 1 1호가목1)), 보관 방법), 품질(예상·실측 당도, 등급), 중량 옵션·상품 최대 판매 박스 수·한 주문 최대 수량, 받는 시기(배송 예정 기간)와 최대 지연 기한(누르면 기간 선택 달력 시트), 배송비(무료·별도)·도서산간, 예약 기간·가격·물량 요약 줄, 판매/총 한도/잔여 요약, 판매 중지·재개, 하단 바 저장 + 게시 요청.
- **입력·출력**: `GET /api/products/mine/{productId}`, 저장 `PATCH /api/products/{productId}`, 공급 승인 요청 `POST /api/products/{productId}/capacity-requests`. 판매 한도·한 주문 상한·중지는 `PUT /api/products/{productId}/sales-settings`(계약 2장).
- **버튼 동작**: 저장 → 초안 유지. 예약 기간 설정으로 → SCR-26. 게시 요청 → 필수값·단계 가격이 모두 있을 때만 활성(AC-04-1) → 승인 대기. 판매 중 가격·옵션·기간 변경은 신규 주문부터 즉시 반영하고 기존 결제 주문은 보존한다(R-25).
- **빈 상태·오류**: 빠진 항목 수(‘빈 칸 n개를 채우면 게시를 요청할 수 있어요’)와 칸별 오류 표시. 원산지는 공백만 있어도 빈 칸이다: 서버·Mock이 첫 공급 승인 요청(판매 요청)과 판매 중 상품 저장을 400(`details.fields.원산지`)으로 막고, 물량·판매 설정은 ‘먼저 입력해 주세요: 원산지’를 보인다(DEV-258). 저장 실패 → 입력 유지. 나가기 전 저장하지 않은 변경이 있으면 확인 시트. 예약이 있는 상품의 배송 예정 기간을 바꾸면 주문자 동의·환불 안내 시트(R-21). 저장 성공 → 토스트. (DEV-68) 입금 계좌가 없는 농가의 첫 공급 승인 요청은 409 `NO_FARM_ACCOUNT` → 물량·판매 설정(P16)의 확인 시트 안에 오류 문구 ‘입금 계좌를 먼저 등록해 주세요. 소비자가 그 계좌로 직접 입금해요. (환경설정 › 농가 프로필 › 입금 계좌)’. 별도 화면 없음.

### SCR-26 예약 기간·가격·물량 `/products/:id/stages`

- **관련**: FEAT-05 AC-05-1~5, R-06·18·25·26 · Must.
- **목적·화면**: 날짜 범위별 가격과 옵션 물량을 입력한다. 빈 기간 하나로 시작, 기간 추가/삭제, 날짜 선택, 옵션별 가격·박스 수, 상품 총 한도 요약, 저장. 단계 번호·프리셋·할인율 선택은 없다.
- **입출력**: 편집 상품 GET과 `PUT /api/products/{productId}/stages`(stageId, version 포함). 상세 계약 3장.
- **동작**: 날짜순 정렬, 기존 ID 유지. 이른 기간 가격은 이후보다 낮고 겹치지 않는다. 저장 즉시 새 주문에 적용하며 기존 주문값은 보존한다.
- **수확(DEV-231, FEAT-17 AC-17-11)**: 저장된 기간 카드 맨 아래에 굵은 선으로 나눈 ‘수확’ 칸. 윗줄 ‘예약 완료 n건 · 입금 대기 m건’. 예약 완료가 있으면 테두리 버튼 ‘수확 시작 · 출하 준비 n건’(수확을 시작한 기간이면 ‘남은 예약 n건도 출하 준비로’), 아래 ‘입금 대기 주문은 승인한 뒤 따로 옮겨요.’. 저장 안 한 값이 있으면 버튼을 막고 ‘저장한 뒤 수확을 시작할 수 있어요.’. 다 옮겼으면 ‘수확 시작함 · 출하 준비 n건 보기 ›’(SCR-29 출하 준비). 입금 대기만 있으면 ‘입금을 승인하면 수확을 시작할 수 있어요.’. 버튼 → 확인 시트: 제목 ‘수확을 시작할까요?’, ‘상품명 · 단계(MM.DD—MM.DD)’, 주문 줄 최대 3 + ‘외 n건’, 예약 기간이 아직 열렸으면 ‘이 기간은 ○월 ○일까지 예약을 받아요. 그 뒤 들어온 주문은 다시 눌러 옮겨요.’, ‘예약 완료 n건이 출하 준비로 옮겨져요. …’, ‘소비자 주문 상세에는 ‘수확·포장 중’으로 보여요. 보내기 전까지는 소비자가 취소(전액 환불)할 수 있어요.’, ‘출하 준비에서 예약 완료로 되돌릴 수 없어요.’, ‘아니요’ 1 : ‘수확 시작 · n건’ 2. 성공 토스트 ‘n건을 출하 준비로 옮겼어요’(서버가 실제로 옮긴 수). 실패는 시트 안 ‘수확을 시작하지 못했어요. 다시 눌러 주세요.’(같은 키로 다시), 404/409는 시트를 닫고 Notice ‘이미 상태가 바뀌었어요. 최신 상태로 다시 보여 드려요.’. `?stage=`로 들어오면 그 카드로 스크롤한다.
- **빈 상태·오류**: 예약 있는 기간은 삭제·날짜 변경을 막고(409 `PERIOD_LOCKED`) 이유를 보여준다. 그 기간의 가격과 물량(사용량 이상)은 바꿀 수 있고 신규 주문부터 적용되며, 기존 결제 주문의 가격·기간은 그대로다([1.4 §3](./capacity-1.4.md)). 필드 오류/버전 충돌 때 입력을 유지하며 최신 값 확인 후 재저장한다.

### SCR-27 소식 올리기 `/broadcast/new`

- **관련**: FEAT-12(AC-12-2·3), FEAT-15 · 규칙: M-01, M-14, M-16 · 우선순위: Should
- **목적**: 팔로워에게 재배·수확 소식을 글·사진·영상으로 올린다.
- **화면 요소·데이터**: 본문, 사진(최대 5장, 장당 10MB)·영상(1개, 60초, 100MB) 첨부와 미리보기·제거, 공개 여부(공개: 농가 페이지에도 / 팔로워 전용), 받을 팔로워 수, 올리기.
- **입력·출력**: 본문이나 첨부 중 하나 이상. `POST /api/messaging/news` → `broadcastId`, 작성 시각. 연락처는 가려서 저장된다.
- **버튼 동작**: 올리기 → 1회, 성공 후 잠금 → 자기 농가 소식방. 뒤로 → 쓰던 내용이 있으면 확인.
- **빈 상태·오류**: 형식·용량 오류는 파일별 사유(413). 첨부 실패 → 글은 유지하고 첨부만 다시 시도.

### SCR-28 농가 채팅 `/chats`

- **관련**: FEAT-12/13/33/34, AC-12-7/9/10/11/12, AC-34-2, M-19, M-22. 채팅 탭.
- **화면**: 소식방 / 1:1 채팅만. 최초 소식방은 자신의 대화 본문이 바로 열린다. 중간 농가 목록·전체/답변 필요 필터·목록 AI/직접 응대 상태 없음.
- **고정**: 두 선택지, 판매 품목(기본 접힘), 입력창(탭 위), 4개 탭. 본문 첫 시스템 문구 ‘보내는 소식은 모든 팔로워에게 보여요’는 대화와 함께 스크롤한다.
- **보내기 확인·삭제 (DEV-210, M-23, AC-12-13~16)**: 입력 안내는 ‘팔로워 N명에게 소식 보내기’(수를 모르면 ‘모든 팔로워에게 소식 보내기’). 전송을 누르면 시트 ‘팔로워 N명에게 보낼까요?’(팔로워 0명이면 ‘아직 팔로워가 없어요. 그래도 보낼까요?’), 소비자에게 보일 미리보기, ‘보낸 소식은 지울 수 있지만 고칠 수는 없어요.’, ‘아니요’(요청 없이 글 유지) · ‘확인 · 보내기’(한 번만). 본인 방송 좋아요 줄 끝 ⋯(길게 누르기도 같음) → ‘이 소식을 삭제할까요?’, 공개 소식은 ‘팔로워 N명의 소식방과 농가 공개 소식방에서 사라져요.’, 팔로워 전용은 ‘…소식방과 채팅 목록에서 사라져요.’, ‘받은 답장은 지워지지 않아요. 삭제한 소식은 되돌릴 수 없어요.’, ‘삭제하고 다시 쓰기’(글 소식만, 본문이 입력칸으로 돌아옴) · ‘아니요’ · ‘삭제’. `DELETE /api/messaging/news/{broadcastId}`의 404는 이미 지운 것으로 보고 성공 처리한다. 토스트 ‘소식을 삭제했어요’(다시 쓰기면 ‘… · 고쳐서 다시 보내 주세요’). 소비자 소식방·채팅 목록 미리보기에서는 원 소식이 빠지고 답장은 남는다(FEAT-12 DEV-210 절, [제안 보드](/docs/design/proposals/dev-210-news-confirm-delete.html), DEV-233에서 옮김).
- **동작**: 본인 roomMessages/sendRoom, 기존 소비자 답장에서 명시적 1:1 시작, 첨부 → SCR-27 → 같은 탭. /news/:farmId 기존 링크는 자기 방이면 이 탭으로 복귀한다.
- **상태**: 접기/전송은 입력·접힘 선택을 유지. 빈 대화·로딩·실패 재시도, 권한/비활성 polling 중단은 유지.

- **farmclub 문의 대화방(DEV-111)**: 1:1 채팅 목록에 'farmclub'(로고, ‘farmclub 운영팀 · 궁금한 점을 물어보세요’)이 보인다. 고정하지 않고 다른 대화처럼 최근 메시지 순이다. 손님 대화가 없을 때의 빈 상태 문구는 ‘아직 손님과 나눈 1:1 대화가 없어요’다.

#### SCR-28 하위: 1:1 채팅 `/chats/:consumerId`
- 머리: 소비자 가림 이름(‘김○○’, R-15)과 부제 ‘1:1 채팅’. 이름은 대화 조회 응답의 `consumerName`(목록과 같은 값)에서 읽어 새로고침·링크로 바로 열어도 같다. 응답 전에는 목록에서 넘긴 이름을 쓴다(DEV-232).
- farmclub 문의 대화방(`consumerId = u-farmclub`, AC-34-2): 제목 'farmclub', 부제 ‘운영팀 문의’. AI 응대 바·농가 AI 설정 링크 대신 ‘farmclub 운영팀에 물어보세요’ 안내(사람이 답하고 AI가 답하지 않음)를 보인다. 운영팀 말풍선 이름은 'farmclub'이다. 입력·첨부는 일반 1:1과 같다.
- 대화 내부 AI 표시/근거·HUMAN 전환·AI 다시 켜기·주문 문의 해결/재열기는 기존 계약 유지. `WRONG_ANSWER` escalation은 코드 대신 “소비자가 AI 답변을 신고했어요” 한국어 레이블로 표시한다. 읽는 것만으로 해결하지 않는다. 실패 시 입력 유지.

### SCR-29 주문·출하 처리 `/ship`

- **관련**: FEAT-17, AC-17-2/3/4/5/6/7/8/9, FEAT-09 AC-09-8/9, R-07/15/19/28 · 디자인: DEV-68 보드, Figma 「현재 시안 · 생산자」 DEV-68 줄.
- **화면**: 전체/입금 대기/예약/출하 준비/출하/환불 탭(가로 스크롤), 주문번호·받는 사람·배송 정보, 준비 주문 선택·택배사/송장 시트·출하 확인. 예약 탭 맨 위에 예약 완료가 남은 기간마다 ‘상품명 단계 · n건 수확 시작하기’ ListRow(부제: 끝난 기간 ‘수확을 시작하면 출하 준비로 옮겨져요’, 열린 기간 ‘예약 기간 ○월 ○일까지’) → SCR-26 `?stage=`. 예약 탭 아래 안내 ‘예약 완료 주문은 상품의 예약 기간에서 「수확 시작」을 누르면 출하 준비로 옮겨져요. 배송 완료는 farmclub이 확인해서 바꿔요.’(DEV-231). 줄에는 상태 바꾸는 버튼이 없다. 모든 줄과 시트(입금 승인·송장·출하 확인)의 둘째 줄은 ‘이름 · 상품명 옵션 × 수량’이다. 줄에서는 한 줄로 두고 상품명만 줄이며, 시트는 줄바꿈한다(DEV-226, AC-17-10). **입금 대기 줄(DEV-68)**: 주문 번호·기한, 이름·상품명·옵션, 입금액·입금자명(=주문 번호), ‘소비자가 입금했다고 알렸어요’ 줄(`depositReportedAt`), 미승인했던 줄은 ‘미승인 사유: …’(`depositIssue`). 배송지는 보여 주지 않는다(R-15). **환불 줄**: 입금액·‘입금했던 계좌로 돌려보내요’, 미승인했던 줄은 ‘미승인 사유: …’(`refundIssue`), 송금을 마친 줄은 ‘○월 ○일 송금 완료’. **두 줄 모두** 아래에 기존 버튼 한 쌍 ‘미승인’(secondary) 1 : ‘승인’(primary) 2. 입금 승인은 이름·옵션×수량·금액을 보여주는 확인 시트 후 처리하며 취소하면 호출하지 않는다(2026-11-02 owner 결정, DEV-179). 기존 이름 표시·마스킹은 유지하고 배송지는 보여주지 않는다. 환불 승인은 기존처럼 줄에서 처리. 미승인은 그 줄 안에 펼쳐진다: (입금만) ‘미승인하면’ 아래 ‘입금 대기로 두기’/‘주문 취소’ 고르기, ‘미승인 사유’ 아래 Radio 줄 4개(로그인 계정 고르기와 같은 부품: 사유 3개 + ‘직접 입력’, 하나만 켜짐, 다시 누르면 꺼짐). ‘직접 입력’을 켜면 그 아래 라벨 없는 입력 칸(필수, 200자)이 바로 열린다. 사유를 고르지 않았거나 직접 입력이 비면 ‘미승인’을 누를 수 없다. ‘닫기’ 1 : ‘미승인’(취소를 고르면 ‘미승인 · 주문 취소’) 2. 탭 아래 안내 문구는 탭마다 다르다(입금 대기: 통장 대조 뒤 누르기·24시간 자동 취소, 환불: 입금했던 계좌로 보내기).
- **조회**: GET /api/orders/producer 전체 cursor(`totalAmount`·`depositDueAt`·`depositReportedAt`·`refundSettledAt` 포함). 조회 시점에 기한 지난 입금 대기는 서버가 취소한다. 예약은 조회만, 자동 전이 없음(수확 시작은 SCR-26). 기존 PREPARING 주문에만 송장·출하 동작을 제공한다.
- **동작**: 입금 승인 → POST /api/orders/:id/confirm-deposit, 환불 승인 → POST /api/orders/:id/refund-settled, 입금 미승인 → POST /api/orders/:id/reject-deposit `{reason, cancel}`, 환불 미승인 → POST /api/orders/:id/refund-issue `{reason}` → 토스트, 목록 갱신. 409면 최신 상태로 다시 그린다. 출하 준비 송장 저장은 로컬 편집·선택, 출하 확인 후 주문별 POST /api/orders/:id/ship. 출하된 줄에는 ‘송장 수정’ 버튼이 있고 같은 시트를 현재 택배사·번호로 열어 PATCH /api/orders/:id/tracking으로 저장한다. 이력은 노출하지 않는다. 수확 시작은 SCR-26에서 `POST /api/orders/producer/harvest-start`(DEV-231)로 한다. 배송 완료 변경 권한은 없다.
- **상태**: 없음·로딩·오류 재시도, 부분 실패/409는 성공분 보존·실패분 재시도. 배송 완료 주문 개인정보는 서버 마스킹 유지.

### SCR-30 농가 프로필·링크 `/farm`

- **관련**: FEAT-02(AC-02-1·2), FEAT-19(AC-19-1~3) · 진입: 환경설정(SCR-33) · 우선순위: Should
- **목적**: 프로필을 고치고 농가 링크를 단골에게 보낸다.
- **화면 요소·데이터**: 농가 링크(글자 한 줄 + 복사·보내기), 프로필 미리보기(대표 사진과 ‘사진 바꾸기’, 농가명, 지역 · 팔로워 수), 항목 줄(농가 이름·지역·소개·입금 계좌 ›; 계좌가 없으면 값 자리에 오류색 ‘계좌를 등록해 주세요’, DEV-68), 안내 ‘소비자가 예약할 때 입금 계좌로 직접 입금해요. 계좌가 없으면 상품 승인을 요청할 수 없어요’, ‘농가 상세 페이지 편집’(→ `/farm/detail`, DEV-233에서 구현대로 적음), ‘소비자 앱에서 내 농가 보기 ›’.
- **입력·출력**: `GET`·`PATCH /api/farms/me`(`bankName`·`accountNumber`·`accountHolder` 포함). 링크는 응답의 `shareUrl`(`/s/farms/{farmId}`).
- **버튼 동작**: 복사 → 토스트 ‘링크를 복사했어요’. 보내기 → 휴대폰 공유 창. 항목 줄 → 하위 화면. 사진 바꾸기 → 사진 고르기 → 저장. 소비자 앱에서 내 농가 보기 → 소비자 앱 SCR-03.
- **빈 상태·오류**: 승인 전에는 링크를 보여주지 않는다.

#### SCR-30 하위: 입금 계좌 `/farm/account` (DEV-68)

- **목적**: 소비자가 직접 입금할 농가 계좌를 등록·수정한다. 가입 신청(SCR-20)에는 넣지 않고 승인 뒤 여기서 등록한다. 작업 화면이라 탭 바를 숨긴다.
- **화면 요소·데이터**: 48 바(뒤로 + ‘입금 계좌’), 입력 16 세 칸(은행 · 계좌번호(숫자·하이픈) · 예금주), 예금주가 대표자 이름과 다르면 안내 한 줄, 안내 ‘입금 확인은 농가가 직접 해요. farmclub은 이 계좌로 돈을 받거나 보내지 않아요’, 하단 ‘저장’ 56.
- **입력·출력**: `PATCH /api/farms/me`(세 칸을 함께). 계좌번호는 숫자·하이픈 6~32자. 하나라도 비면 저장하지 않고 칸 아래 오류.
- **버튼 동작**: 저장 → 검증 후 저장, 토스트 ‘입금 계좌를 저장했어요’, SCR-30.
- **빈 상태·오류**: 실패 → 입력 유지. 계좌 없는 농가는 상품 초기 승인 요청에서 409 `NO_FARM_ACCOUNT`(SCR-25 물량 설정에 ‘환경설정 › 농가 프로필 › 입금 계좌’ 안내).

#### SCR-30 하위: 농가 상세 편집 `/farm/detail`

- **목적**: 농가의 긴 소개(상세 페이지 블록)를 쓰고 고친다. 짧은 소개 한 칸은 프로필 항목 고치기(`/farm/edit/:field`)가 맡는다. 작업 화면이라 탭 바를 숨긴다.
- **화면 요소·데이터**: 헤더 ‘농가 상세 편집’, 상세 초안 만들기(참고 글 ‘농가의 이야기, 과일의 특징을 적어 주세요’, 참고 사진 최대 10장, ‘상세 초안 생성’), ‘내용 편집’/‘미리보기’, 글 섹션·상세 사진 추가, 하단 ‘상세 저장’.
- **입력·출력**: `GET /api/farms/me`, 초안 `POST /api/farms/me/detail-draft`, 저장 `PATCH /api/farms/me`(`detailContent`).
- **버튼 동작**: 저장 → Notice ‘상세 페이지를 저장했어요’. 저장 안 한 채 나가면 확인.
- **빈 상태·오류**: 초안 실패 → ‘생성에 실패했어요. 직접 편집하거나 다시 시도해 주세요’, 저장 실패 → ‘저장하지 못했어요. 다시 시도해 주세요’, 입력 유지. Figma v6 P09는 짧은 소개 한 칸만 그려 둬서 어느 쪽이 의도인지는 PM 판단(감사 J8)이며, 이 절은 지금 구현을 적은 것이다(DEV-233).

#### SCR-30 하위: 프로필 항목 고치기 `/farm/edit/:field`

- **목적**: 농가 이름·지역·소개 중 하나만 고친다(결정 34). 작업 화면이라 탭 바를 숨긴다.
- **화면 요소·데이터**: 48 바(뒤로 + 항목 이름), 입력칸(소개는 여러 줄), 소비자 앱에 어디에 보이는지 한 줄, 하단 ‘저장’.
- **입력·출력**: `PATCH /api/farms/me`(그 필드만).
- **버튼 동작**: 저장 → 검증 후 저장, 토스트, SCR-30.
- **빈 상태·오류**: 필수값(이름·지역)이 비면 저장하지 않고 빈 칸 표시(AC-02-2). 실패 → 입력 유지.

### SCR-31 AI 응답 설정 `/farm/ai-settings`

- **관련**: FEAT-32 AC-32-1~4 · 생산자·승인 농가 · Should.
- **화면**: AI 사용 스위치, 소량 주문·예약 배송 응대 원칙, FAQ, 추가 전달 주제, 고정 전달 주제 안내, 저장, 질문 미리보기.
- **입출력**: `/api/farms/me/ai-settings` GET/PUT, `/preview` POST. 필드 제한·버전·우선순위는 계약 5장.
- **동작**: 저장 전 변경 표시, 나가기 확인. 미리보기는 답변/전달 사유·근거를 보여주고 임시 설정임을 표시한다.
- **오류**: 필드 오류·네트워크 실패 시 입력 유지. 저장에서 `409 STALE_VERSION`이면 최신 버전을 불러오면서 사용자가 편집한 필드는 유지하고, 그 최신 버전으로 다시 저장할 수 있다. OFF여도 HUMAN 상태와 기존 대화는 보존한다.

### SCR-32 주문 문제 문의 `/orders/:orderId/inquiry`

- **관련**: FEAT-33 AC-33-1~4 · 본인 결제 이력 주문 · Should.
- **화면**: 주문 요약, 유형(파손·상태/품질·맛·기타), 설명, 선택 사진 3장, ‘보내면 농가가 직접 확인해요’, 문의 보내기.
- **입출력**: 비공개 attachments 업로드 후 `/api/orders/{orderId}/inquiries` POST. 조회·상태·사진 권한은 계약 6장.
- **동작**: 성공 시 주문 문맥을 가진 SCR-16으로. 생산자는 SCR-28에서 확인·답변·해결/재열기. 해결은 환불 승인이 아니다.

## 7. API

### 7.1 공통

- **기준 주소**: 서버의 `/api`(앱), `/admin`(운영자, Swagger UI), `/s`(공유 링크). 버전 접두어는 쓰지 않는다([server/spec.md](/server/spec.md)).
- **인증**: `Authorization: Bearer <액세스 토큰>`. I1 토큰은 Mock 로그인(`POST /api/auth/test-login`, `app` 필수)으로 받고, I2 소비자 앱은 카카오 로그인(`POST /api/auth/kakao`)으로도 받는다(DEV-32). 토큰에는 계정의 역할(`CONSUMER`·`PRODUCER`)이 들어 있다. 표의 ‘공개’는 토큰 없이 된다.
- **앱 간 토큰**: 소비자 계정과 생산자 계정은 따로다(ADR 0010). 소비자 API를 생산자 계정 토큰으로, 생산자 API를 소비자 계정 토큰으로 부르면 403 `FORBIDDEN`(`details.reason: WRONG_APP`). 앱은 이 응답을 받으면 토큰을 지우고 그 앱의 로그인으로 보낸다. 공개 API와 `GET /api/auth/me`는 두 계정 모두 된다.
- **가입 온보딩**: 소비자 카카오 계정이 온보딩을 마치기 전(`needsOnboarding=true`)에 `POST /api/orders`, `PUT /api/farms/{farmId}/follow`, `PUT /api/messaging/news/{broadcastId}/reaction`, `POST /api/messaging/chats`, `POST /api/messaging/chats/{farmId}/messages`, 소비자의 `POST /api/messaging/rooms/{farmId}/messages`를 부르면 403 `FORBIDDEN`(`details.reason: ONBOARDING_REQUIRED`). 토큰은 지우지 않고 앱이 SCR-06으로 보낸다(FEAT-01 AC-01-12).
- **현재 세션 응답(DEV-252)**: 일반 JSON 요청과 비공개 사진 조회/업로드의 401·403 WRONG_APP는 같은 인증 변경 알림으로 즉시 토큰·보호된 읽기 상태를 지운다. 요청 시작 때의 auth event serial·앱 namespace·토큰이 여전히 현재일 때만 인증/온보딩 부작용을 적용한다. 이전 세션의 늦은 응답은 새 로그인(토큰 문자열이 같아도)을 지우거나 다른 앱 namespace를 바꾸지 않는다.
- **오류 형식**: 모든 오류는 `{"code": "...", "message": "...", "details": {}}`. `message`는 화면에 그대로 보일 한국어 문구(정책 문서), `details`는 필드별 오류·최신 값 등.

  | 상태 | code | 언제 |
  | --- | --- | --- |
  | 400 | `VALIDATION_ERROR` | 입력 형식·필수값. `details.fields`에 필드별 사유 |
  | 401 | `UNAUTHENTICATED` | 토큰 없음·만료 → 로그인(SCR-05) |
  | 403 | `FORBIDDEN` | 역할·승인 상태 부족(N-06); 같은 역할의 타인 자원은 404. 다른 앱 계정의 토큰이면 `details.reason: WRONG_APP` |
  | 404 | `NOT_FOUND` | 없음. 남의 주문·대화도 404 |
  | 409 | `CONFLICT` | 상태·물량 충돌. `details.reason`: `STAGE_CHANGED`, `SOLD_OUT`, `QUANTITY_LIMIT`, `INVALID_TRANSITION`, `IDEMPOTENCY_MISMATCH`, 추가 판매·버전 reason은 계약 1장. 최신 값을 `details`에 담는다 |
  | 413 | `PAYLOAD_TOO_LARGE` | 첨부 개수·용량 초과 |
  | 5xx | `INTERNAL_ERROR` | 서버 오류. AI 실패는 오류로 돌려주지 않고 각 FEAT의 대체 동작(전달, 빈 초안)으로 처리 |

- **페이지네이션**: 목록은 `limit`(기본 20, 최대 50)과 `cursor`. 응답 `{"items": [...], "nextCursor": "..." | null}`. 정렬은 각 화면의 순서를 따른다.
- **멱등 키**: `POST /api/orders`, `POST /api/orders/{orderId}/pay`, 운영자 생산자 결정·공급량 결정·배송 완료·환불은 `Idempotency-Key`(UUID) 헤더가 필수다. 같은 사용자·범위·키는 처음 결과를 그대로 돌려주고, 같은 키에 다른 본문이면 409 `IDEMPOTENCY_MISMATCH`. 키는 24시간 보관한다.
- **서버 시각**: 모든 응답에 `X-Server-Time` 헤더(ISO 8601, 서버의 지금 시각, `FIXED_NOW`를 따른다)를 붙이고 CORS로 노출한다. 앱(`packages/api` `serverNow()`)은 받은 순간의 기기 시각과의 차이를 기억해 3장 ‘시각 판단’에 쓴다. 헤더가 없으면(Mock) 기기 시계를 쓴다(DEV-229).
- **시간 제한**: AI 초안 20초, 문의 응답은 시간을 넘기면 전달(N-04).
- **개인정보**: 응답·로그에 필요한 것만(N-05). 생산자에게 배송 정보(실명·연락처·주소)는 출하 처리 목록의 배송 완료 전 주문만(R-15). 현황·채팅은 이름 앞 글자만.
- **세는 단위**: `reservedCount`는 그 상품을 예약한 사람 수(중복 없음, 화면 ‘n명 예약’), 단계·옵션별 수량은 박스(`StageAllocation.reservedCount`), 주문 수는 건(PRD 용어집).
- **택배사 코드**: `carrier`는 `CJ`(CJ대한통운), `EPOST`(우체국택배), `HANJIN`(한진택배), `LOTTE`(롯데택배), `LOGEN`(로젠택배), `ETC`(기타).
- **경로 순서**: 같은 prefix에서 고정 경로(`/mine`, `/me`, `/following`, `/drafts`, `/stage-presets`, `/producer`)를 경로 변수(`/{productId}`, `/{farmId}`, `/{orderId}`)보다 먼저 등록한다.

### 7.2 엔드포인트

I1 열: Must 화면(4장)이 쓰는 API는 Must, 나머지는 Should다. 단 Must 화면에 있어도 Should 기능으로 이어지는 좋아요·채팅 시작 API는 Should다. 운영자 API는 게시에 필요한 상품 승인만 Must다. 1.2의 신규·변경 API 우선순위는 아래 보충 표를 따른다. Should API를 쓰는 버튼은 API가 준비될 때까지 프론트에서 숨긴다.

### I4 local preview controls — DEV-287
판매·가격 화면과 최종 미리보기에도 같은 위치의 페이지/연필 아이콘으로 보기/편집을 전환한다. 작성 중 언제든 현재 로컬 가격·기간·배송비를 미리보기로 보고 돌아올 수 있으며 전환으로 저장하지 않는다. 미입력은 0원/가짜 날짜 대신 미입력으로 표시한다. 저장·판매 시작 요청에는 기존 검증을 유지하며 판매 요청 전에 최신 입력을 저장하고 새 상품 버전으로 요청한다.

DEV-287: 새 상품 편집은 최종 구매자 화면과 같은 제목·사진·본문 배치에서 제자리 수정한다. 편집 가능 영역은 항상 주황색으로 표시하며, 페이지/연필 아이콘으로 보기/편집을 전환한다. 채팅 목록은 실제 브랜드 로고를 쓴다.

DEV-287: 편집 가능 영역은 선택 전에도 연한 주황 배경·테두리로 표시한다. 구매자 보기에는 표시하지 않는다.

DEV-287: 내용 추가 영역은 제목에서 복원을 빼고, 버튼을 기존 섹션 그림·항목명·오른쪽 +로 표시한다. 상품 소개는 문서 아이콘을 쓴다.

DEV-287: 한눈에 보기 추가 항목을 제거하고 기존 summary 내용을 상품 소개에 이어 표시한다. 원본 필드·근거·제외 상태는 보존한다. 대표사진 추가·교체는 단일 사진 선택기를 바로 열며 AI 시트나 분석을 실행하지 않는다.

DEV-287: 내용 추가는 선택 상태와 독립적으로 enabled에 기록한다. 빈 항목도 여러 개 추가한 상태를 유지하며 구매자에게는 빈 내용을 표시하지 않는다.

DEV-287: 검증 오류는 하단에 작은 오류 문구로 표시하고 해당 입력 위치로 이동해 빨간 테두리를 3회 점멸 후 유지한다. 움직임 줄이기 설정에서는 점멸하지 않는다. 접힌 AI 시트는 평평한 하단 액션 바로 표시한다.

DEV-287: AI 재시도는 비용 확인 체크박스 없이 재시도 버튼 하나로 제공한다. 클릭 즉시 중복을 차단하고 3초 간격을 적용하며 서버의 실행 중·멱등성 보호는 유지한다.

DEV-287: 상단 아이콘 아래에 미리보기(보기 상태에서는 편집하기), AI 초안 문구를 항상 표시한다.

DEV-287: 판매·가격도 상품 사진·이름·상세와 같은 페이지에서 주황색 입력 영역으로 편집하며 상단 미리보기/편집하기 전환을 제공한다. 측정 당도는 새 상품 편집에서 입력한다. 다음 단계 진입은 준비된 대표사진이 필수이고 임시 저장은 사진 없이 허용한다. 분석하지 않은 상품도 수동 초안 반영으로 사진을 넘긴다.

DEV-287: 당도 입력·표시는 측정 당도 하나로 통합한다. 기존 실측값이 있으면 우선 사용하고 없으면 기존 예상값을 보존한다. 입력 변경/삭제 시 두 기존 API 필드를 동기화한다.

DEV-287: 상품 편집의 품종명과 AI 초안은 동일 입력 상태를 공유한다. 앱 내 뒤로 이동할 때 수정사항을 임시 저장한 후에만 임시 저장됐어요를 표시하고 이동하며, 실패하면 입력을 보존하고 현재 화면에 남는다.
