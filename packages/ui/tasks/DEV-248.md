### 목표
Both order-detail buttons pass fromOrder only, which is used for back navigation. The chat screen starts a thread only with start=1 and sends orderId or the first inquiry’s orderId. Thus the reported first-order route never initializes and never supplies its paid-order context.

### 작업
1. Route both order-detail entry points through a single typed helper carrying start=1, orderId, and the existing back-navigation fields.
2. Implement initialize → authorized first-page load → ready as explicit screen states, with retry and terminal access-denied behavior.
3. Send/upload against a visible, validated order context and preserve the originating-order back target.

### 완료 조건
- [ ] Both inline and bottom-bar “농가에 물어보기” actions open the same farm with start=1&orderId=<order>&from=order&fromOrder=<order>. Normalize legacy from=order&fromOrder URLs to the same initialization behavior after server validation.
- [ ] Before the first messages poll, startChat receives that orderId and succeeds; fetch an authorized first page next. Enable sending and photos only after the current session/farm/context has a valid page/thread. Opening never auto-follows or creates an inquiry.
- [ ] A transient start/load failure shows a plain error and an accessible retry action. Retry uses the same initialization key for the same request body. The UI exits the loading state on failure and does not repeat terminal 401/403/404 requests every two seconds.
- [ ] Navigation/auth changes cancel or ignore stale requests. Reset ready, page, errors, and initialization key when the semantic farm/order/session request changes. An old response cannot enable or populate another conversation.
- [ ] The explicitly requested order is used for each send. When reopening from the private list without a route order, use only a server-validated linked order: auto-select if exactly one, require visible selection if several, and explain how to open a paid order if none. Never silently choose inquiries\[0\] or an arbitrary unrelated order.
- [ ] Show the active order context. While unfollowed, the send payload always includes its valid orderId. Upload with exactly one resource: selected orderId for an order-context photo, otherwise the validated threadId. Context changes must not silently reuse photos bound to another order.
- [ ] Failed sends retain the draft and valid photos; retry of the same full payload reuses its key. Changing farm/order/product/text/attachment IDs creates a new semantic payload/key. Add an optional sendScope prop to ChatThread so its pending key includes route context; preserve existing callers by default.
- [ ] Header Back returns to the originating order via DEV-224 rules. General product/info chat still shows the follow notice and follows once. HUMAN and AI-OFF labels remain correct.
- [ ] Screen tests cover first/existing thread, legacy URL, two buttons, transient retry, terminal denial, rapid farm/order switching, multiple-order selection, and draft/photo retry. Sync new error/selection states to Figma v6 or create the repository-required linked design follow-up.
- [ ] 관련 테스트 실제 실행 및 결과 기록
- [ ] 사람 리뷰, main 머지 및 해당 배포 확인
