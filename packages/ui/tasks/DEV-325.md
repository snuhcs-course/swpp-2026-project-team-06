### 목표

### 결정 사항
- 11/15 사본 크기 = 코드에서 가장 크게 그리는 크기 × 3(최대 3배 화면 밀도), 원본보다 크면 원본 크기. WebP `cwebp -q 82 -alpha_q 90`(알파 유지), 축소는 `cwebp -resize`.
- 11/15 파일 이름은 `<원본 이름>.display.webp`. 원본 옆에 두어 어느 원본에서 만들었는지 바로 보이게 한다. e2e가 테두리 주소에 `photo-frame`이 들어 있는지 보므로 이름 앞부분은 유지한다.
- 11/15 사진 테두리는 CSS `border-image`의 9% 9-slice라 비율을 바꾸지 않는다(정사각형 그대로).
- 11/15 크기: 소제목 8종 144px(36px×4, 생산자 추가 버튼 24px도 이것), 당도계 840px, 손 3종 960px(약 316px), 로고 글자형 522px·심볼 120px·흑백/조합형 516px. 주황 배경(전체 폭 stretch, 최대 480×약 620px)과 사진 테두리(최대 약 476px 사진 둘레)는 3배가 원본보다 커서 원본 1254px 그대로 WebP로만 바꾼다.
- 11/15 생산자 새 상품 화면(`NewProductComposer.tsx`) 미리보기 메모이즈는 하지 않는다. `ProductPageBody`를 부르는 곳이 모두 `slots`·`reference`를 매 렌더 새로 만들고, 새 상품 화면의 `slots`는 입력칸(상품명·원산지·품종·당도) 자체와 `form`·`busy`·`activeRun`·`review` 등 수십 개 상태에 묶여 있어 `React.memo`가 건너뛸 렌더가 없다. `toPageData(...)`와 `slots`는 JSX 안 즉시 실행 함수(조건부 렌더) 안에 있어 `useMemo`를 쓰려면 블록 전체를 끌어올려야 해 변경이 크고 위험하다. 버벅임의 주원인인 이미지(아래 기록)만 고친다. 필요하면 후속 이슈로 나눈다.

### 후속 (근거만 적고 이번에 고치지 않음)
- **서버: AI 상세 사진이 원본 해상도 PNG이고 캐시 금지**(가장 큰 후보). 상품사진을 `prepare_photo`가 원본 해상도 PNG로 다시 저장하고(`server/app/source_analysis/photos.py:37`), 공개할 때도 PNG로 복사한다(`publish.py:60-62`). `/api/source-media/{id}`는 `Cache-Control: no-store`로 보낸다(`publish.py:125`). 레포 사진으로 재면 같은 780px도 PNG가 JPEG의 6.0~6.6배다(greenhouse 120,319 → 795,778 B, farmer 152,374 → 925,155 B, orchard-crate 161,310 → 972,065 B). 휴대폰 사진(약 12MP)이면 장마다 수십 MB를 볼 때마다 다시 받는다. 긴 변 상한(예: 1600px) JPEG/WebP 저장과, id가 같으면 캐시 허용이 필요하다(서버 변경).
- **서버: 업로드 사진 크기 변형 없음.** `/api/media`는 받은 파일(최대 10MB, `server/app/core/images.py:9`)을 그대로 저장·제공한다(캐시는 1년 immutable로 좋음). 64~173px 썸네일도 원본을 받는다. 서버가 크기 변형(또는 R2 이미지 변환)을 주기 전에는 앱에서 줄일 방법이 없다.
- **채팅 목록 중복 읽기.** 소비자 채팅 탭에서 배지(8초)와 목록 `useLiveList`(2초/10초, `apps/consumer/src/app/(tabs)/chats/index.tsx:56-61`)가 같은 `/api/messaging/chats` 전체 페이지를 따로 읽는다. 생산자도 배지와 채팅 목록이 `producer/chats`를 따로 읽는다. 공유 저장소가 필요한 구조 변경이다.
- **긴 목록 가상화 없음.** `FlatList`·`SectionList`를 쓰는 곳이 없다. 주문(`apps/consumer/src/app/(tabs)/orders/index.tsx:151,225`), 상품(`apps/producer/src/app/(tabs)/products/index.tsx:92,163`), 채팅(`apps/producer/src/app/(tabs)/chats/index.tsx:128`)이 `allPages`로 전부 받아 `ScrollView` + `map`으로 다 그린다. 지금 데이터 규모(수십 건)에서는 체감이 작고, 바꾸면 스크롤·e2e 가정이 달라지는 구조 변경이라 둔다.
- **PostHog 웹 SDK를 처음부터 싣는다.** `posthog-js`가 생산자 번들 2,140,022 B 중 318,882 B(14.9%, 소스맵 기준)다. `packages/analytics/src/client.ts:17`이 바로 import하지만 켜는 곳은 공식 도메인뿐이다(DEV-125). 동적 import로 나누면 첫 이벤트 시점·번들 분할이 바뀌어 별도 이슈로 둔다. 나머지 큰 묶음은 expo-router 441,593 B(20.6%), react-native-web 290,759 B, react-dom 178,881 B로 줄일 수 없는 기반이다.
- **Mock 전용 데모 사진.** `apps/*/public/photos/farm-story.png` 2,480,484 B(765×2056 PNG)는 `packages/api/src/mock/db.ts:676`(DEV-327이 고치는 파일)에서만 쓰고 운영 화면에는 나오지 않는다. DEV-327 뒤에 JPEG/WebP로 바꾼다.
- **분석 진행 중 폴링이 숨김을 확인하지 않는다.** `apps/producer/src/lib/NewProductComposer.tsx:447`, `SourceWorkspace.tsx:389`은 분석이 도는 동안에만 돌아 영향이 작다. 쉬게 하려면 진행 표시가 늦게 따라오지 않는지 확인이 필요해 이번에는 두었다.
- 확인했지만 원인이 아닌 것: 작은 폼 객체의 `JSON.stringify` 비교, 이미 숨김에서 쉬는 `ChatThread`·`NewsRoom`·`useLiveList`·`useOrderDetail`, 동적 subset CSS인 Pretendard, 네이티브 전용인 앱 아이콘·스플래시, 링크 미리보기 전용 `og.jpg`.
